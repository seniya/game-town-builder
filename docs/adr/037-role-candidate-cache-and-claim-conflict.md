# ADR 037. 역할 후보 캐시와 같은 프레임 예약 충돌 거절 (PERF-002)

Status: Accepted
Date: 2026-09-25
Basis: PERF-002 계측(`tests/perf002.test.ts`, headless Chrome `?scene=perf&load=1000&jumps=0`). 새 외부 조사 없음.
Related: ADR 017 / 029 / 030 / 031 / 032
Amends: ARCHITECTURE 14.4 / 14.5 구현 노트

## 배경

PERF-002 가 두 가지를 찾았다.

1. **같은 프레임 예약 경쟁**: 판단(10 번)이 주민마다 후보를 계산하고 예약은 실행(11 번)에서 잡으므로, 같은 프레임의 두 농부가 같은
   성숙 작물을 받을 수 있었다. 예약은 한 명만 잡혔지만 두 번째 농부도 그 칸으로 걸어갔다(첫 불변식 검사에서 발견).
2. **후보 수 × 역할 주민 수**: 농부·목수가 매 프레임 모든 밭·피해를 훑어, 후보 1000 건·주민 100 명에서 update 평균 11.8 ms,
   p95 15.4 ms 였다(Node).

## 결정

1. NPCSystem 은 새 계획의 밭 칸(farmTarget)이나 시설(facilityClaim)을 **이미 다른 주민이 잡았으면 시작하지 않는다**. 실패 간격(0.5 초)을
   둔 뒤 다음 판단에서 소유 시스템이 예약을 뺀 다른 후보를 준다. 판단은 여전히 순수하다.
2. FarmSystem / RepairSystem 은 **변경 판(revision)** 을 두고, 판과 5 게임분 시각 칸이 같으면 주민별 지난 후보를 돌려준다
   (작물 성숙·예약 해제는 시계로도 바뀌므로 시각 칸을 함께 본다). 이미 칸을 잡고 일하러 가는 농부에게는 그 칸이 유효한 한 그대로 준다.
3. 이것은 MVP 의 역할 후보 조회이며 범용 Job Queue 가 아니다(ARCHITECTURE 14.4). 장기 Job System 은 같은 부하를 실제 생성·claim·취소·완료 경로로 다시 잰다.

## 검토한 대안

- **판단 안에서 임시 예약 집합**: 판단이 프레임 상태를 갖게 되어 순수 함수 계약(14.3)이 깨진다.
- **매 프레임 전체 스캔 유지 + 주기만 늘리기**: 역할 반응이 늦어지고 후보 수에 비례하는 비용은 그대로다.
- **공간 인덱스(칸 격자)**: 장기에는 필요하지만 MVP 밭 8 칸 규모에서는 과하다. 기록만 남긴다.

## 예상되는 결과

- Node: 후보 1000 건 update 평균 11.8 → 2.7 ms, p95 15.4 → 9.8 ms. 후보 100 건 2.4 → 0.6 ms.
- 브라우저(headless): 후보 1000 건에서 60 FPS·하위 1% 56, update p95 7.2 ms.
- 후보 선정은 여전히 후보 수에 비례한다. 대형 월드·후보 1 만 건 규모에서는 공간 인덱스를 도입한다.

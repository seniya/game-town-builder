# ADR 013. 감사 포인트와 마을 레벨을 도입하되, 파생 지표와 축을 분리한다

Status: Accepted
Date: 2026-09-22
Related: ADR 004 (유지), ADR 012

## 배경

ADR 004 는 `WorldState` 를 파생 지표로 정의했다.

건물이 숫자를 직접 올리지 않는다. 지표는 마을의 실제 상태에서 매번 계산되고,
그래서 **내려갈 수 있다.**

이 결정은 유효하며 유지한다.

그러나 DQB2 와 같은 게임이 되려면 이것만으로는 부족하다.

DQB2 의 성장 루프는 다음과 같다.

```text
주민이 방을 사용한다
    ↓
감사 포인트가 쌓인다
    ↓
빌더의 종을 친다 → 포인트를 소비한다
    ↓
마을 레벨이 오른다 (최대 4)
    ↓
새 레시피 / 새 주민 / 주민 능력 향상이 해금된다
```

현재 프로젝트에는 이 회로가 통째로 없다.

플레이어가 얻는 보상은 "주민의 행동이 바뀌는 것" 뿐이다.
20~30 분 MVP 에서는 충분했지만, 수 시간 분량의 게임에서는 성장의 축이 없다.

문제는 ADR 004 와 충돌하는 것처럼 보인다는 점이다.
감사 포인트는 누적되고 단조 증가한다. ADR 004 가 거부한 바로 그 구조다.

## 결정

**두 축은 서로 다른 것을 표현하며, 공존한다.**

```text
축            WorldState (파생 지표)        Gratitude (감사 포인트)
질문          마을은 지금 어떤 상태인가       플레이어는 무엇을 이뤄냈는가
값의 성질      실제 상태에서 매번 계산         누적되고 소비된다
내려가는가      내려간다                      소비할 때만 줄어든다
저장하는가      저장하지 않는다                저장한다
쓰이는 곳      이벤트 조건 / 주민 판단 / UI    해금 / 마을 레벨
```

ADR 004 가 금지한 것은 **"마을의 현재 상태를 누적값으로 표현하는 것"** 이다.
식량 지표가 높은데 창고가 비어 있는 상황을 막기 위한 결정이었다.

감사 포인트는 마을의 상태가 아니다. 플레이어의 누적 성취다.
창고가 비어도 과거에 쌓은 성취가 사라지지 않는 것이 옳다.

**1. 감사 포인트는 주민의 실제 행동에서 발생한다.**

건물을 짓는 순간이 아니다. 주민이 그것을 쓰는 순간이다.

```text
주민이 침대에서 잠들었다          +gratitude
주민이 주방에서 요리를 완성했다     +gratitude
주민이 식탁에서 밥을 먹었다        +gratitude
새 방이 처음 인식되었다           +gratitude (1회)
진행 이벤트를 완료했다             +gratitude
```

이 규칙이 핵심이다.

플레이어가 얻어야 하는 감정은 **"내가 만든 것을 사람들이 쓰고 있다"** 이고,
포인트는 그 장면을 본 대가로 주어져야 한다.

방을 만들었을 때 즉시 포인트를 주면 "만들면 점수가 오르는 게임" 이 된다.
그것은 ADR 002 가 Prefab 에서 우려했던 것과 같은 실패다.

**2. 마을 레벨은 종을 쳐야 오른다.**

자동으로 오르지 않는다. 플레이어가 마을의 종에 상호작용해야 한다.

```text
levelUp 가능 조건 = gratitude >= levelCost[next]
                  AND 파생 게이트 조건을 만족한다
```

파생 게이트 조건은 마을의 **현재** 상태를 본다.

```text
레벨 2    인식된 방 >= 2, housingLevel >= 50
레벨 3    인식된 방 >= 4, foodLevel >= 50, housingLevel >= 100
레벨 4    인식된 방 >= 6, safetyLevel >= 100, happinessLevel >= 70
```

정확한 수치의 정본은 `MVP_SPEC.md` 와 `data/balance.ts` 다.

**3. 마을 레벨은 내려가지 않는다. 게이트 조건은 내려간다.**

몬스터가 벽을 부수면 방 인식이 풀리고 파생 지표가 내려간다.
그러면 **다음 레벨업이 막힌다.** 이미 올린 레벨은 유지된다.

DQB2 는 베이스 레벨 자체를 떨어뜨리지만, 이 프로젝트는 그렇게 하지 않는다.

ADR 005 가 같은 문제를 이미 지적했다.
진행 조건이 다시 거짓이 되면 이벤트가 롤백되어 플레이어가 진행 불가에 빠진다.
해금된 레시피와 도착한 주민을 되돌릴 방법도 없다.

긴장은 "레벨이 깎인다" 가 아니라 "다음 레벨로 못 간다" 로 표현한다.

**4. 해금은 레벨에만 건다.**

레시피, 주민 정원, 가구 종류는 `villageLevel` 을 조건으로 해금한다.
감사 포인트 잔액을 직접 조건으로 쓰지 않는다.

플레이어가 포인트를 아껴야 할지 써야 할지 고민하게 만들지 않는다.
MVP 에서 종 이외의 포인트 소비처를 두지 않는다.

## 검토한 대안

**A. 마을 레벨도 파생값으로 만든다**

`villageLevel = f(방 개수, 주민 수, 지표)` 로 계산한다.

ADR 004 와 완벽히 일관된다. 저장할 것이 없다.

문제:

- 종을 치는 행위가 사라진다. DQB2 에서 종은 단순한 UI 가 아니라
  "마을이 한 단계 올라가는 순간" 을 플레이어가 직접 만드는 의식이다.
- 레벨이 자동으로 오르면 플레이어의 성취가 아니라 시스템의 통보가 된다.
- 몬스터가 벽을 부술 때마다 레벨이 오르내린다. 해금이 롤백된다.

**B. 감사 포인트 없이 레벨만 둔다**

종을 칠 때 파생 조건만 검사한다.

문제는 주민이 시설을 사용하는 장면이 아무 보상도 만들지 않는다는 것이다.
"주민의 사용" 과 "성장" 사이의 인과가 끊어진다.
그 인과가 DQB2 의 성장 루프 전부다.

**C. 감사 포인트를 자유 통화로 만든다 (아이템 구매 등)**

DQB2 는 후반에 실제로 이렇게 한다.

MVP 범위를 넘는다. 소비처가 늘면 가격표라는 새 밸런스 축이 생긴다.
확장 후보로 남긴다.

**D. 방을 만드는 즉시 포인트를 준다**

즉각적인 피드백이라 손맛이 좋다.

문제는 주민이 실제로 쓰지 않아도 보상이 나온다는 것이다.
주민 없이 빈 방만 찍어내는 것이 최적 전략이 된다.
게임의 주제와 정면으로 반대다.

방이 처음 인식되는 순간의 1 회 보너스만 허용하고, 반복 보상은 사용에 건다.

## 예상되는 결과

긍정적:

- 주민을 관찰하는 행위에 기계적인 보상이 붙는다. 플레이어가 마을을 지켜보게 된다.
- 성장의 축이 생겨 수 시간 분량의 진행이 가능해진다.
- 두 축이 분리되어 "지금 상태" 와 "누적 성취" 가 서로 오염되지 않는다.
- 종을 치는 순간이 챕터의 마디가 된다. 연출을 집중시킬 지점이 명확해진다.

부정적 / 위험:

- 저장 대상이 늘어난다. `gratitude`, `villageLevel`, 해금 목록을 저장해야 한다.
  ADR 004 가 얻었던 "SaveData 가 단순하다" 는 이점이 일부 사라진다.
- 포인트 획득 빈도가 밸런스의 새 축이 된다. 너무 느리면 지루하고
  너무 빠르면 종을 치는 순간의 무게가 사라진다.
- 플레이어가 레벨업 게이트 조건을 만족하지 못할 때 이유를 알려줘야 한다.
  종 UI 에 미충족 조건을 반드시 표시한다.
- 주민이 방을 쓰는 순간을 놓치면 포인트가 어디서 나왔는지 모른다.
  획득 시 해당 주민 머리 위에 표시를 띄운다. 연출이 필수다.

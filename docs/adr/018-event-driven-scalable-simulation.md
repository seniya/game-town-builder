# ADR 018. 사건 기반 작업과 다중 주기·LOD·계층 경로를 장기 확장 계약으로 둔다

Status: Accepted — 장기 구조 계약, 전체 구현은 MVP 범위 밖
Date: 2026-09-22
Basis: 사용자 논의 반영 — 두 핵심 축, 주민 50~100명과 대형 마을, 조기 구조 검증
Related: ADR 006 / 008 / 012 / 014 / 015 / 016 / 017

## 배경

ADR 017은 MVP 5명과 주민 100명·대형 월드의 구조 경계를 분리했다.
이번 논의는 아름다운 마을 전체에서 주민이 생활하는 장기 장면을 구체화한다.
주민마다 전체 월드를 검색하거나 모든 판단을 렌더 FPS로 실행하는 구조는 피해야 한다.
동시에 이 장면을 이유로 첫 방·첫 취침 검증보다 대규모 시스템 구현을 앞당겨서는 안 된다.

## 결정

ADR 017을 유지하고 다음 장기 계약을 구체화한다. 인터페이스와 책임의 정본은
[ARCHITECTURE](../project/ARCHITECTURE.md)의 2.3, 3.2~3.3, 9.6, 11.6, 14.4~14.5다.

1. **Job System / Job Queue**: 월드 사건을 해당 도메인 시스템이 작업으로 등록한다.
   NPC는 욕구·시간표·등록된 작업·유효 시설에서 선택한다. 장기 JobSystem이 중복 방지와
   claim을 소유하고 Action은 수행을 담당한다. 결과 소비·생산은 기존 도메인 서비스가
   원자적으로 확정한다. Action 단일 상태와 시설/재료의 단일 예약 소유권을 유지한다.
2. **인덱스 조회**: RoomIndex·FacilityIndex는 RoomRegistry의 결과에서, ResourceIndex는
   자원 소유자에서, JobIndex는 JobSystem에서 파생한다. 지역 인덱스로 후보를 좁히며
   NPC가 블록·가구·작업 대상을 전역 검색하지 않는다.
3. **Multi-rate simulation**: 렌더·플레이어 이동·NPC 이동·판단·장기 상태의 빈도를
   분리할 수 있어야 한다. 구체 Hz는 성능 가설이며 지금 수치로 고정하지 않는다.
   긴급 무효화는 즉시 반영하고 시간 경계는 통과 여부로 처리한다.
4. **Simulation LOD**: 근거리의 실제 행동과 원거리의 추상 진행을 전환할 수 있게 한다.
   npcId·시간·예약·생산·보상은 동일한 사실을 유지하고 상세/추상 실행을 중복하지 않는다.
   렌더 가시성과 별개이며 접근 시 위치와 시설을 재검증한다. 저장 계약은 도입 전에 확장한다.
5. **Hierarchical Navigation**: World Region → Village District → Local Nav → Facility
   Approach Cell의 계층을 장기 목표로 둔다. 경로 Worker는 snapshot·요청 id·revision으로
   분리 가능해야 한다. MVP A*의 continuation·공유 예산·NO_PATH 구분을 유지한다.
6. **대형 복셀 월드**: 16³ Chunk·Uint16Array·Worker greedy meshing·dirty 재메싱을 유지한다.
   장기에는 필요한 청크만 활성/메싱하고 원거리 메시를 해제한다. 미로드를 air로 취급하지
   않으며 방·경로·예약과 청크 경계의 계약을 먼저 정한다. 복셀별 객체 생성은 금지한다.
7. **국소 방 인식**: 변경 → 영향받은 방/문 dirty → 큐 → 공유 예산 처리를 유지한다.
   방 인식의 시설 결과가 AI의 조회 원천이며 대형 마을에서도 전역 flood fill로 바꾸지 않는다.

MVP는 기존 역할 시스템의 변경 기반 후보 목록·예약, 단일 dt, 전 주민 상세 처리,
예산형 A*, 전체 섬 로드로 시작할 수 있다. 범용 Job/LOD/계층 경로/스트리밍의 전체
구현은 요구하지 않는다. Harvest/Cooking/Repair/Haul Job은 장기 예시이며 Haul 메커닉,
광산·광석·허기 수치·음식 부족에 따른 조리 조건을 MVP에 추가하지 않는다.

첫 취침 통과 뒤 TASK-PERF-001에서 큰 fixture·100명 실제 이동·다수 방/가구·경로·메싱을
측정한다. 역할 시스템 완성 뒤 TASK-PERF-002에서 사건 기반 후보·예약·취소 부하를
추가한다. fixture 규모는 TASKS가 정하고, MVP 성능 조건과 별개로 보고한다.
이 결정은 성능 달성 증거가 아니다. 각 장기 기능을 도입할 때 실제 경로로 다시 측정한다.

## 검토한 대안

- NPC마다 월드 검색·매 프레임 전체 판단: 책임과 작업량이 주민 수에 따라 중복되므로 기각.
- 모든 최종 규모 기능을 MVP부터 완성: 감정 목표의 검증을 늦추므로 기각.
- 100개 id 등록만으로 확장성을 검증: 이동·시설·작업·메싱의 결합 비용을 놓치므로 부족하다.
- 현재 책임 경계를 지키고 synthetic 시험으로 조기 점검: 채택. 필요한 내부 최적화는
  측정 후 도입하며 아직 없는 기능의 성능을 입증했다고 주장하지 않는다.

## 예상되는 결과

생활 로직이 특정 주민 수·렌더 주기·상주 월드에 묶이는 것을 줄인다. 대신 Job claim,
시설 예약, LOD 전환, 비동기 결과의 정합성을 명시적으로 검증해야 한다.
MVP의 수치·레시피·콘텐츠는 유지하며 두 재미 검증 지점에서 여전히 멈춘다.
감성 축이 실패하면 기존 팔레트·조명·가구·주민 실루엣과 행동을 개선한다.
어떤 구현 Task나 100명 성능 시험도 이번 문서 개정으로 통과 처리하지 않는다.

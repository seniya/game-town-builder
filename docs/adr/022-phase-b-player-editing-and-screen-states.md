# ADR 022. Phase B의 플레이어 이동·편집 원자성·화면 상태 구현 방식

Status: Accepted
Date: 2026-09-23
Basis: TASK-009~016 구현과 단위 테스트, headless Chrome(ANGLE Vulkan, GTX 1070) 관찰. 새 외부 조사 없음.
Related: ADR 003 / 006 / 011 / 014 / 020 / 021
Amends: 없음. MVP_SPEC 9 / 10 / 29와 ARCHITECTURE 3 / 5 / 6 / 8의 실행 계약을 구현 수준에서 구체화한다.

## 배경

Phase B는 걷기·채집·제작·설치·파괴를 처음으로 연결한다. 명세가 정하지 않았거나
구현에서 선택이 필요했던 지점은 다음과 같다.

- READY-06 / 02 / 03은 물·경계, 지지면 제거, 모달 중 시간·입력을 해당 Task 전에 확정하도록 남아 있었다.
- 3인칭 카메라에서 화면 중앙 조준점과 레이캐스트가 어긋나거나, 캐릭터가 조준점을 가릴 수 있다.
  실내 벽 높이는 최소 2 칸이라 머리 위에 시선 원점을 두면 천장 안에서 시작한다.
- 인벤토리와 VoxelWorld가 각자 즉시 알림을 보내면, 설치 도중 구독자가 "블록은 바뀌고 아이템은
  아직 그대로"인 상태를 읽는다 (MVP_SPEC 10.4, ARCHITECTURE 6.1).
- 브라우저는 Esc로 포인터 락을 풀고, Esc 키 입력으로는 락을 다시 걸 수 없다.

## 결정

1. **물은 경계다 (READY-06).** 발 칸·머리 칸이 water 면 마지막 안전 지면으로 즉시 복귀한다.
   수영·익사·낙하 피해는 없다. 수평 월드 밖과 y < 0 은 플레이어 충돌에서 고체다. 해안 수심 1 칸이
   해변보다 2 칸 낮아 물을 통과시키면 올라올 수 없기 때문이다. 복귀·안전 지면·끼임 해소는
   collision.ts 가 아니라 PlayerMovementSystem 이 소유한다.
2. **지지 조건은 설치 때만 본다 (READY-02).** 지지면이 부서져도 가구·문·침대·횃불·farmland 는 남고,
   연쇄 파괴·드롭이 없다. 한 번의 파괴는 대상 블록 또는 그 다중 칸 객체 전체만 바꾼다.
   예외는 기존 규칙인 farmland 제거 시 crop 제거(TASK-030)뿐이다.
3. **조준 광선을 카메라와 공유한다.** 시선 원점은 발 + 1.6(머리 칸), 카메라 기준 오른쪽 0.6 의
   어깨점에서 시선 방향으로 레이캐스트한다. 카메라는 같은 어깨점에서 시선 반대 방향으로 거리 5.0
   (고체·door 에 막히면 줄인다)에 두고 시선 방향을 본다. `systems/aim.ts` 한 곳이 두 계산을 가진다.
   어깨점이 벽 안이면 시선 원점을 쓴다. 값은 balance.player 에 둔다.
4. **알림은 트랜잭션으로 모은다.** `EventBus.transaction(fn)`이 fn 안의 발행을 모아 끝난 뒤 순서대로
   전달한다. BlockEditSystem 은 모든 조건(범위·점유·캐릭터 AABB·지지·인벤토리 공간/개수)을 먼저
   검사하고, 트랜잭션 안에서 월드 편집과 인벤토리 변경을 함께 커밋한다. 제작은
   `InventorySystem.exchange`(재료 차감 + 결과 추가를 한 계획으로)를 쓴다.
5. **화면 상태는 UI 의 상태 기계다 (READY-03).** 조작 중 / 모달 / 메뉴(+ 락 재요청 중).
   메뉴는 일시정지(main 이 world.update 를 건너뜀), 모달은 시간이 흐르고 조작 입력만
   `InputSystem.setGameplayBlocked` 로 막는다. 조작 중 락을 잃으면 메뉴가 열리고, 게임 시작 화면도
   메뉴다. E 로 닫으면 락을 다시 요청하고 Esc 로 닫으면 메뉴로 간다. 모달 전후에 누르고 있던 키는
   새로 눌러야 게임에 들어간다. 상태 기계는 DOM 을 모르며 부수 효과를 주입받아 테스트한다.
6. **입력은 원시 이벤트 → InputFrame 이다.** InputSystem(game)은 DOM 을 모르고, `ui/domInput.ts` 가
   DOM 이벤트를 넣는다. 다른 시스템은 프레임마다 확정된 InputFrame 만 읽는다.
7. **GameWorld 가 플레이어 쪽 상태 소유자를 만든다.** `playerSpawn` 이 있으면 Player·InputSystem·
   InventorySystem·CraftingSystem·BlockEditSystem·DebugSystem 을 만들고 슬롯에 연결한다. 없으면
   관찰·측정 장면이다(`?view=`). 설치 점유 검사 대상(NPC·몬스터 몸체)은 포트 함수로 주입한다.

## 검토한 대안

- **물 안을 걷게 두기**: 해안에서 올라올 수 없는 구덩이가 생긴다. 계단 해변을 섬 데이터에 넣는 방법은
  연못·플레이어가 판 물가까지 보장하지 못한다. 수영은 38장의 새 메커닉이다.
- **지지면 제거 시 떨어뜨리기·연쇄 제거**: 복셀 중력은 금지 사항이고, 연쇄 제거는 드롭·DamageLog·
  수리 예산의 원자성을 여러 객체로 넓혀 복잡도가 크다. DQB2 류 건축 감각과도 맞지 않는다.
- **카메라 뒤에서 화면 중앙으로 레이캐스트**: 카메라와 캐릭터 사이의 블록을 먼저 맞히고 도달 거리
  5.0 의 기준점이 흐려진다. 머리 바로 뒤 카메라는 캐릭터가 조준점을 가린다.
- **머리 위 시선 원점(2.2)**: 벽 높이 2 칸 실내에서 원점이 천장 안이 된다.
- **InventorySystem 이 VoxelWorld 를 직접 호출**: voxel↔inventory 의존과 소유권 침범이 생긴다.
  이벤트를 늦게 발행하는 별도 큐를 각 소유자에 두는 것보다 EventBus 한 곳이 단순하다.
- **모달 중 일시정지**: 인벤토리를 열어 밤·습격을 피하는 우회가 생긴다. 메뉴만 멈춘다.

## 예상되는 결과

- 물가를 걷다 물에 들어가면 순간 이동처럼 되돌아온다. 불쾌하면 복귀 연출(페이드)을 표현 과제로
  다루며 규칙은 바꾸지 않는다. HR-005 에서 사람이 확인한다.
- 부서진 지지면 위에 가구가 떠 있을 수 있다. 방 판정은 기존 조건(바닥 구멍은 실패)을 그대로 쓴다.
- 트랜잭션 안에서 검증을 통과한 편집이 실패하면 예외로 드러난다(조용히 절반만 반영하지 않는다).
- Esc 로 인벤토리를 닫으면 메뉴를 한 번 거친다. 브라우저 제약이며 실제 창에서의 체감은 HR-005 대기다.
- headless 에서는 포인터 락이 걸리지 않아 락 경로는 단위 테스트와 상태 기계 시뮬레이션으로만 확인했다.

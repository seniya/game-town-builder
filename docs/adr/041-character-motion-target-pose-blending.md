# ADR 041. 캐릭터 동작: 목표 자세 계산과 전환 보간, 렌더 전용 (TASK-ANIM-001)

Status: Accepted
Date: 2026-09-25
Basis: G2 게이트 Q6 "애니메이션 부족"([기록](../state/2026-09-23_2309-task-033-gate-g2-passed.md)), 기존 `NpcView`·`EntityView`·`MonsterView` 구조, 시험 `tests/characterPose.test.ts`. 새 외부 조사 없음.
Related: ADR 008 / 020 / 025 / 026 / 030 / 031 / 032 / 036
Amends: ARCHITECTURE 12.3 구현 노트, MVP_SPEC 31 장

## 배경

G2(TASK-033)에서 확인자는 "주민의 모습과 행동에 정감이 가는가"에 **애매**라고 답했고, 이유로 애니메이션 부족을 들었다. 당시에는 추가하지 않기로 했다.
2026-09-25 사용자가 동작 다듬기를 진행하기로 정했다. 구현 상태는 이랬다.

- 주민(`NpcView`): 자세마다 관절 값을 곧바로 정했다. 자세가 바뀌면 한 프레임에 튀었다(걷다가 침대 위로 순간 이동해 눕고, 의자 위로 튀어 오름).
  수리(목수)는 밭일과 같은 'work' 자세였고, 기절은 광장에 앉아 쉬는 자세와 같았다. 도피(fleeSpeed 5)는 빠른 걸음으로만 보였다.
- 플레이어(`EntityView`): 관절 없는 임시 상자 네 개. 걷기·점프·파괴·설치·공격 동작이 없었다.
- 몬스터: 걷기(튐)·부수기(부딪침)는 있었지만 공격 동작이 없었다.

## 결정

1. **자세 계산은 three 없는 순수 모듈(`render/characterPose.ts`)**: 게임 상태(Action kind·key·자세·lookAt·속도·접지)를 받아 "목표 자세"를 돌려준다.
   관절 회전·몸 이동·뿌리 이동(rootOffset)·눈 높이를 담는다. 시험이 WebGL 없이 자세를 비교할 수 있다.
2. **전환은 교차 보간(PoseBlender)**: 자세 종류(key)가 바뀌면 직전에 그린 자세를 붙잡아 두고 새 목표 쪽으로 smoothstep 으로 섞는다.
   기본은 0.28 초이고, 눕기 0.7, 의자 0.45, 바닥 앉기 0.5, 기절 0.35, 플레이어 0.12~0.18 초다. 같은 종류 안의 움직임(걸음 흔들기)은 목표를 그대로 따른다.
   의자·침대 위로 옮기는 것도 rootOffset 으로 보간하므로, 몸이 접근 셀에서 침대 위로 옮겨 가며 눕는다. 한 프레임에 3 칸 넘게 움직이면 순간 이동으로 보고 보간하지 않는다.
3. **서기 ↔ 걷기 ↔ 달리기는 속도의 연속 함수**: 걸음 비중(0.15~1.2 칸/초)과 달리기 비중(걷기 속도 → 달리기 속도)으로 섞는다.
   멈추거나 출발할 때 다리가 튀지 않는다(시험에서 처음 발견한 불연속을 고쳤다).
4. **구별되는 동작**(라벨 없이): 걷기 / 달리기(앞으로 숙임, 큰 흔들기) / 밭일(허리 굽힘) / 조리(젓기) / 의자·바닥 식사 / 취침 / 수리(서서 망치질, 목수 손에 망치) /
   기절(털썩 주저앉아 고개를 떨굼, 머리가 빙빙) / 대화(손짓·끄덕임). 대기 중에는 숨·체중 옮기기·둘러보기·눈 깜빡임(주민마다 박자가 다름)이 있다.
5. **플레이어**: 관절 모형(다리·몸통·팔·머리, 높이 1.8·폭 0.6 안)이다. 걷기·달리기·점프·낙하, 파괴 중 반복 휘두르기, 설치·공격 한 번 휘두르기를 그린다.
   고개는 시선 피치를 조금 따른다. 팔 동작은 비중(actionWeight)으로 들어오고 나가서 시작·끝에 팔이 튀지 않는다.
   입력은 main 이 읽어 넘긴다. 파괴 중인지는 `BlockEditSystem.breakingPos`, 설치는 `BLOCK_CHANGED`(by 'player', to ≠ air), 공격은 `COMBAT_HIT`(target 'monster')에서 온다.
6. **몬스터 공격**: 공격 간격(1.5 초) 박자로 움츠렸다가 달려든다. 부수기·공격 동작의 비중도 부드럽게 옮긴다. 실제 타격 시각은 CombatSystem 이 정하며 이 박자는 표현이다.
7. **게임 상태는 바꾸지 않는다**: Action·자세 종류·저장 형식·충돌 위치(body.pos)를 그대로 둔다. 애니메이션 상태는 뷰 안에만 있다(ARCHITECTURE 12.3).
   새 Action·자세 종류를 게임에 더하지 않는다. 수리·기절·도피는 이미 있는 kind·key 와 속도로 구별한다.
8. 팔다리의 z 회전 부호: 왼쪽(−x)은 음수, 오른쪽(+x)은 양수가 바깥이다(XYZ 오일러). 처음에 반대로 잡은 것을 headless 관찰에서 고쳤다.

## 검토한 대안

- **골격 애니메이션 파일(glTF + AnimationMixer)**: 모델·리깅 제작이 필요하고, 에셋 파이프라인과 새 의존이 생긴다. 지금 상자 모형의 표현력으로도 Q6 의 부족을 줄일 수 있다.
- **관절마다 지수 감쇠로 목표를 따라가기**: 전환은 부드러워지지만 걸음·젓기처럼 빠른 반복 동작의 진폭까지 줄어든다. 교차 보간은 전환 때만 섞는다.
- **게임 상태에 애니메이션 상태(예: 눕는 중) 두기**: 저장·판단이 렌더 표현에 묶인다. ADR 008 / 020 과 어긋난다.
- **도피용 새 자세 종류 추가**: MVP_SPEC 38 장 금지(새 메커닉)에 가깝다. 속도로 충분히 구별된다.

## 예상되는 결과

- 자세 전환의 한 프레임 변화가 60 FPS 에서 관절 0.2 rad·위치 0.2 칸 미만이다(시험). 보간이 없으면 눕기에서 π/2 가 튄다.
- 드로우콜: 눈은 전에도 상자 두 개였으므로 그대로이고, 목수 망치가 +2, 플레이어 관절 모형이 4 → 13 메시(+9)다.
  mvp-perf(플레이어 없음) 평균이 346 → 348(같은 날 비교)이며 600 미만 목표와 멀다.
  렌더 CPU 는 같은 날 변경 전 1.55~1.8 ms, 변경 후 1.38~1.47 ms 로 늘지 않았다.
- 주민 100 명(PERF-001 장면)에서는 주민마다 매 프레임 작은 객체 몇 개를 만든다. GC 부담은 재지 않았다. 장기 규모에서 원거리 주민 동작 LOD 를 둘 때 함께 본다.
- 동작의 정감·자연스러움은 사람의 판단이 필요하다(HR-030).

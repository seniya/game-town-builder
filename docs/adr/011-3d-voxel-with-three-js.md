# ADR 011. 2D Top-down Phaser 3 를 버리고 3D 복셀 Three.js 로 전환한다

Status: Accepted
Date: 2026-09-22
Evidence: docs/research/2026-09-22-voxel-web-stack.md
          docs/research/2026-09-22-dragon-quest-builders-2.md
Supersedes: ADR 001

## 배경

이 프로젝트의 목표가 **드래곤 퀘스트 빌더즈 2 와 같은 게임**으로 재정의되었다.

DQB2 의 재미는 세 개의 루프가 겹쳐서 발생한다.

```text
1. 요청 루프    주민이 요구한다 → 만들어 준다 → 스토리와 레시피가 열린다
2. 인식 루프    자유롭게 지었는데 게임이 "이건 침실이다" 라고 알아본다 → 주민이 쓴다
3. 성장 루프    감사 포인트가 쌓인다 → 종을 친다 → 마을 레벨 → 새 주민 / 새 레시피
```

이 중 2번이 DQB2 의 정체성이며, 그 전제는 **블록 단위 자유 건축**이다.

ADR 002 는 자유 건축을 MVP 범위에서 제외하고 Prefab 배치를 선택했다.
그 결정의 전제는 "MVP 는 건축의 자유도를 검증하지 않는다" 였다.
목표가 바뀌면서 이 전제가 사라졌다.

Phaser 3 는 2D Canvas / WebGL 스프라이트 엔진이다.
3D 복셀 월드를 만들 수 없다.

## 결정

**1. 게임 엔진을 Three.js 로 교체한다.**

```text
렌더러      three (r180 이상, 메이저 0.18x 계열)
언어        TypeScript 5.x (strict)
빌드        Vite 8.x — SPA. React / Next.js 를 사용하지 않는다 (ADR 003 유지)
테스트      Vitest 3.x
패키지      pnpm
런타임      Node.js 24 LTS
```

Phaser 3, Tiled 맵 에디터는 사용하지 않는다.

**2. 렌더 백엔드는 WebGL2 로 시작한다.**

`THREE.WebGLRenderer` 를 사용한다.

WebGPU 는 지금 채택하지 않는다. 전환 조건을 아래 "WebGPU 전환 조건" 에 명시한다.

**3. Three.js 를 게임 규칙에서 분리하는 규칙을 유지한다.**

ADR 006 (Entity / View 분리) 의 원칙을 그대로 승계한다.
엔진이 한 번 교체된 프로젝트이므로 이 경계는 더 중요해진다.

```text
src/game/**     three 를 import 하지 않는다. 순수 TypeScript.
src/render/**   three 를 import 한다. 게임 상태를 읽어서 그리기만 한다.
```

`src/game/` 아래의 어느 파일도 `three` 를 import 하지 않는다.
이 규칙은 lint 로 강제한다.

## 왜 Three.js 인가

**Babylon.js**

Babylon 9.0 (2026-03) 은 WebGPU 클러스터드 라이팅, 볼류메트릭 라이팅,
Havok 물리 내장, 웹 에디터, 애셋 파이프라인을 제공한다.

그러나 이 프로젝트가 Babylon 에서 얻을 것이 적다.

```text
Havok 물리      복셀 충돌은 그리드 AABB 로 직접 계산한다. 물리 엔진을 쓰지 않는다.
웹 에디터       월드는 코드와 데이터로 생성한다. 씬 파일을 만들지 않는다.
컴포넌트 모델    게임 규칙을 엔진에서 분리하므로 엔진 컴포넌트를 쓰지 않는다.
애셋 파이프라인   복셀 게임의 애셋은 텍스처 아틀라스 1장과 소수의 모델뿐이다.
```

번들은 1.4MB 로 Three.js 의 168KB 보다 크다.

**Three.js**

주간 다운로드 500만으로 Babylon / PlayCanvas 대비 300배다.
복셀 청크 메싱, 그리디 메싱, InstancedMesh 예제와 레퍼런스가 압도적으로 많다.

AI 코딩 에이전트가 문서 기반으로 작업하는 프로젝트에서 레퍼런스 양은 직접적인 비용이다.

우리가 실제로 필요한 것은 다음뿐이다.

```text
BufferGeometry 로 청크 메시를 올린다
텍스처 아틀라스 1장
방향성 광원 + 앰비언트 + 낮/밤 색 보간
카메라 제어
스키닝된 캐릭터 모델 소수
```

Three.js 가 전부 제공한다.

**PlayCanvas / Unity WebGL / Godot Web**

에디터 중심 워크플로다. 씬 파일 비중이 커져 문서 기반 에이전트 협업 비용이 높다.
ADR 001 에서 같은 이유로 제외했고, 그 판단은 유효하다.

**Phaser 3 유지 + 2.5D 표현**

스프라이트로 높이를 흉내내는 방식.

방 인식은 "벽 높이 2 이상" 같은 3차원 조건을 쓴다.
높이가 가짜면 플레이어가 쌓은 벽과 게임이 판정하는 벽이 어긋난다.
자유 건축의 핵심이 무너진다.

## WebGPU 전환 조건

지금 WebGL2 를 선택하는 이유는 이 게임의 월드가 작기 때문이다.

```text
월드        128 × 64 × 128 voxel
청크        16 × 16 × 16
청크 개수    8 × 4 × 8 = 256
```

무한 월드가 아니다. 드로우콜은 수백 단위이고 컴퓨트 셰이더가 필요한 작업이 없다.
그리디 메싱은 Worker 의 CPU 작업이지 GPU 작업이 아니다.

`WebGPURenderer` 는 TSL / NodeMaterial 이라는 다른 재질 시스템을 쓴다.
지금 도입하면 얻는 것 없이 불확실성만 늘어난다.

다음 중 하나가 발생하면 전환을 검토한다.

```text
월드가 256 × 128 × 256 이상으로 커진다
드로우콜이 2000 을 넘는다
GPU 프레임 타임이 예산의 절반을 넘는다
동적 광원이 10 개를 넘는다 (마을 조명)
```

전환 비용을 낮추기 위해 렌더 코드에서 재질 생성을 한 곳에 모은다.

## 검토한 대안

**복셀 엔진 라이브러리 채택 (voxel.js 계열)**

`voxeljs-next` 등이 존재하나 유지보수가 멈춰 있고 TypeScript 지원이 없다.
청크 메싱은 이 게임의 핵심 자산이므로 직접 소유한다.

**블록 하나를 InstancedMesh 인스턴스 하나로 그린다**

구현이 가장 쉽다.

문제는 보이지 않는 면을 그린다는 것이다.
16 × 16 격자 기준 나이브 방식은 24,576 면, 청크 + 면 컬링은 1,536 면이다.
6.25% 로 줄어든다. 월드 전체로 확대하면 차이가 더 벌어진다.

블록 파괴 / 설치가 게임의 핵심 동사인 이상 인스턴스 개별 관리는 유지 비용도 높다.

**청크 크기 32 × 32 × 32**

렌더 드로우콜은 줄지만 블록 하나를 놓을 때마다 32,768 복셀을 다시 메싱해야 한다.

이 게임은 건축 게임이다. 편집 빈도가 매우 높다.
16 × 16 × 16 이 컬링 성능과 편집 반영 속도의 균형점이다.

## 예상되는 결과

긍정적:

- 자유 건축과 방 인식이 가능해진다. DQB2 의 인식 루프를 구현할 수 있다.
- 높이가 실제로 존재하므로 "벽 2칸" 같은 규칙이 플레이어가 본 그대로 판정된다.
- 낮/밤, 실내/실외, 조명이 물리적으로 표현되어 "마을이 살아난다" 는 연출이 강해진다.

부정적 / 위험:

- **기존 ARCHITECTURE.md 의 상당 부분이 무효화된다.** Tilemap, GridPosition 2D,
  NavigationGrid 2D, Phaser Scene 구조, EntityView 의 Sprite 전제가 전부 바뀐다.
- 청크 메싱, Worker 풀, 3D 경로탐색, 복셀 충돌을 직접 만들어야 한다.
  ADR 001 이 피하려 했던 "엔진을 만드는 비용" 을 일부 지불하게 된다.
- 애셋 제작 난이도가 올라간다. 2D 스프라이트보다 3D 모델과 애니메이션이 비싸다.
  플레이스홀더 단계를 길게 유지한다.
- MVP 일정이 20~30 분 분량에서 크게 늘어난다. 새 범위는 MVP_SPEC.md 가 정의한다.

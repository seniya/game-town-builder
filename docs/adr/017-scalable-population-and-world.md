# ADR 017. MVP는 5명으로 구현하고 구조는 주민 100명과 대형 월드 확장을 수용한다

Status: Accepted
Date: 2026-09-22
Basis: 사용자 지시 — MVP 주민 5명, 주민 100명과 대형 월드로 확장 가능한 아키텍처
Related: ADR 006 / 008 / 014 / 015 / 016 / 018 / 019

> ADR 018은 이 결정을 유지하며 Job System·multi-rate·Simulation LOD·계층 경로·
> 인덱스와 조기 synthetic 시험을 구체화한다. 배포·에셋 경계는 ADR 019가 보완한다.

## 배경

현재 MVP는 최대 주민 5명과 128 × 64 × 128 고정 섬을 대상으로 한다.
이 규모를 엔티티·월드·저장 구조의 고정 상한으로 구현하면 이후 규모 확대 때
생활 로직과 공간 처리를 다시 작성해야 한다. 사용자는 MVP 범위를 유지하면서도
주민 100명과 대형 월드로 확장할 수 있는 구조를 요구했다.

## 결정

MVP 콘텐츠 규모와 아키텍처의 확장 목표를 분리한다.
구체적인 구조 원칙의 정본은 [ARCHITECTURE 2.3](../project/ARCHITECTURE.md#23-주민-100명과-대형-월드를-위한-확장-원칙)이다.

- 주민은 id 기반 가변 컬렉션으로 관리한다. 최대 5명은 진행 데이터의 제한이다.
- 월드 크기는 데이터로 주입하며 청크 저장·메싱·국소 변경 처리를 유지한다.
  시스템은 VoxelWorld를 통해 조회하고 전체 상주 방식에 직접 결합하지 않는다.
- 공간 조회의 책임을 모으고, 방·경로 작업은 공유 예산 안에서 나누어 처리한다.
  NPC 판단 시점과 Action 실행의 책임을 분리해 갱신 빈도 조정 경계를 확보한다.
- 주민의 지속 상태와 렌더 View의 수명을 분리한다.
- 저장은 주민 id·청크 좌표에 기반하며 입출력은 SaveSystem이 소유한다.

MVP에서 월드 전체 로드와 일괄 저장은 허용한다. 스트리밍, 원거리 시뮬레이션,
계층 경로 탐색, LOD를 모두 지금 구현하지는 않는다. 확장 단계에서는 미로드 청크의
조회 의미, 방·경로·예약의 경계 처리, 저장 버전을 먼저 명세화한다.

100명·대형 월드의 구체 성능은 아직 검증되지 않았다. 확장 구현 전에 월드 크기,
상주 청크·활성 주민·가시 주민 수, 시험 장치와 성능 기준을 정하고 실제로 측정한다.

## 검토한 대안

- 5명·고정 섬 전용으로 구현하고 나중에 재작성: 현재는 단순하지만 요청한 확장 원칙을
  만족하지 못하므로 채택하지 않는다.
- MVP에서 100명 콘텐츠와 대형 월드 스트리밍까지 완성: 방 만들기와 주민 생활의
  재미 검증을 늦추므로 채택하지 않는다.
- MVP부터 확장 경계를 지키고 측정에 따라 내부 구현을 발전: 현재 콘텐츠 범위와
  장기 구조 요구를 함께 만족시킬 수 있으므로 채택한다.

## 예상되는 결과

주민 수·월드 크기 하드코딩을 피하고 현재 기능을 구현할 때 확장 비용을 검토하게 된다.
TASK-003은 다른 월드 크기 fixture, TASK-028은 100개 NPC id의 registry 처리로
고정 한계가 없는지 확인한다. 이 검사는 100명 생활 시뮬레이션의 성능 보장이 아니다.
TASK-PERF-001/002는 실제 이동·공간·역할 후보 부하를 조기에 점검하고,
TASK-053은 저장 연동과 확장 경계·남은 병목을 기록한다 (ADR 018).

새 게임 메커닉·프레임워크·절차적 지형 생성은 추가하지 않는다.
MVP 콘텐츠 범위·성능 목표와 두 재미 검증 지점은 유지한다.

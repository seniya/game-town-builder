# ADR 038. 저장 슬롯·자동 저장·이어하기

Status: Accepted
Date: 2026-09-25
Basis: ARCHITECTURE 23, TASK-051 구현과 테스트(`tests/save.test.ts` 10 개), headless Chrome 저장·새로고침 확인. 새 외부 조사 없음.
Related: ADR 020 / 022
Amends: ARCHITECTURE 23 구현 노트

## 배경

ARCHITECTURE 23 은 저장 대상·로드 순서·IndexedDB 선택을 정했지만, 언제 불러오는지·어떤 장면을 저장하는지·새로 시작하는 방법·
각 시스템 스냅샷을 SaveData 에 어떻게 싣는지는 구현에서 정해야 했다.

## 결정

1. **고정 섬(기본 장면)만 자동 저장한다.** 시험 장면(`?scene=…`)은 저장하지 않는다. 슬롯은 하나(`small-village / slots / main`).
2. **시작할 때 슬롯이 있으면 이어 한다.** `?new=1` 이면 무시하고 새로 시작한다. 일시정지 메뉴의 "새로 시작" 은 확인 뒤 슬롯을 지우고 다시 연다.
   버전이 맞지 않거나 형식이 잘못되면 SaveRejectedError 로 거부하고 새로 시작하며 이유를 알린다(조용히 깨지지 않는다).
3. **자동 저장 시점**: 매일 07:00(시작 시각이 07:00 전이면 그날부터)과 종을 친 직후. 16 번 슬롯에서 목표 갱신 뒤 커밋된 상태를 캡처한다.
4. **캡처는 structuredClone** 으로 살아 있는 데이터와 분리한다. 쓰는 동안 새 요청은 최신 스냅샷 하나로 합치고 순서대로 쓴다.
   실패하면 IndexedDB 트랜잭션이 되돌아가 이전 슬롯이 남고 SAVE_FAILED 를 알린다. 성공 전에는 "저장됨" 을 보이지 않는다.
5. **각 소유자가 자기 스냅샷을 준다**(sleep / gratitude / arrivals / dialogue / objectives / raids / repair / farm / quarry …).
   SaveData 는 그것을 모으고, 로드는 23.4 순서로 각 소유자의 restore 를 부른다. 임시 Action·예약(조리 재료 예약·시설 예약·몬스터 실행 상태)은 저장하지 않는다.
6. **불러오기는 새로 만든 섬 위에 변경 청크와 배치를 덮는다.** 방은 재판정하며(rebuildAll, 이벤트 없음) 완료 이벤트를 다시 실행하지 않는다.

## 검토한 대안

- **모든 장면 저장**: 시험 장면의 상태가 섞여 관찰이 어긋난다.
- **매 프레임·편집마다 저장**: 약 2MiB 원시 복셀을 자주 쓰게 되고 명세의 시점과 다르다.
- **SaveData 를 명세 그대로의 평면 구조로**: 소유자 스냅샷을 다시 풀어 쓰는 코드가 생겨 두 곳이 어긋날 수 있다. 소유자 스냅샷을 그대로 싣고 차이를 ARCHITECTURE 에 적었다.

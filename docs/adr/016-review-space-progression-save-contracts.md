# ADR 016. 설계 검토를 반영해 공간·진행·저장 계약을 보완한다

Status: Accepted
Date: 2026-09-22
Evidence: docs/research/2026-09-22-review-source-check.md
Related: ADR 003 / 004 / 007 / 008 / 010 / 011 / 012 / 013 / 014 / 015
Review: docs/state/2026-09-22_1802-design-review.md

## 배경

v1.0 검토에서 R01~R18을 확인했다. 빈 방에 고체 가구를 놓으면 형태 판정이 실패하고,
첫 주방에 필요한 가구가 첫 종 이후에만 해금되는 등 정본 사이에 구현 불가능한 경로가 있었다.
실제 구현은 아직 없다. 이번 결정은 사용자가 승인한 검토 반영이며 콘텐츠 범위를 늘리지 않는다.

자유 건축, 자동 방 인식, 단일 방 타입, 게임·렌더 분리, 비가역 성장 원칙은 유지한다.
기존 ADR은 이 원칙에 대해 Accepted 상태를 유지하되 아래 운영 계약을 현재 정본에 적용한다.

## 결정

### 1. 방의 바닥 영역과 보행 영역을 분리한다

가구 점유도 방 면적에 포함한다. 통행에는 아래 고체와 발·머리 비고체를 요구한다.
room과 nav는 voxel/occupancy의 순수 함수를 공유한다.
방 안에서 문까지 연결된 접근 셀이 있는 가구만 시설로 제공한다.
NPC는 접근 셀로 걷고 가구 사용 위치로 자세를 전환한다.
국소 접근성과 외부 주민의 실제 경로는 별도이며 실패 시 대체 행동을 수행한다.

최종 방 타입이 제공하는 시설만 활성화한다.
타입·시설 변화 시 사라진 침대 배정과 예약을 해제한다.
다기능 방을 새로 도입하지 않으며 이 제한의 직관성은 기존 검증 지점에서 확인한다.

### 2. 침대와 문은 원자적인 다중 칸 객체다

VoxelWorld의 PlacementIndex가 id / anchor / facing과 점유 관계를 소유한다.
침대는 수평 두 칸, 문은 수직 두 칸이다.
어느 점유 칸을 편집해도 전체 객체를 설치·파괴·수리하고 드롭은 한 아이템이다.
DamageLog와 SaveData도 원본 배치 정보를 보관한다.
기존 blockId 체계 안에서 표현하므로 새 블록 종류는 추가하지 않는다.

### 3. 완성되지 않은 방도 변경으로 발견한다

기존 방뿐 아니라 변경점에서 바닥 면적 상한으로 제한한 거리 안의 문을 공간 인덱스로 찾는다.
바닥·둘째 층 벽·머리 공간 변경까지 영향을 받는 후보를 큐에 넣는다.
문에서 먼 마지막 벽을 막거나 해제된 방을 복구해도 재인식한다.
여러 문과 공유 문 양쪽은 interior 집합으로 구분·중복 제거한다.
dirty 시설은 새 예약·보상 확정에서 제외하고 직접 파괴는 즉시 사용을 취소한다.

진단은 확인된 원인 좌표 또는 실제 탐색 영역·경로를 보여 준다.
열린 평지에서 구멍 위치를 유일하게 알아냈다고 주장하지 않는다.
진단과 자동 탐색은 프레임 예산을 공유하며 작업을 나눠 실행한다.

### 4. 자원·해금·성장 계산을 연결한다

- leaves는 잎 한 개를 항상 회수하고 씨앗 한 개를 25% 확률로 추가 드롭한다.
  다시 놓은 잎에도 같은 규칙을 적용한다. 씨앗의 유한 공급을 새로 강제하지 않는다.
- cooking_stove / water_pot은 레벨 1로 옮긴다. 레벨 2에서는 window / chest가 열린다.
- 성장 표시 세 단계는 각각 4시간이며 세 번째 단계가 시작되는 8시간에는 미성숙이다.
  12시간 경과 때 수확 가능하다.
- 밭 4칸은 시작 목표다. 첫 종 안내에 8칸 확장과 씨앗 보충을 포함한다.
  주간 업무 기준 일당 8 crop → 12 food를 검증 가설로 두어 주민 5명의 10 food와 비교한다.
- 레벨 비용은 단계별 80 / 200, 총 소비 280이다.
- 최초 방 타입 보상은 등록·타입 변경 모두에서 같은 중복 키를 쓴다.
  취침은 달력 날짜가 아니라 20시에 시작하는 nightId를 쓴다.

### 5. 도착과 습격은 지속 상태의 소유자를 하나로 둔다

ResidentArrivalSystem만 주민 도착을 예약·스폰한다.
레벨별 고유 키로 다음 아침 예약을 만들고 스폰과 완료를 원자적으로 기록한다.
EVENT_NEW_RESIDENT는 주민 5명 도착을 확인하고 대화·연출만 수행한다.

몬스터는 고체 종이 아닌 목표 반경의 통행 셀로 이동한다.
NO_PATH일 때 도달 가능한 경계의 실제 파괴 가능한 객체와 접근 경로를 고른다.
NODE_LIMIT은 다음 프레임으로 이어지는 탐색 예산 중단이며, 무한 재시작하지 않는다.
종은 파괴되지 않는다. 습격당 피해는 점유 복셀 16칸으로 제한한다.
두 칸 객체는 남은 예산보다 크면 부분 파괴하지 않는다.
흙벽 불파괴는 현재 제한으로 남기되 노동량·미관으로 균형이 맞는다고 단정하지 않는다.

### 6. 저장은 프레임 끝의 일관된 지속 상태를 기록한다

IndexedDB 스냅샷은 시간, 누적 변경 청크, 다중 칸 배치, 주민 체력·기절·식사 구간,
침대 배정, 도착 예약, 진행 중 습격, 도달 집합, 피해 예산, 당일 수리량, 목표·대화,
보상 중복 키를 포함한다.
일시적인 Action·경로·시설 예약은 버리고 지속 상태에서 다시 판단한다.
조리는 완료 시 자원을 소비하므로 Action 중단으로 자원이 사라지지 않는다.

로드 중 방 재구축은 보상을 발행하지 않는다.
렌더가 소비하는 dirty 알림과 저장용 누적 변경 청크를 구분한다.
gameMinutes가 시각 정본이며 day/hour/minute는 파생이다.
원시 복셀 2MiB 자체가 localStorage 한도를 넘는다는 설명은 철회한다.
IndexedDB는 구조화된 원자적 저장과 문자열 변환 회피를 위해 선택한다.

### 7. 명시적인 변경 포트와 최신 Worker 결과를 사용한다

다른 시스템의 내부 상태 직접 수정은 금지한다.
생성자로 주입한 gain / spend / 완료·예약 API는 허용한다.
진행 데이터는 계속 순수 커맨드를 반환하고 알림 이벤트와 명령을 구별한다.

메싱 요청·결과에 revision을 넣고 현재 revision일 때만 업로드한다.
AO가 읽는 면·모서리·꼭짓점 이웃 변경도 무효화한다.
월드 원본 배열을 transfer하지 않는다.

### 8. 핵심 검증에 도달하는 순서를 앞당긴다

TASK 번호를 유지하고 TASKS 2.3의 실행 순서를 정본으로 둔다.
027 월드 골격은 초기에, 039 지표 계산은 종 게이트 전에 실행한다.
022 이후 이동·시계·낮밤을 연결하고 농사·요리 전에 033 취침을 검증한다.
최종 게임의 첫 방은 10~20분, 첫 취침은 20~30분을 목표로 측정한다.
90~120분은 최종 분량 가설이며 시간을 채우기 위한 지연을 추가하지 않는다.

Vite 8을 유지하고 공식 지원 근거가 있는 Vitest 4.1 이상 4.x를 사용한다.
근거와 확인 범위는 Evidence의 조사 문서에 있다.
DQB2의 건물 파괴에 따른 레벨 하락은 미확인이므로 결정의 사실 근거에서 제외한다.

## 검토한 대안

- 가구를 전부 비고체로 바꾸기: 충돌·가구 접근성 의미를 훼손하므로 기각.
- 매 편집마다 월드 전체 방 탐색: 단순하지만 편집 비용을 통제하기 어려워 기각.
- 모든 열린 공간에서 정확한 구멍 좌표를 보장: 의도한 경계가 유일하지 않아 기각.
- 침대와 문을 별개의 블록 id들로 표현: 기존 22종에 구현 전용 블록을 늘리는 대신 별도 점유 인덱스를 선택.
- NPC Action 전체 직렬화: 경로·작업 구현에 저장 형식이 종속되므로 지속 사실만 저장.
- 수치 검산을 맞추기 위해 농부가 밤에도 일하게 하기: 취침이라는 핵심 경험과 충돌하므로 밭 확장을 선택.
- 첫 종 전에 주방을 요구하지 않기: 기존 요청 흐름을 유지하기 위해 필수 가구 해금을 앞당김.
- 전체 ADR 폐기: 핵심 결정은 유효하므로 구체 계약만 보완하고 역사적 예시의 범위를 표시.

## 예상되는 결과

빈 방 → 가구 → 주민 사용과 초기 요청 → 첫 종의 문서상 경로가 연결된다.
다중 칸 편집·접근 판정·저장 대상이 늘지만 상태 소유자가 명확해진다.
검토 R01~R18의 수정이 어느 명세·완료 조건에 반영됐는지 추적할 수 있다.

진단의 이해도, 단일 방 타입의 직관성, 흙벽 방어, 8칸 밭의 실제 생산량,
성능·분량은 아직 확인하지 않았다. TASK-022 / 033 / 045 / 053에서 검증한다.
이번 결정으로 어떤 구현 Task도 통과 처리하지 않는다.

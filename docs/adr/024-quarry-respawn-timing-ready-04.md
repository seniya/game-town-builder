# ADR 024. 채석장 재생의 시각·소유자·당일 처리 키 (READY-04)

Status: Accepted
Date: 2026-09-23
Basis: MVP_SPEC 14 / 20 / 32, ARCHITECTURE 3.2 / 4.1 / 5.2 / 23, READY-01 결과(`selectQuarryRespawnCells`). 새 외부 조사 없음.
Related: ADR 014 / 016 / 018 / 020
Amends: MVP_SPEC 14.3·20.3 신설, 32.1 저장 대상, ARCHITECTURE 5.2 `by`·15 책임표·23.1 SaveData·24·27

## 배경

MVP_SPEC 14는 "채석장 노출면은 게임일마다 8 블록 복구"라고만 정했다. READY-01에서 어느 칸을
고를지는 순수 함수로 정했지만, 다음이 비어 있어 TASK-023(게임 시계) 전에 정해야 했다.

- "게임일마다"의 경계 시각. 시작이 Day 1 07:00이라 자정을 쓰면 첫날 밤, 05:00을 쓰면 둘째 날 새벽이 첫 복구다.
- 어느 시스템이 블록을 쓰는가. 블록 변경은 update 4 번 슬롯 뒤의 방·통행 처리와 순서가 맞아야 한다(ARCHITECTURE 4.2).
- 같은 날 두 번 처리하지 않는 기준. 배속 16×, 디버그 시각 강제 설정, 로드가 경계를 다시 넘게 만들 수 있다.
- 저장·로드. 복구된 돌은 변경 청크로 저장되지만, "오늘 이미 복구했는가"는 블록만으로 알 수 없다.
- BLOCK_CHANGED 의 `by`. 기존 `player / monster / npc` 어느 것도 사실이 아니다.

## 결정

1. **매일 05:00 경계 통과 때 한 번.** 직전 프레임 gameMinutes < 그날 05:00 ≤ 현재를 검사한다. 등호 비교를 쓰지 않는다.
   첫 복구는 Day 2 05:00이다. 밤 동안 바뀐 채석장을 아침에 발견하게 하고, 07:00 자동 저장 전에 끝나 그날 저장에 들어간다.
2. **소유자는 `QuarryRespawnSystem`.** update 4 번(blockEdit) 슬롯에서 BlockEditSystem 뒤에 실행한다. 같은 프레임의 방 재판정(5)·
   통행 정리(6)가 이 변경을 본다. 후보는 섬 데이터(`quarryRespawnCandidates`)를 주입받고, 칸 선택은 기존 순수 함수를 그대로 쓴다.
   점유 조회는 플레이어·NPC·몬스터 몸체 목록을 주입받는다.
3. **처리 키 `respawnedThroughDay`.** 마지막으로 처리한 05:00 경계의 day 번호다. 현재 시각의 가장 최근 05:00 경계 day
   (`floor((7·60 + gameMinutes − 5·60) / 1440) + 1`)가 이 값보다 클 때만 처리하고 그 값으로 바꾼다. 시작 값은 시작 시각의
   경계 day(1)다. 한 프레임에 경계를 여러 개 넘어도 한 번만 처리하며 지나간 날을 보충하지 않는다(14.2의 이월 없음과 같은 원칙).
4. **시간은 앞으로만 간다.** 디버그 "시각 강제 설정"은 지정 시각의 다음 도래로 앞당기기만 한다. gameMinutes 가 줄면 이 키와
   nightId·예약 시각이 모두 과거를 다시 처리하거나 영원히 막힌다.
5. **`by = 'world'`를 추가한다.** 드롭·DamageLog·수리 대상이 아니다. 방 재판정과 통행 무효화는 다른 주체와 똑같이 거친다.
6. **저장은 키 하나.** `SaveData.quarry.respawnedThroughDay`. 로드 중에는 처리하지 않고, 로드 뒤 첫 update 에서 남은 경계가
   있으면 한 번 처리한다. 필드가 없는 저장은 gameMinutes 의 최근 경계 day 로 둔다(그날을 다시 복구하지 않는 쪽).
   이번 Task 는 snapshot / restore 만 제공하고 실제 IndexedDB 왕복은 TASK-051 이 검증한다.
7. **점유된 후보는 그날 건너뛴다.** 경계 순간 캐릭터 AABB 와 겹치는 칸은 뒤의 후보로 채우고, 그날 나중에 다시 시도하지 않는다.

## 검토한 대안

- **자정(00:00) 경계**: day 번호와 그대로 맞아 계산이 한 줄 짧다. 그러나 첫날 밤 한밤중에 돌이 생겨 07:00 저장과 관계가 없고,
  몬스터가 활동하는 21:00~05:00 사이에 채석장 몸체가 바뀌어 습격 경로 재계산을 한 번 더 일으킨다.
- **키를 저장하지 않고 로드 때 gameMinutes 로 계산**: 저장이 항상 프레임 끝이면 결과가 같다. 그러나 저장 시점이나 처리 슬롯이
  바뀌면 조용히 중복·누락이 생긴다. 필드 하나로 명시하는 쪽이 ADR 020 의 "지속 사실은 저장한다"와 맞다.
- **지나간 날마다 8 칸씩 보충**: 시각 강제 설정 한 번에 수십 칸이 생긴다. 14.2 가 부족분 이월을 금지한 것과 모순이다.
- **`by = 'npc'` 재사용**: RepairSystem 이 피해 해결로 오인할 수 있다(5.2 의 npc 의미). 사실이 아닌 주체를 쓰지 않는다.
- **점유된 칸을 그날 계속 재시도**: 매 프레임 후보를 다시 훑는 상시 작업이 된다. 이벤트 구동 원칙(ADR 018)과 맞지 않는다.

## 예상되는 결과

- 채석장 복구는 하루 한 번의 이벤트성 작업이다. 상시 비용이 없다.
- 배속·강제 설정·로드 모두 같은 키 비교로 중복을 막는다. 테스트는 시계를 fixture 로 움직여 확인한다.
- 대형 월드의 여러 자원 지대로 넓힐 때도 지대별 키 하나로 같은 구조를 쓸 수 있다(확장 구현은 범위 밖).
- 전제가 틀리면(예: 05:00 이 주민 기상과 겹쳐 보기 어색함) 경계 시각만 바꾸면 되고 키 구조는 유지된다.

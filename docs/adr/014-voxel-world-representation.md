# ADR 014. 복셀 월드를 청크 16³ 와 그리디 메싱으로 표현한다

Status: Accepted — operational details amended by ADR 016
Date: 2026-09-22
Evidence: docs/research/2026-09-22-voxel-web-stack.md
Related: ADR 011

## 배경

ADR 011 이 3D 복셀 월드를 결정했다.

복셀 월드는 두 개의 표현을 동시에 가진다.

```text
데이터 표현    게임 규칙이 읽고 쓰는 블록 배열
렌더 표현      GPU 에 올리는 삼각형 메시
```

블록 하나가 바뀔 때마다 두 표현을 동기화해야 하고,
건축 게임에서는 이 변경이 매우 잦다.

## 결정

**1. 월드 크기**

```text
x  128
y   64
z  128
```

무한 월드가 아니다. 사방이 바다로 둘러싸인 섬 하나다.

y 는 0 이 해수면 아래 바닥, 32 부근이 지표면이다.

**2. 청크는 16 × 16 × 16 이다.**

```text
청크 개수    8 × 4 × 8 = 256
청크당 복셀   4,096
월드 복셀     1,048,576
```

16³ 은 컬링 성능과 편집 반영 속도의 균형점이다.

32³ 은 드로우콜이 줄지만 블록 하나를 놓을 때 32,768 복셀을 다시 메싱한다.
이 게임은 편집 빈도가 높은 건축 게임이므로 편집 비용을 우선한다.

**3. 블록 데이터는 Uint16Array 다.**

```ts
class Chunk {
  readonly blocks: Uint16Array;   // length 4096, index = x + z*16 + y*256
}
```

`blockId` 0 은 공기다.

블록의 성질은 배열이 아니라 **블록 정의 테이블** 이 가진다.

```ts
interface BlockDefinition {
  id: number;
  solid: boolean;          // 충돌 / 통행 차단
  opaque: boolean;         // 면 컬링에 사용
  furniture: FurnitureKind | null;   // 방 레시피 판정에 사용
  breakSeconds: number;
  drops: ItemStack[];
}
```

블록에 인스턴스 상태를 두지 않는다.
문의 열림 상태는 없다. 다중 칸 객체의 anchor·방향·id는 PlacementIndex,
침대 사용자 배정은 SleepSystem이 관리한다 (ADR 016).
1,048,576 개의 객체를 만들지 않기 위한 결정이다.

**4. 메싱은 그리디 메싱으로 하고 Worker 에서 수행한다.**

나이브 렌더링과의 차이는 크다.

```text
나이브        모든 복셀의 6 면을 그린다
면 컬링       인접 블록이 불투명이면 그 면을 버린다
그리디 메싱    같은 재질의 인접한 면을 하나의 큰 사각형으로 합친다
```

빈 주변 공간에 놓인 완전히 채워진 16³ 블록 기준으로 나이브 24,576 면이 청크 + 면 컬링에서 1,536 면이 된다.
6.25% 다. 그리디 메싱은 여기서 더 줄인다.

메싱은 CPU 작업이므로 Worker 풀에서 수행한다.

```text
블록 변경
    ↓
padded가 변경점을 읽는 청크를 dirty로 표시하고 meshRevision 증가 (모서리 AO 포함)
    ↓
메싱 큐에 넣는다 (같은 청크가 이미 큐에 있으면 합친다)
    ↓
Worker 가 메싱하여 transferable ArrayBuffer 로 반환
    ↓
메인 스레드가 최신 revision일 때만 BufferGeometry를 교체한다
```

프레임당 GPU 업로드 청크 수에 상한을 둔다.
건축 중에 연속으로 블록을 놓아도 프레임이 끊기지 않게 하기 위한 것이다.

**5. 텍스처는 아틀라스 1 장이다.**

블록 재질마다 Material 을 만들지 않는다.
아틀라스 1 장 + 청크당 Mesh 1 개로 드로우콜을 청크 수로 고정한다.

반투명 블록(물, 유리)은 별도 Mesh 로 분리한다. 청크당 Mesh 는 최대 2 개다.

**6. 조명은 복셀 광원 전파를 구현하지 않는다.**

```text
구현한다      방향광 (태양) + 앰비언트, 시간에 따른 색/강도 보간
구현한다      정점 AO (그리디 메싱 시 함께 계산)
구현한다      방 안에 놓인 조명 블록 위치에 PointLight (개수 상한)
구현하지 않는다  블록 단위 빛 전파 (flood-fill lighting)
```

빛 전파는 편집할 때마다 재계산 범위가 넓고, 이 게임의 재미에 기여하는 바가 작다.
"실내는 어둡다" 는 방 인식 결과로 판정한다. ADR 012 의 방 판정이 이미
"안 / 밖" 을 알고 있으므로 여기에 기대는 것이 싸고 정확하다.

## 검토한 대안

**A. 블록당 InstancedMesh 인스턴스**

구현이 가장 쉽다.

보이지 않는 면을 그린다. 100 만 복셀 규모에서 성립하지 않는다.
블록 파괴 / 설치가 핵심 동사이므로 인스턴스 인덱스 관리 비용도 계속 발생한다.

**B. 옥트리 / 스파스 자료구조**

메모리를 절약한다.

월드가 약 100만 복셀 고정이므로 `Uint16Array` 전체가 2MB 다. 절약할 이유가 없다.
접근이 O(1) 인 것이 게임 규칙 코드 전체에서 이득이다.

**C. 메인 스레드 메싱**

Worker 통신이 없어 단순하다.

블록을 연속으로 놓을 때 프레임이 끊긴다. 건축 게임에서 치명적이다.

**D. 마칭 큐브 / 부드러운 지형**

DQB2 는 각진 블록 월드다. 목표와 다르다.
방 인식이 "벽 블록" 이라는 이산적 개념에 의존하므로 구현도 불가능해진다.

## 예상되는 결과

긍정적:

- 드로우콜이 청크 수에 비례해 고정된다. 예측 가능한 성능 예산을 세울 수 있다.
- 블록 데이터가 평평한 배열이라 저장 / 직렬화가 단순하다.
- 게임 규칙은 `getBlock(x,y,z) / setBlock(x,y,z,id)` 두 함수만 알면 된다.
  렌더 표현을 전혀 모른다. ADR 011 의 분리 규칙을 지킬 수 있다.

부정적 / 위험:

- 그리디 메싱과 AO 계산을 직접 작성하고 테스트해야 한다.
  메싱 함수는 순수 함수로 두어 Worker 없이 단위 테스트한다.
- 청크 경계의 면 컬링 버그가 나기 쉽다. 인접 청크를 읽어야 한다.
  경계 1 칸을 포함한 18³ 뷰를 Worker 에 넘기는 방식으로 고정한다.
- 조명이 단순해 동굴 같은 공간이 밋밋하다. MVP 이후 확장 후보다.

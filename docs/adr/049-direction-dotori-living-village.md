# ADR 049. 방향 전환: 1인칭 빌더(v1)에서 "가꾸고 지켜보는 살아 있는 마을"(v2 도토리 마을)로

Status: Accepted
Date: 2026-09-26
Evidence: [Generative Agents 조사](../research/2026-09-26-generative-agents.md), [CC0 3D 에셋 팩 조사](../research/2026-09-26-cc0-3d-asset-packs.md), [시험판 제안](../proposals/2026-09-26-world-simulation-prototype.md)
Related: ADR 011(3D 복셀 재정의), ADR 017(확장 가능 구조), ADR 044(귀여운 미술 방향)
Supersedes: v1 정본(docs/project/GAME_DESIGN·MVP_SPEC·ARCHITECTURE·TASKS)의 **다음 개발 기준** 지위. v1 문서와 코드는 동결 보존한다.

## 배경

- v1(드래곤 퀘스트 빌더즈 2 형 1인칭 복셀 빌더)은 MVP Task 를 모두 마치고 두 재미 검증(G1·G2)을 통과했다.
  그러나 2026-09-26 오너는 "지금까지 만든 결과물이 생각보다 재미없다" 고 했다.
- 같은 대화에서 드러난 오너의 동기(메모리·제안 문서 1 장):
  - 어릴 적부터 "컴퓨터로 세상과 삶을 시뮬레이션해 보고 싶다" 는 꿈이 있었다.
  - 어쩌면 시티빌더·도시건설 시뮬레이션을 원했던 것 같다.
  - 재미는 매력적인 그래픽·음악·플롯에서 온다고 보지만, 셋 다 자신이 없다.
  - G1 Q8: "아기자기한 예쁜 집에서 NPC 들이 즐겁게 생활하는 모습을 감상하고 싶다."
- 그 뒤 만든 시험판 도토리 마을(주민 30 명 규칙 기반, 2D·3D)에 대해 오너는
  "내가 지시하여 만들었을 때보다 더 멋지고 근사하게 결과물이 나왔다" 고 했고,
  "나의 계획보다 너의 판단을 믿겠다. 스스로 로드맵을 만들고 게임의 방향성을 잡고 계속 개발을 진행하자" 며
  방향 결정을 에이전트에게 맡겼다(2026-09-26).

## 결정

1. **게임을 "도토리 마을" 로 다시 정의한다.** 비스듬히 내려다보는 3D 마을에서, 성격이 과장된 주민들이 스스로
   일하고 어울리고 사랑하고 소문을 퍼뜨린다. 플레이어는 캐릭터를 조작하지 않는다. **마을을 가꾸고(청사진),
   주민의 마음에 작은 생각을 심고(개입), 지켜본다(관찰).**
2. **최상위 목표 문장은 그대로 둔다.** "아름답게 만든 공간에서 정감 있는 주민이 실제로 살아가는 순간."
   v1 은 "만든 공간" 을 1인칭 블록 쌓기로 풀었고, v2 는 **내려다보며 배치하면 주민이 직접 지어 올리는 것**으로 푼다.
   시험판에 없던 "플레이어가 공간을 만든다" 를 v2 의 첫 핵심 기능으로 둔다.
3. **플롯은 쓰지 않고 생겨나게 한다.** 성격·욕구·관계·소문의 규칙이 부딪혀 이야기를 만든다(드워프 포트리스·림월드·
   Generative Agents 의 원리). 오너가 약하다고 느낀 플롯 부담을 규칙 설계로 바꾼다.
4. **그래픽은 CC0 에셋 팩 + 코드 소품**으로 한다(Kenney Mini Characters, KayKit Medieval Hexagon, Kenney Fantasy Town Kit).
   ADR 045(코드 지오메트리)는 v1 에 한정한다. 에셋은 저장소에 라이선스 원문과 함께 둔다.
5. **새 코드는 TypeScript 로 `src/dotori/` 에 둔다.** 시험판(`prototypes/dotori-village/`)은 비교용으로 남긴다.
   v1 코드(`src/game`·`src/render`·`src/ui`·`src/workers`)는 지우지 않고 동결한다. 빌드·시험은 둘 다 계속 통과시킨다.
6. **구조 원칙은 이어받는다(ADR 017).** 시뮬레이션(`src/dotori/sim/`)은 three·DOM 을 모른다. 주민 수·지도 크기를 고정 한계로
   넣지 않는다. 수치는 `src/dotori/data/` 에 둔다. 공간 격자로 이웃을 찾고, 경로 탐색에 틱당 예산을 둔다.
7. **새 정본은 `docs/dotori/`** 의 네 문서다(DESIGN·SPEC·ARCHITECTURE·TASKS). AGENTS.md 의 읽는 순서를 여기로 옮긴다.
8. **재미 검증 게이트를 새로 둔다.** v1 의 G1·G2(TASK-022·033)는 통과로 닫혀 있다. v2 는 `docs/dotori/TASKS.md` 의
   게이트 VG1(가꾸는 마을)·VG2(분주한 마을)를 사람의 관찰로 통과해야 다음 단계 콘텐츠로 넘어간다.

## 검토한 대안

| 대안 | 판단 |
| --- | --- |
| v1 을 계속 다듬는다(X1 쉬는 방 등) | 오너가 "재미없다" 고 했다. 동작·가구를 더 다듬어도 1인칭 블록 편집의 수고가 "감상" 과 부딪히는 구조는 남는다. 기각 |
| v1 에 시뮬레이션만 얹는다(1인칭 + 주민 30 명) | 복셀 편집·방 판정·1인칭 카메라가 30 명을 한눈에 보는 것과 맞지 않는다. 비용이 크고 시험판의 장점(한눈에 보는 마을)을 잃는다 |
| 시험판 JS 를 그대로 키운다 | 빠르지만 시험·타입·구조 원칙이 없어 100 명·큰 지도로 갈 때 무너진다. 규칙은 옮기고 코드는 TS 로 다시 짠다 |
| 2D 판을 주력으로 | 오너의 반응은 3D 판을 본 뒤에 가장 좋았다("더 멋지고 근사하게"). 3D 를 주력, 2D 는 시험판으로만 남긴다 |
| LLM 으로 주민 대화 | 비용·지연·재현성 문제. 규칙 기반으로 먼저 재미를 확인하고 드문 순간만 나중 후보로 둔다(제안 3.3) |

## 예상되는 결과

- 좋아지는 것: 오너의 꿈(세상 시뮬레이션)과 G1 Q8(감상)에 바로 닿는다. 에셋 팩으로 그래픽 수준이 올라간다.
  100 명 구조 원칙이 콘텐츠 방향과 처음으로 맞는다.
- 잃는 것: v1 의 블록 편집·방 판정·습격·전투는 v2 에 들어오지 않는다. 필요하면 v2 에서 따로 명세한다.
- 위험: 규칙 기반 이야기가 반복되면 금방 질린다(시험판 관찰 필요). 에셋 팩 캐릭터 12 종이 겹친다(모자·색으로 보완).
  모바일·저사양 성능은 아직 측정하지 않았다.
- 되돌리기: v1 은 동결 보존하므로 오너가 원하면 이 ADR 을 Superseded 로 돌리고 v1 로 돌아갈 수 있다.

# ADR 040. 몬스터 추적 탐색 상한과 대상 포기 (TASK-PERF-003)

Status: Accepted
Date: 2026-09-25
Basis: TASK-053 의 36장 측정(`?scene=mvp-perf`, [기록](../state/2026-09-25_0600-task-053-balance-perf.md)), 이 Task 의 시험 `tests/chase.test.ts`와 같은 날 같은 장치에서 변경 전후 빌드를 번갈아 잰 headless 측정. 새 외부 조사 없음.
Related: ADR 015 / 029 / 036
Amends: MVP_SPEC 24.3 의 5, 34 장 `monster`, ARCHITECTURE 18.1 구현 노트

## 배경

종에 닿았거나 부술 것이 없는 몬스터는 반경 12 안에서 가장 가까운 플레이어·주민을 쫓는다(TASK-046). 경로는 1 초마다 대상의 현재 칸으로 다시 찾았다.
대상이 방 안에 숨은 주민처럼 닿을 수 없는 칸에 있으면 A* 가 섬의 통행 영역을 다 훑은 뒤에야 NO_PATH 를 냈다. 이 비용이 1 초마다 되풀이됐다.
몬스터 다섯이 이렇게 하면 프레임당 경로 예산 4000 노드를 여러 프레임 연속으로 다 썼다. TASK-053 브라우저 측정에서 nav 슬롯 최대는 18.5 ms 였다.
예산(노드 수)은 지켰지만, 한 노드의 비용이 기기마다 달라 느린 기기에서는 끊김이 된다. 게다가 닿을 수 없는 대상을 계속 쫓느라 닿을 수 있는 다른 대상은 보지 않았다.

## 결정

1. **요청 하나의 누적 확장 상한**: `PathScheduler.request(from, goal, actor, { maxNodes })` 를 더했다. 누적 확장이 상한에 닿으면 이어 가지 않고
   `reason: 'NODE_LIMIT'`, `continuation: null` 로 끝낸다. 프레임 예산(pathfindMaxNodes)과는 별개이며, 상한이 없는 요청(종 목표 탐색, 주민)은 전과 같다.
2. **추적 탐색은 chaseMaxNodes(800)까지**: 대상은 수평 12 칸 안에 있으므로, 열린 곳이나 집 한 채를 돌아가는 경로는 이 안에서 찾는다.
3. **대상 포기**: 추적 요청이 NO_PATH 이거나 상한에 걸리면 그 대상 id 를 몬스터별로 chaseRetrySeconds(3 실초) 동안 제외한다.
   `CombatSystem.chaseTarget(m, skip)` 이 제외한 id 를 건너뛰고 다음으로 가까운 대상을 준다.
4. **추적 끝**: 쫓을 대상이 없으면 추적 전 모드로 돌아간다. 배회하던 몬스터는 배회(4 초 뒤 종 재탐색)로, 종에 닿은 몬스터는 대기로 간다.
   전에는 배회하던 몬스터도 추적이 끝나면 대기(arrived)로 굳었다. MVP_SPEC 24.3 의 5 "그 경로도 없으면 배회한다" 와 맞춘다.
5. 추적 도중 대상이 바뀌면 이전 대상으로 가는 요청을 취소하고 곧바로 새로 찾는다.

## 검토한 대안

- **닿을 수 있는 영역을 캐시해 두기**(NO_PATH 의 `reachable` 집합 + 그래프 revision): 영역이 작으면 정확하다. 하지만 편집할 때마다 revision 이 바뀐다.
  습격 중에는 플레이어가 자주 편집하므로 무효화될 때마다 섬 전체를 다시 훑게 되고, 첫 탐색의 비용은 그대로 남는다. 상한이 더 단순하고 비용 한도가 확실하다.
- **대상이 방 안이면 쫓지 않기**: 방 판정에 기대야 하고, 방이 아닌 닫힌 공간(흙으로 두른 구멍 등)은 막지 못한다.
- **재탐색 간격만 늘리기(1 → 3 초)**: 비용을 3 분의 1 로 줄일 뿐 요청 하나의 상한이 없다. 닿을 수 있는 대상도 반응이 굼떠진다.
- **pathfindMaxNodes 낮추기**: 종 목표 탐색과 주민 경로까지 느려진다. 이 Task 에서는 바꾸지 않는다.

## 예상되는 결과

- 추적 요청 하나는 최대 800 노드다. 닿을 수 없는 대상은 3 초에 한 번만 다시 시도한다.
  같은 날 같은 장치에서 잰 값은 아래와 같다(headless Chrome 148 ANGLE Vulkan, GTX 1070, `?scene=mvp-perf&view=0&seconds=60&jumps=0&dpr=1`, 60 초).

  | 빌드 | update 평균 / p95 / 최대 | nav 최대 | A* 프레임 확장 최대 | 평균 / 하위 1% FPS |
  | --- | --- | --- | --- | --- |
  | 변경 전(3b6b8d9) 1 | 0.90 / 4.9 / 24.0 ms | 23.7 ms | 4000 | 59.3 / 26.9 |
  | 변경 전 2 | 1.05 / 5.4 / 34.0 ms | 33.9 ms | 4000 | 58.6 / 22.6 |
  | 변경 후 1 | 0.16 / 0.6 / 3.3 ms | 3.2 ms | 1625 | 59.8 / 44.5 |
  | 변경 후 2 | — / — / 3.3 ms | 3.2 ms | 1600 | 60.0 / 56.4 |
  | 변경 후 3 | 0.15 / 0.6 / 7.5 ms | 7.4 ms | 3225 | 59.8 / 44.5 |

  TASK-053 기록(nav 최대 18.5 ms, 하위 1% 59.5)과 변경 전 값이 다른 것은 측정한 날 기계 상태가 달랐기 때문이다. 비교는 같은 날 번갈아 잰 값끼리 한다.
  하위 1% 는 측정마다 편차가 커서(44.5~56.4) 이것만으로 판단하지 않는다.
- 몬스터 다섯이 같은 프레임에 상한까지 쓰면 한 프레임에 4000 노드에 가까워질 수 있다(변경 후 3 의 3225). 평균은 크게 줄었지만 최악 프레임의 상한은 여전히 프레임 예산이다.
- 800 노드 안에 경로를 못 찾는 먼 우회로 끝의 대상은 "닿을 수 없음" 으로 처리해 쫓지 않는다. 좁은 미로 같은 마을에서는 추적이 줄 수 있다. 사람 확인 HR-031.
- 포기 목록은 몬스터 실행 상태이며 저장하지 않는다(로드하면 다시 판단한다).

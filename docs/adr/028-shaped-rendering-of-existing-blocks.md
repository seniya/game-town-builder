# ADR 028. 기존 블록의 비정육면체 모양 표현 — 범위와 시점

Status: Accepted (범위·시점, 2026-09-24 TASK-SHAPE-001 착수 전 구현 방식 보완)
Date: 2026-09-24
Basis: 사용자 의견("DQB2 는 모든 블록이 정사각형 모양이 아니다. 이를 구현해야 오브젝트의 미적 완성도가 높아진다"), 시점 결정(선택지 b). ADR 026(침대·문 모형) 경험.
Related: ADR 011 / 021 / 026
Amends: MVP_SPEC 31(표현), TASKS 2.3(실행 순서), ROADMAP E

## 배경

모든 블록이 1 칸 정육면체로 그려진다. G2 에서 침대·문은 렌더 모형으로 바꿨고(ADR 026) 확인자가 자연스럽다고 했다(HR-010).
나머지 가구·소품도 상자라서 공간을 꾸미는 즐거움(GAME_DESIGN, TASK-022 감성 축)이 모양에서 막힌다.

## 결정

1. **범위는 기존 블록의 모양만.** torch / window / table / chair / chest / cooking_stove / water_pot / crop / bell 이 후보다.
   새 블록 종류(반 블록·계단·울타리 등)는 MVP_SPEC 38 에 따라 만들지 않고 MVP 이후 확장 후보로 둔다.
2. **게임 규칙은 그대로.** 충돌·통행·방 판정·설치·드롭은 blocks 의 기존 필드를 쓴다. 모양은 렌더 표현이다(ADR 026 과 같은 원칙).
3. **시점은 Phase E 의 TASK-032(식사) 뒤, TASK-039 앞.** 요리·식사가 붙어 화덕·식탁·의자가 주민의 사용 장면이 된 다음, 모양과 사용 자세(앉기·조리)를 함께 맞춘다.
4. **방식은 착수 전에 정한다.** 기본 방향: 정적인 모양은 청크 메셔의 "블록 → 상자 목록" 모양 표로 그리고(드로우콜을 늘리지 않는다), 움직이는 것(문)은 모형으로 둔다.
   메셔 성능(TASK-005 / 006 기준)과 AO·면 컬링 규칙을 착수 전에 이 ADR 에 보완한다.

## 검토한 대안

- **지금(PERF-001 전) 구현**: 가구 사용 장면이 아직 없어 모양과 자세를 두 번 맞추게 된다.
- **MVP 이후로 미루기**: 공간을 가꾸는 즐거움이 MVP 검증의 핵심인데, 053 통합 검증까지 상자 가구로 보게 된다.
- **모든 모양을 렌더 모형(PropView)으로**: 가구 수만큼 객체·드로우콜이 늘어 대형 마을 원칙(ADR 017)과 맞지 않는다.

## 예상되는 결과

- Phase E 의 식사 뒤에 한 Task 가 늘어난다. 콘텐츠·규칙은 늘지 않는다.
- 조준 테두리·파괴 균열은 1 칸 상자 기준으로 남을 수 있다. 착수 때 함께 검토한다.

## 보완: 구현 방식 (2026-09-24, TASK-SHAPE-001 착수 전)

Basis: 현재 메셔(`src/workers/greedyMesh.ts`)·셰이더(`materials.ts` 의 `fract(vUv)` 타일 반복)·TASK-031 / 032 의 사용 자세. 새 외부 조사 없음.

1. **모양 표**: `src/game/data/blockShapes.ts` 에 블록별 상자 목록(1/16 단위, 칸 로컬)을 둔다. three 를 모르는 순수 데이터다.
   대상은 torch / window / table / chair / chest / cooking_stove / water_pot / bell. crop 은 이미 CropView 모형(ADR 030), door / bed 는 PropView 모형(ADR 026)이다.
   상자마다 다른 블록의 타일 행을 빌려 쓸 수 있다(예: 화덕 위 냄비는 water_pot 타일).
2. **방향 규칙 두 가지만**: 방향 정보가 없는 단일 칸 블록이라 메셔가 padded 이웃으로 정한다.
   - window: ±x 이웃이 고체(모양 블록 제외)이거나 window 면 판유리를 x 방향으로, 아니면 z 방향으로 세운다(벽 가운데 평면).
   - chair: 맞닿은 table 반대쪽에 등받이를 둔다. 식탁이 없으면 북쪽(−z).
3. **메셔**: 모양 블록은 그리디 마스크에서 빼고 상자마다 여섯 면을 그대로 낸다. 같은 청크 메시(불투명 / 반투명 두 개)에 들어가므로
   **모양 블록 수와 드로우콜이 무관**하다. window 판유리는 반투명 메시, 나머지는 불투명 메시다.
4. **면 컬링**: 모양 블록은 이웃 면을 가리지 않는다(식탁 다리 사이로 바닥이 보인다). 모양 상자의 면이 칸 경계에 있고 그 이웃이
   모양이 아닌 불투명 블록이면 그 면만 지운다. 모양 블록끼리 맞닿은 면은 지우지 않는다(작은 겹침 허용).
   예외: 반투명 모양(window 판유리)은 같은 블록과 맞닿은 경계 면도 지운다. 이어진 창문 사이에 끝면이 비치지 않게 한다.
   블록 정의의 `opaque`(MVP_SPEC 8.1)는 바꾸지 않는다. 메셔 안에서만 "모양 블록은 가리지 않음"으로 본다.
5. **AO**: 모양 상자의 정점 AO 는 1(가려지지 않음)이다. 모양 블록은 이웃의 AO 에도 기여하지 않는다. 작은 상자에 칸 단위 AO 를 쓰면 얼룩이 생기기 때문이다.
6. **UV**: 상자 면의 UV 는 칸 로컬 좌표(0~1)다. 셰이더의 fract 반복을 그대로 쓰며 상자는 타일의 해당 부분을 보인다.
7. **사용 자세와 맞춤**: 의자 앉는 높이를 모양 표의 상수(`CHAIR_SEAT_HEIGHT` = 9/16)로 두고 matchRecipe 의 의자 usePosition 이 쓴다(렌더 전용 필드).
   식탁 윗면은 칸 윗면(1.0) 그대로라 식탁 위 음식(DishView)은 바뀌지 않는다. 화덕 윗면은 13/16 이다.
8. **조준 테두리·파괴 균열**은 1 칸 상자로 둔다. 충돌·설치·조준이 1 칸 규칙이므로 규칙과 표시를 일치시킨다.
9. **성능 기준**: Node 에서 바닥 한 층(16 × 16 = 256 칸)을 모양 블록으로 채운 청크의 메싱이 20 ms 미만(측정값을 기록)이고,
   결과 버퍼는 불투명·반투명 두 벌을 넘지 않는다. 브라우저에서 기존 편집 장면(TASK-006) 기준 33 ms 초과 프레임이 늘지 않는다.

### 결과 (2026-09-24, TASK-SHAPE-001)

- 여덟 블록의 모양을 청크 메시에 넣었다. 기존 충돌·통행·방 판정·설치·드롭 테스트는 바꾸지 않고 모두 통과했다.
- Node: 바닥 한 층(256 칸)을 모양 블록으로 채운 청크 메싱 평균 5.1 ms, 쿼드 4550, 버퍼 두 벌.
- 브라우저(headless, `?scene=perf&residents=5`, 20:10): 모양 표를 끈 빌드와 드로우콜이 같았다(1404 / 1404).
- 사람 확인은 HUMAN_REVIEW HR-016.

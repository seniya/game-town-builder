# ADR 039. 엔딩 연출을 모달로 두고 게임은 계속 진행한다

Status: Accepted
Date: 2026-09-25
Basis: MVP_SPEC 27.1(EVENT_SLICE_END)·28 Phase 6·39 Test 10, ARCHITECTURE 20·23, TASK-052 구현과 `tests/ending.test.ts`, headless Chrome 관찰. 새 외부 조사 없음.
Related: ADR 010 / 038

## 배경

EVENT_SLICE_END 의 조건과 결과(대사 표시·+15·playCutscene)는 TASK-043 에서 이미 만들었다. 남은 것은 연출 자체,
연출 뒤의 계속 플레이, 저장과의 관계였다. 명세의 장면은 "아침. 목수가 부서진 곳을 고치기 시작한다. 주민 5 명이 각자의 일로 흩어진다.
이 마을을 조금 더 키워보고 싶다." 다.

## 결정

1. **엔딩 상태는 게임 쪽 EndingSystem 이 가진다.** CUTSCENE_REQUESTED(slice_end)를 받으면 pending, 연출이 닫히면 played 와 ENDING_FINISHED.
   { pending, played } 는 SaveData.ending 에 싣는다. 연출 전·중에 새로고침하면 이어 할 때 다시 보여 주고, 본 뒤에는 보이지 않는다.
   이벤트 자체는 완료 목록에 있으므로 다시 발생하지 않는다(27.3).
2. **연출은 화면 상태 기계의 `ending` 모달이다.** 조작은 막히고 게임 시간은 흐른다. 그래서 목수의 수리·주민의 출근이 연출용 가짜가 아니라
   실제 시뮬레이션이다. 메뉴만 일시정지라는 기존 규칙(READY-03)을 그대로 쓴다.
3. **카메라 샷은 게임 쪽 순수 함수**(`game/ending/endingShot.ts`)가 종·목수·주민 좌표로 시점·주시점을 계산하고, 렌더(CameraController.showPose)가 적용한다.
   샷 구성·문장·카메라 거리는 `game/data/ending.ts` 에 둔다(연출 표현 데이터).
4. **건너뛰기**: 1 초 뒤 아무 키·클릭은 닫고 조작으로 돌아간다. Esc 는 닫고 메뉴로 간다. 어느 쪽이든 본 것으로 기록한다.
5. **같은 아침의 피해 보고는 엔딩 뒤에 연다.** 두 모달이 같은 프레임에 겹치지 않는다.
6. **엔딩을 본 직후 저장을 요청한다.** 메뉴(일시정지) 중에는 world.update 가 돌지 않으므로 main 이 일시정지 중에도 SaveSystem.update 만 부른다.
   다른 시스템이 멈춰 있어 상태는 이미 커밋되어 있다.

## 검토한 대안

- **연출 중 게임 정지 + 미리 짠 주민 동작**: 주민이 "실제로 살아가는 순간" 이라는 게임 목표(GAME_DESIGN)와 맞지 않고, 연출이 끝난 뒤 위치가 튄다.
- **연출을 렌더만의 상태로 두기**: 연출 중 새로고침하면 엔딩을 영영 못 보거나 매번 보게 된다. 저장할 사실이므로 게임 쪽에 둔다.
- **엔딩 뒤 크레딧·타이틀로 전환**: AC 가 연출 뒤 계속 플레이를 요구한다. 알림 한 줄("마을의 하루는 계속된다")만 띄운다.

## 예상되는 결과

- 목수 컷의 설득력은 피해가 남아 있는지에 달려 있다. 2 차 습격에서 부서진 곳이 없으면 목수는 서 있다. HR-028 에서 확인한다.
- 카메라 충돌은 하지 않는다. 높은 곳에서 내려다보게 두어 대부분 피하지만, 큰 구조물 근처에서는 가릴 수 있다(HR-028).

# ADR 023. Phase C의 방 판정 kernel·재판정 큐·방 식별·진단 구현 방식

Status: Accepted
Date: 2026-09-23
Basis: TASK-017~022 구현과 단위 테스트 71개, headless Chrome 148(ANGLE Vulkan, GTX 1070) 관찰·계측. 새 외부 조사 없음.
Related: ADR 012 / 013 / 015 / 017 / 018 / 020 / 022
Amends: 없음. MVP_SPEC 11 / 12와 ARCHITECTURE 5 / 10 / 26의 실행 계약을 구현 수준에서 구체화한다.
방 판정 조건(MVP_SPEC 11.2 / 12.1 / 12.2)은 바꾸지 않았다.

## 배경

Phase C는 방 판정을 처음으로 게임에 연결한다. 명세가 정한 것은 조건식·실패 사유·재판정 범위·
3 ms 예산이며, 구현에서 선택이 필요했던 지점은 다음과 같다.

- 11.3의 탐색을 "한 셀씩 진행하는 kernel"로 나눠 프레임 예산 안에서 이어서 실행해야 한다.
- 11.6은 작업 키를 (문 anchor, 시작 면)으로 정했지만, 문이 사라졌거나 문 앞 칸이 막힌 방은
  문 작업만으로 해제되지 않는다. 큐가 비었을 때 최신 상태와 일치해야 한다는 조건(10.5)을 못 지킨다.
- 10.4는 "같은 interior의 재판정에서 id를 유지하고 합병·분할은 해제 후 새 등록"이라고만 한다.
  방 안에 기둥 하나를 세우면 interior가 한 칸 줄어 "다른 interior"가 된다.
- ROOM_UNREGISTERED의 reason 은 RoomFailure 인데, 합병으로 사라진 방에는 판정 실패가 없다.
- "벽 틈에 낀 침대"(TASK-019 AC, ARCHITECTURE 25.2)는 12.2의 접근성 규칙으로 해석해야 한다.
- 바닥 구멍(NO_FLOOR)의 좌표가 탐색 칸(y)인지 빈 바닥 칸(y-1)인지 정해지지 않았다.
- 브라우저에서 첫 방 인식 프레임이 5.2 ms 로 예산을 넘었다. 원인은 탐색이 아니라 같은 프레임에
  동기로 실행된 라벨·빛남 메시·AudioContext 생성이었다.

## 결정

1. **탐색 kernel = `RoomSearch`.** `step(n)`이 BFS 한 칸 또는 경계 한 칸의 높이 검사를 한 단계로 진행한다.
   `detectRoom`은 같은 kernel 을 끝까지 돌린다. 시작 칸이 벽 블록이면 내부가 없으므로 TOO_SMALL,
   NO_FLOOR 의 좌표는 비어 있는 바닥 칸(y-1)이다. 문은 아래 anchor 가 이 평면에 있을 때만 문으로 센다
   (한 칸 낮게 놓인 문의 윗칸은 벽 블록으로만 본다). 탐색 내부 집합은 수치 키(x·z ±2^20, y ±2^10)로
   두어 칸마다 문자열을 만들지 않는다. 외부 키는 계속 `posKey`다.
2. **탐색이 읽은 범위로 무효화한다.** `touches(pos)`는 방문 범위의 xz 경계 +1, y 는 바닥(y-1)~벽 최소
   높이다. 진행 중 작업이나 진단이 읽은 칸이 바뀌면 시작점을 최신 상태로 다시 골라 처음부터 한다.
   블록 변경 알림은 편집 슬롯(4)에서 동기로 오고 탐색은 슬롯 5 에서만 진행되므로, 한 호출 안에서
   끝난 결과는 항상 최신이다.
3. **큐 작업은 두 종류다.** 문 작업 `door:(anchor):(면)`과 방 확인 작업 `room:(id)`. 영향 칸(바닥·내부
   두 층·경계 두 층)에 걸린 기존 방은 dirty 가 되고 확인 작업이 그 방의 벽이 아닌 첫 내부 칸에서
   다시 판정한다. 문 작업은 시작 칸이 벽·월드 밖이거나 이미 유효한(dirty 아닌) 방 안이면 건너뛴다.
   두 키 모두 대기 중 중복을 넣지 않는다. 문 공간 인덱스는 32 × 32 xz 버킷이다.
4. **방 식별: 겹치는 기존 방이 하나면 갱신, 둘 이상이면 합병.** 성공한 interior 가 기존 방 하나와만
   겹치면 그 방의 id 를 유지하고 형태·타입·시설을 갱신한다(기둥·가구 추가, 벽 이동 뒤 재인식).
   둘 이상과 겹치면 이전 방들을 `{ reason: 'MERGED' }` 로 해제하고 새로 등록한다. 분할은 먼저 확인된
   쪽이 id 를 이어받고 나머지 쪽은 새 방이다. 최초 타입 보상은 방 id 와 무관하므로(10.4) 보상 규칙에
   영향이 없다. `ROOM_UNREGISTERED.reason` 을 `RoomFailure | { reason: 'MERGED' }` 로 넓힌다.
5. **"벽 틈에 낀 침대" = 문과 이어진 보행 셀이 옆에 없는 침대.** 12.2 그대로, 침대 두 점유 칸의 수평
   이웃 중 하나라도 문 아래 셀에서 이어진 `isStandableCell`(npc) 칸이면 접근 가능하다. 벽과 칸막이 사이
   틈에 넣고 입구를 가구가 막은 경우, 옆 칸 머리 공간이 막힌 경우가 여기에 해당한다. 가구가 벽 줄을
   메워 밖으로 이어지면 8.4 에 따라 방 자체가 성립하지 않는다(가구는 경계가 아니다).
   단일 칸 가구의 objectId 는 posKey, usePosition 은 침대·의자는 점유 칸 윗면 가운데, 화덕·상자는 첫
   접근 셀의 발밑이다(렌더 전용).
6. **진단은 자동 큐보다 먼저, 같은 예산으로.** `beginDiagnosis`는 진행 중 자동 작업보다 먼저 진행되고
   예산이 끝나면 다음 프레임에 잇는다. 재계산 중에는 이전 결과를 계속 보여 주어 걸을 때 깜빡이지
   않게 한다. RoomSystem 은 Tab 을 읽고, 플레이어 칸이 바뀌면 그 칸에서 다시 진단한다. 문 칸에 서 있으면
   시선 앞쪽의 벽이 아닌 이웃에서 시작한다. `RoomDiagnostic`에 start / failureDetail(`outside` 열린 공간,
   `notWall` 벽이 아닌 블록) / roomType 을 더한다. 가구 문제·미충족 레시피·우선순위로 쓰이지 않는 가구를
   `facilityIssues` 로 알려 주되, 확인한 가구 좌표만 가리킨다.
7. **표현은 게임 예산 밖에서.** 방 이벤트 구독자(RoomOverlayView / RoomLabelView / RoomSound)는 이벤트
   안에서 기록만 하고, 메시·DOM 생성은 렌더 단계의 update 에서, 소리는 microtask 에서 한다. 오버레이는
   해제 연출에 쓸 형태를 매 프레임 레지스트리에서 기억한다(로드로 조용히 인식된 방 포함). 합병은 경고
   깜빡임·경고음을 내지 않는다(새 방 등록 연출이 곧 따른다).
8. **로드·장면 초기화는 `rebuildAll`.** 문 목록으로 예산 없이 끝까지 재구축하고 이벤트를 발행하지 않는다.
   관찰 장면(`?scene=room-lab` 등)도 미리 지어 둔 방을 이렇게 조용히 인식한다.

## 검토한 대안

- **문 작업만 두기(명세 문자 그대로)**: 방의 유일한 문을 부수거나 문 앞 칸에 블록을 놓은 경우 그 방이
  dirty 로 영원히 남는다. 삭제 전 소속 방 무효화(11.6 의 3)만으로는 "무효화 뒤 해제"를 끝낼 주체가 없다.
- **interior 가 조금이라도 바뀌면 새 id**: 방 안에 기둥·단을 놓을 때마다 붉은 해제 연출과 새 인식음이
  나서, 공간을 가꾸는 행동이 매번 실패처럼 보인다(GAME_DESIGN 13, TASK-022 감성 축).
- **합병에 기존 RoomFailure 재사용(예: NOT_ENCLOSED)**: 사실이 아닌 사유가 기록·진단·후속 NPC 처리
  (11.7)에 퍼진다.
- **"벽 틈" = 침대 한 칸이 벽 줄에 있으면 무조건 제외**: 12.2 에 없는 조건을 추가하는 셈이고,
  AGENTS 7 의 "방 판정 조건을 임의로 강화" 금지에 걸린다.
- **탐색 키를 문자열 `posKey`로 유지**: 기능은 같지만 칸마다 문자열을 할당한다. 500 편집/s 부하의 최대
  프레임은 바꾸기 전 3.1~11.9 ms, 바꾼 뒤 3.3~7.7 ms(각 3 회)로 실행마다 흔들려 개선 폭은 확인하지
  못했다. 할당을 줄이는 쪽이 대형 월드 원칙(ADR 017)과 맞아 채택했다.
- **라벨을 three 스프라이트(CanvasTexture)로**: 한글 글자 선명도와 화면 공간 겹침 회피가 DOM 쪽이
  단순하다. 투영 계산이 필요하므로 파일은 render/ 에 둔다(`RoomLabelView`).

## 예상되는 결과

- 블록 편집 한 번의 비용은 영향 방 수 + 근처 문 수 × 4 면의 작업으로 제한된다. 월드 크기와 무관함을
  테스트로 확인했다(48 / 160 월드에서 같은 읽기 수).
- headless 브라우저, 방 10 개, 20 편집/s: 방 처리 프레임 최대 3.0 ms, 3 ms 초과 0/300.
  500 편집/s(사람의 약 25 배) 합성 부하에서는 중앙값 1.3~1.5 ms, 초과 1~6/300(최대 7.7 ms).
  단위 작업(탐색 32 단계·결과 반영)은 최대 0.5 ms 로 측정되어, 초과는 예산 논리가 아닌 GC 등 외부
  멈춤으로 본다. 실제 창의 F3 값은 HUMAN_REVIEW 에 올린다.
- 방 id 유지 규칙은 이후 SleepSystem 배정(TASK-033)이 "모양만 바뀐 같은 침실"에서 배정을 잃지 않게
  한다. 분할에서 어느 쪽이 id 를 이어받는지는 탐색 순서에 달려 있으므로, 배정은 방 id 가 아니라
  침대 objectId 와 시설 목록으로 재검증해야 한다(ARCHITECTURE 10.6 과 같다).
- 진단 문구·색은 TASK-022 사람 관찰의 판정·진단 축 결과에 따라 바뀔 수 있다. 조건 자체를 바꿀 때는
  MVP_SPEC·완료 조건을 먼저 개정한다(AGENTS 8).

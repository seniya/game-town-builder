# 0. 이 문서는 한 번 크게 바뀌었다

Version 0.2 까지 이 프로젝트는 **2D Top-down / Prefab 건물 배치** 게임이었다.

Version 1.0 에서 목표가 재정의되었다.

> **드래곤 퀘스트 빌더즈 2 와 같은 게임을 만든다.**

이 변경으로 다음이 폐기되었다.

```text
Phaser 3 / Tiled / 2D Top-down        →  Three.js / 3D 복셀        (ADR 011)
Prefab 건물 4 종 배치                  →  블록 단위 자유 건축 + 방 인식 (ADR 012)
성장 축 없음                           →  감사 포인트 + 마을 레벨      (ADR 013)
방벽은 파괴되지 않는다                   →  몬스터가 블록을 파괴한다      (ADR 015)
20~30 분 MVP                          →  90~120 분 수직 슬라이스
```

유지된 것도 많다. 이 프로젝트의 **철학은 바뀌지 않았다.**

```text
건설 자체를 목표로 만들지 않는다
주민이 플레이어가 만든 것을 실제로 사용한다
지표는 파생값이며 내려갈 수 있다              (ADR 004)
게임 규칙은 렌더 엔진을 모른다                (ADR 006)
```

# 1. 프로젝트 개요

## 프로젝트 목표

플레이어가 폐허가 된 섬을 탐험하고, 자원을 모으고, **블록을 직접 쌓아 공간을
만들면**, 게임이 그 공간을 알아보고 주민들이 그곳에서 살아가기 시작하는
경험을 만든다.

게임의 핵심 문장은 다음과 같다.

> **죽어 있던 작은 마을을 내가 만든 것들로 살아 움직이게 만드는 게임**

이 문장은 Version 0.2 에서 그대로 가져왔다. 바뀐 것은 "내가 만든 것" 의 의미다.

```text
이전    게임이 준 건물을 좋은 자리에 놓는 것
현재    내가 설계한 공간을 게임이 알아보는 것
```

# 2. DQB2 가 실제로 굴러가는 방식

이 게임이 목표로 삼는 구조를 먼저 정확히 적는다.

DQB2 의 재미는 하나의 루프가 아니다. **세 개의 루프가 겹쳐 있다.**

## 2.1 요청 루프 — 건설에 이유를 만든다

```text
주민이 구체적으로 요구한다
    ↓
플레이어가 만들어 준다
    ↓
스토리가 진행되고 새 레시피가 열린다
```

건설 자체가 목표가 되지 않도록 막는 장치다.

Version 0.2 의 진행 이벤트 시스템이 이 루프를 이미 설계해 두었다.
**이 부분은 거의 그대로 살아남는다.**

## 2.2 인식 루프 — DQB2 의 심장

```text
플레이어가 자유롭게 공간을 만든다
    ↓
게임이 "이건 침실이다" 라고 알아본다
    ↓
주민이 그 방을 실제로 사용한다
    ↓
감사 포인트가 쌓인다
```

**이것이 DQB2 가 마인크래프트와 갈라지는 지점이다.**

마인크래프트에서 플레이어가 만든 집은 플레이어에게만 집이다.
게임은 그것이 집인지 모른다.

DQB2 에서는 게임이 알아본다. 그리고 주민이 들어와 산다.

플레이어가 느끼는 감정은 다음과 같다.

> 내가 만든 것이 인정받았다.

Version 0.2 에는 이 루프가 **없었다.** Prefab 을 놓으면 주민이 쓸 뿐이었다.
이번 재설계의 가장 큰 추가분이다.

## 2.3 성장 루프 — 계속할 이유를 만든다

```text
감사 포인트가 쌓인다
    ↓
마을의 종을 친다 → 포인트를 소비한다
    ↓
마을 레벨이 오른다
    ↓
새 레시피 / 새 주민 / 새 가구가 해금된다
    ↓
더 큰 것을 만들고 싶어진다
```

Version 0.2 에는 이 루프도 없었다. 20~30 분 분량이라 필요하지 않았다.

수 시간 분량의 게임에서는 성장의 축이 없으면 플레이어가 멈춘다.

## 2.4 세 루프의 관계

```text
요청 루프   무엇을 만들지 알려준다        →  막막함을 없앤다
인식 루프   만든 것이 의미를 갖게 한다     →  애착을 만든다
성장 루프   계속할 이유를 만든다          →  지속을 만든다
```

셋 중 하나라도 빠지면 게임이 성립하지 않는다.

```text
요청만 있다        시키는 대로 짓는 심부름 게임
인식만 있다        무엇을 지어야 할지 모르는 막막한 샌드박스
성장만 있다        숫자를 올리는 클리커
```

# 3. DQB2 에서 가져오는 것과 가져오지 않는 것

목표가 "DQB2 같은 게임" 이라고 해서 DQB2 의 규모를 복제하지 않는다.

DQB2 는 대형 스튜디오가 수년을 들인 3D 액션 RPG 다.

**가져오는 것은 구조와 감정이지 분량이 아니다.**

## 3.1 가져온다

```text
블록 단위 자유 건축
방 인식 (Room Recipe)
가구 배치의 논리성 판정 (의자는 테이블 옆에)
감사 포인트 → 종 → 마을 레벨
주민이 시설을 실제로 사용하는 생활 AI
주민의 요청으로 시작하는 건설
낮 / 밤 사이클
농사 → 요리 → 식사의 생산 체인
야간 몬스터 습격과 마을 방어
몬스터가 건물을 부순다
천장을 요구하지 않는 관대한 방 판정
```

## 3.2 지금은 가져오지 않는다

```text
여러 챕터 / 여러 섬 / 아이템 리셋 구조
영구 거점 (각성의 섬) 과 챕터 섬의 이중 구조
보스 전투
무기 / 방어구 / 장비 성장
주민이 청사진을 대신 지어주는 자동 건설
주민 직업 10 종 이상 (광부 / 상인 / 가수 / 무희 / 병사)
탈것 / 비행
감사 포인트의 화폐화 (상점 구매)
멀티플레이
```

이 목록은 "영원히 안 한다" 가 아니다. **수직 슬라이스 검증 전에는 안 한다** 다.

## 3.3 DQB2 와 다르게 한다

의도적으로 다르게 가는 부분이다.

**마을 레벨은 내려가지 않는다.**

DQB2 는 몬스터가 건물을 부수면 베이스 레벨이 떨어진다.

이 프로젝트는 레벨을 떨어뜨리지 않는다.
대신 **다음 레벨로 가는 문이 닫힌다.**

이유는 ADR 013 에 있다. 해금된 레시피와 이미 도착한 주민을 되돌릴 방법이 없고,
진행이 롤백되면 플레이어가 진행 불가에 빠질 수 있다.

긴장은 "빼앗긴다" 가 아니라 "나아가지 못한다" 로 표현한다.

**지표는 누적 점수가 아니라 파생값이다.**

ADR 004 의 결정을 유지한다.

```text
foodLevel        창고의 음식 / 주민이 며칠 먹을 양
housingLevel     침대 수 / 주민 수
safetyLevel      직전 습격에서 막아낸 비율
happinessLevel   위 셋의 가중 평균
```

건물을 지어서 숫자를 올리는 것이 아니다.
마을의 실제 상태를 읽어서 계산한다. 그래서 **내려간다.**

감사 포인트는 이것과 완전히 다른 축이다. 자세한 것은 ADR 013 에 있다.

# 4. 플레이어가 느껴야 하는 감정

기능보다 아래 감정 흐름을 우선한다.

## 4.1 발견

폐허가 된 섬에 도착한다.

> 여기에 예전에는 사람들이 살았던 것 같다.

## 4.2 필요

주민의 문제를 발견한다.

> 이 사람들에게 지금 필요한 것이 있다.

## 4.3 시행착오

벽을 쌓는다. 문을 단다. 침대를 놓는다.

> 이 정도면 방이 되지 않을까?

**이 감정은 Version 0.2 에 없었다.** Prefab 은 놓으면 끝이었다.

## 4.4 인정

방이 인식된다. 화면에 방 이름이 뜬다.

> 알아봤다.

**이 순간이 이 게임의 가장 중요한 한 점이다.**

## 4.5 변화

밤이 되자 주민이 그 방으로 걸어 들어가 침대에 눕는다.

> 내가 만든 곳에서 자고 있다.

## 4.6 성취

감사 포인트가 쌓이고, 종을 친다. 마을 레벨이 오른다.

> 마을이 한 단계 올라갔다.

## 4.7 기대

새 주민이 오고, 새 가구가 해금된다.

> 다음에는 무엇을 만들어볼까?

이 감정 흐름이 발생하지 않는 기능은 우선순위를 낮춘다.

# 5. 수직 슬라이스 범위

첫 번째 버전은 여전히 작게 만든다. 다만 Version 0.2 보다는 크다.

목표는 콘텐츠 양이 아니라 **세 루프가 전부 돌아가는지 검증하는 것** 이다.

```text
분량        90 ~ 120 분
월드        128 × 64 × 128 복셀 섬 1 개
블록        22 종 (air 제외)
방 레시피    5 종 (빈 방 / 침실 / 주방 / 식당 / 창고)
주민        3 명 시작 → 마을 레벨로 최대 5 명
마을 레벨    1 → 3
몬스터 습격   2 회
진행 이벤트   8 개
```

한 챕터도 아니다. **한 챕터의 앞부분** 이다.

정확한 정본은 `MVP_SPEC.md` 다.

# 6. 월드

## 섬 하나

```text
마을 터       폐허. 부서진 벽과 기초만 남아 있다
숲            나무 / 씨앗
채석장        돌
물가          물 / 점토
어두운 외곽    밤에 몬스터가 나온다
```

사방이 바다다. 절차적 생성을 쓰지 않는다.
섬은 고정된 데이터로 만들고, 그 위를 플레이어가 자유롭게 바꾼다.

## 지형과 건축물을 구분한다

```text
지형 블록      흙 / 풀 / 돌 / 원목. 몬스터가 부수지 않는다
플레이어 블록   플레이어가 놓은 모든 것. 몬스터가 부순다
```

이 구분이 없으면 몬스터가 섬을 관통하는 터널을 판다. ADR 015 에 근거가 있다.

# 7. 건축

## 7.1 플레이어는 블록을 놓고 부순다

건물이라는 배치 단위는 존재하지 않는다.

```text
좌클릭    블록을 부순다
우클릭    선택한 블록을 놓는다
휠 / 숫자  손에 든 블록을 바꾼다
```

## 7.2 방은 규칙으로 인식된다

플레이어가 "여기를 침실로 지정" 하지 않는다. **게임이 판정한다.**

빈 방 조건:

```text
바닥이 있다
벽으로 완전히 둘러싸여 있다
벽 높이가 2 칸 이상이다
문이 1 개 이상 있다
바닥 면적이 상한 이하다
천장은 필요 없다
```

천장을 요구하지 않는 것은 DQB2 와 같다.
플레이어가 방을 만들고도 인식되지 않는 좌절을 줄이기 위한 선택이다.

## 7.3 방 타입은 가구로 결정된다

```text
침실     침대
주방     조리대 + 물통
식당     식탁 + 의자 + (식탁 위의) 음식
창고     상자
```

개수만 세지 않는다. **배치가 논리적이어야 한다.**

```text
의자는 식탁 옆에 붙어 있어야 한다
음식은 식탁 위에 있어야 한다
침대는 최소 한 면이 통행 가능해야 한다
```

마지막 조건이 특히 중요하다.
주민이 도달할 수 없는 침대는 침대가 아니다.

## 7.4 인식되지 않으면 이유를 알려준다

**이것은 선택 기능이 아니라 필수 기능이다.**

플레이어가 방을 만들었는데 인식되지 않고 이유도 모르면 게임이 그 자리에서 끝난다.

```text
"벽이 한 칸 뚫려 있습니다"     → 해당 좌표를 하이라이트한다
"문이 없습니다"
"벽 높이가 부족합니다"
"침대가 벽에 막혀 있습니다"
```

방 판정에 실패한 공간을 플레이어가 조사할 수 있어야 한다.

# 8. 주민 생활

## 8.1 NPC AI 의 목적은 하나다

> **플레이어가 만든 공간을 주민들이 실제로 사용하게 한다.**

기술 시연이 아니다.

## 8.2 생활 주기

```text
아침    기상 → 방에서 나온다
오전    각자의 업무
점심    식당 또는 광장에서 식사
오후    업무 / 자유 행동
저녁    식사 → 모닥불 주변
밤      침실로 귀가 → 취침
```

## 8.3 시작 주민 3 명

### 농부

```text
역할      밭 관리 / 씨앗 심기 / 수확
초기 문제  밭이 망가져 식량을 생산할 수 없다
```

### 요리사

```text
역할      작물 수집 / 조리 / 음식 배급
초기 문제  요리를 할 공간과 화덕이 없다
```

### 목수

```text
역할      파괴된 블록 수리 / 방어 관련 요청
초기 문제  마을을 지킬 것이 아무것도 없다
```

**목수의 역할이 Version 0.2 보다 강해졌다.**

몬스터가 블록을 부수게 되었으므로(ADR 015), 목수에게
"낮에 파괴된 곳을 고친다" 는 명확한 일이 생겼다.

다만 목수가 모든 피해를 되돌리면 플레이어가 개입할 이유가 없다.
하루에 고칠 수 있는 양에 상한을 둔다.

## 8.4 주민이 방을 쓰는 순간이 보상이다

감사 포인트는 **건설할 때가 아니라 사용될 때** 발생한다.

```text
주민이 침대에서 잠들었다        +
주민이 주방에서 요리를 끝냈다     +
주민이 식탁에서 밥을 먹었다      +
새 방이 처음 인식되었다         + (1 회)
```

건설 즉시 포인트를 주면 "만들면 점수가 오르는 게임" 이 된다.
주민 없이 빈 방만 찍어내는 것이 최적 전략이 되어버린다.

**포인트를 얻으려면 주민이 사는 모습을 봐야 한다.**

## 8.5 획득은 반드시 눈에 보여야 한다

포인트가 언제 어디서 나왔는지 모르면 인과가 끊어진다.

주민 머리 위에 표시가 뜨고, 그 주민이 무엇을 하고 있었는지 보여야 한다.

---

# 9. 마을의 종

## 9.1 레벨은 자동으로 오르지 않는다

플레이어가 마을의 종에 직접 상호작용해야 한다.

```text
감사 포인트가 충분하다
    AND
마을의 현재 상태가 게이트 조건을 만족한다
    ↓
종을 친다
    ↓
포인트를 소비하고 마을 레벨이 오른다
    ↓
해금 / 새 주민 도착
```

종을 치는 것은 UI 조작이 아니라 **마을이 한 단계 올라가는 의식** 이다.
연출을 여기에 집중시킨다.

## 9.2 게이트 조건은 마을의 현재 상태를 본다

```text
레벨 2    인식된 방 >= 2, housingLevel >= 50
레벨 3    인식된 방 >= 4, foodLevel >= 50, housingLevel >= 100
```

몬스터가 벽을 부수면 방 인식이 풀리고 게이트가 닫힌다.
**이미 올린 레벨은 유지된다.**

## 9.3 미충족 조건을 반드시 보여준다

종 UI 는 "칠 수 없음" 만 표시하면 안 된다.

```text
감사 포인트   120 / 100   OK
인식된 방      1 / 2       부족
housingLevel  33 / 50     부족
```

무엇을 해야 하는지가 그 자리에서 보여야 한다.

# 10. 방어

## 10.1 몬스터는 벽을 부순다

```text
경로가 있다    → 마을 중심으로 이동한다
경로가 없다    → 앞을 막은 플레이어 블록을 부순다 → 다시 경로를 찾는다
```

지형 블록은 부수지 않는다. 우회한다.

## 10.2 벽이 영구 해결책이 아니다

Version 0.2 의 방벽은 파괴되지 않았다.
자유 건축에서 그렇게 하면 마을을 한 번 둘러싸는 것으로 방어가 끝난다.

부서지기 때문에 다음이 생긴다.

```text
더 두꺼운 벽을 쌓을 동기
더 단단한 재질을 찾을 동기
목수의 존재 이유
아침에 마을을 둘러볼 이유
```

## 10.3 아침에 피해를 보여준다

플레이어가 자는 사이 마을이 부서져 있는 경험은 불쾌할 수 있다.

```text
피해 규모에 상한을 둔다
아침에 피해 요약을 보여준다
파괴된 좌표를 지도 / 월드에 표시한다
```

## 10.4 safetyLevel 은 결과로만 계산한다

```text
safetyLevel = 100 × (마을 중심에 도달하지 못한 몬스터 수) / (직전 습격의 총 수)
```

벽을 사전에 채점하지 않는다.

채점하면 플레이어가 미학이 아니라 점수를 위해 벽을 쌓는다.
그러면 방어라는 상황이 사라지고 체크리스트가 남는다.

---

# 11. 진행 이벤트

## 11.1 진행은 시간이 아니라 플레이어의 행동으로 흐른다

```text
좋은 조건    "첫 번째 침실이 인식되었다"     플레이어가 만들었기 때문에 발생
나쁜 조건    "게임 시간 2 일 경과"          플레이어가 무엇을 했든 발생
```

시간 기반 조건은 최소한으로 쓴다.

## 11.2 모든 조건은 결정적이다

"첫 번째 밤 또는 두 번째 밤" 같은 모호한 조건을 쓰지 않는다.
게임 상태만으로 참 / 거짓을 판정할 수 있어야 한다.

## 11.3 완료된 이벤트는 롤백되지 않는다

조건이 다시 거짓이 되어도 이미 완료된 이벤트는 되돌리지 않는다.

몬스터가 벽을 부술 수 있게 되었으므로(ADR 015) 이 규칙이 필수가 되었다.

정본은 `MVP_SPEC.md` 의 필수 이벤트 목록이다.

# 12. 첫 번째 플레이 경험

## 도착

플레이어가 폐허가 된 섬에 도착한다. 살아 있는 주민은 세 명뿐이다.

목표 표시:

> 섬을 둘러보세요.

대사가 플레이어를 붙잡고 먼저 시작되지 않는다.
플레이어가 직접 다가가서 말을 거는 것이 첫 행동이 된다.

## 첫 번째 블록

플레이어가 나무를 베고, 흙을 파고, 처음으로 블록을 놓아 본다.

이 단계에서 아직 방도 주민 행동도 없다.
**블록을 놓고 부수는 것 자체가 기분 좋아야 한다.**

## 첫 번째 문제 — 밭

농부:

> 밭이 망가져서 먹을 것을 만들 수 없어.

플레이어가 밭흙을 깔고 씨앗을 심는다.

농부가 밭으로 걸어가 일을 시작한다.

## 첫 번째 방 — 이 게임의 분기점

밤이 되어도 주민들이 광장에 앉아 있다.

목수:

> 밥은 먹었지만, 잘 곳이 없어.

플레이어가 벽을 쌓고, 문을 달고, 침대를 놓는다.

**아무 일도 일어나지 않는다.** 벽 한 칸이 뚫려 있다.

플레이어가 진단 UI 로 뚫린 곳을 찾아 막는다.

```text
   침실
```

화면에 방 이름이 뜬다.

밤이 되자 주민이 그 방으로 걸어 들어가 침대에 눕는다.
감사 포인트가 주민 머리 위에 뜬다.

**이 장면이 만족스럽지 않으면 이후 단계를 진행하지 않는다.**

## 첫 번째 종

감사 포인트가 쌓였다. 게이트 조건을 만족한다.

플레이어가 마을의 종을 친다.

마을 레벨 2. 새 가구가 해금되고, 새 주민이 섬에 도착한다.

## 첫 번째 밤 습격

몬스터가 나타난다. 벽이 없는 쪽으로 들어와 주민을 위협한다.

목수:

> 이대로는 마을을 지킬 수 없어.

## 두 번째 밤 습격

플레이어가 마을을 둘러쌌다.

몬스터가 벽 앞에서 멈추고, 벽을 부수기 시작한다.
플레이어가 직접 막아선다. 벽 몇 칸이 부서지지만 마을은 지켜진다.

아침에 목수가 부서진 곳을 고치기 시작한다.

## 수직 슬라이스 종료

마을 레벨 3. 주민 5 명.

> 이 마을을 조금 더 키워보고 싶다.

이 문장이 나오면 성공이다.

# 13. 핵심 피드백 연출

변화는 반드시 눈에 보여야 한다. 내부 수치만 바꿔서는 안 된다.

```text
블록을 부순다        조각이 튀고, 아이템이 떨어지고, 소리가 난다
방이 인식된다        방 경계가 한 번 빛나고, 이름이 뜬다        ★ 가장 중요
방 인식이 풀린다      경고음과 함께 이름이 사라진다
주민이 방을 쓴다      감사 포인트가 머리 위에 뜬다
종을 친다            소리, 빛, 카메라 연출, 새 주민 도착
밤이 온다            집에 불이 켜지고, 하늘색이 바뀐다
몬스터가 벽을 친다     블록에 금이 가고 흔들린다
목수가 수리한다       비계가 서고 망치 소리가 난다
```

"방이 인식되는 순간" 의 연출에 가장 많은 공을 들인다.
이 게임에서 플레이어가 가장 많이 기다리는 순간이다.

# 14. 그래픽 방향

사실적 표현이 목표가 아니다. **생활감과 변화가 잘 보이는 그래픽** 이 목표다.

```text
각진 복셀 블록. 부드러운 지형을 쓰지 않는다
텍스처 아틀라스 1 장. 저해상도 픽셀 텍스처
정점 AO 로 입체감을 만든다

```

플레이스홀더 단계에서도 다음은 시각적으로 구분되어야 한다.

```text
블록 파괴 / 설치
방 인식 성공 / 실패
주민의 이동 / 작업 / 식사 / 취침
몬스터의 이동 / 파괴 행동
```

# 15. 개발 우선순위

이 순서는 **의존성 순서** 다. 뒤 단계는 앞 단계 없이 동작을 확인할 수 없다.

```text
 A  복셀 기반       청크 / 메싱 / 렌더 / 블록 데이터
 B  플레이어        이동 / 복셀 충돌 / 카메라 / 블록 파괴와 설치
 C  채집과 인벤토리   블록 드롭 / 핫바 / 제작
 D  방 인식 ★       flood fill / 방 레시피 / 진단 UI
 E  시간과 주민      GameClock / 통행 그래프 / A* / NPC Action / 스케줄
 F  주민 생활 ★     농사 / 요리 / 식사 / 취침 — 방을 실제로 쓴다
 G  성장            감사 포인트 / 종 / 마을 레벨 / 해금
 H  진행            WorldState / Dialogue / Objective / 진행 이벤트
 I  방어            몬스터 / 블록 파괴 / 목수 수리 / 플레이어 전투
 J  마무리          오디오 / 저장 / 밸런스
```

## 15.1 D 와 F 가 두 개의 검증 지점이다

**D 단계 검증**

```text
벽을 쌓는다 → 문을 단다 → 침대를 놓는다 → "침실" 이 뜬다
```

아직 주민도 시간도 없다. 방 판정만 있다.

이 단계에서 확인할 것은 **판정이 플레이어의 직관과 일치하는가** 다.

```text
방이 될 거라고 생각했는데 안 되는 경우가 잦은가
왜 안 되는지 진단 UI 만으로 알 수 있는가
```

여기서 좌절이 발생하면 이후 단계를 진행하지 않는다.
방 레시피 조건을 먼저 완화한다.

**F 단계 검증**

```text
침실을 만든다 → 밤이 온다 → 주민이 걸어 들어간다 → 침대에 눕는다
```

Version 0.2 의 "밭과 농부" 검증 지점이 여기로 이동했다.

이 장면이 만족스럽지 않으면 이후 단계를 진행하지 않는다.
**감사 포인트와 마을 레벨은 이 재미를 포장하는 것이지, 만들어내는 것이 아니다.**

## 15.2 저장을 마지막에 두는 이유

저장은 다른 모든 시스템의 상태 구조가 확정된 뒤에 만든다.

다만 Version 0.2 와 달리 이번에는 **저장이 필수** 다.
90~120 분 분량은 한 번에 플레이하기 어렵다.

J 단계에 두되 빼지 않는다.

# 18. 개발 의사결정 원칙

새로운 기능을 추가하려 할 때 항상 다음을 묻는다.

> 이 기능이 세 루프 중 어느 것을 강화하는가?

```text
요청 루프    무엇을 만들지 알려주는가
인식 루프    만든 것에 의미를 부여하는가
성장 루프    계속할 이유를 만드는가
```

어느 것도 아니면 우선순위를 낮춘다.

규모를 키우는 것보다

**플레이어의 건축 → 게임의 인식 → 주민의 사용 → 플레이어의 관찰**

이 연결을 만드는 것을 최우선으로 한다.

# 19. 장기 확장 방향

수직 슬라이스의 재미가 확인된 이후 아래 순서로 확장한다.

```text
1 단계   방 레시피 확장 (여관 / 대장간 / 목욕탕 / 정원)
         가구 확장. 새 방 = 새 주민 행동
2 단계   주민 직업 확장 (광부 / 상인 / 병사)
         주민 10 명 규모
3 단계   주민 자동 건설 (청사진)
4 단계   지역 확장 → 두 번째 섬 → 챕터 구조
5 단계   전투 심화 (보스 습격 / 장비)
6 단계   주민 Personality / Relationship / Memory
```

이 모든 확장 역시 하나의 목표를 가진다.

> **플레이어가 만든 마을에서 사람들이 실제로 살아가고 있다는 느낌을 만든다.**

# 20. 프로젝트의 최우선 목표

이 프로젝트의 성공 기준은 기능의 개수가 아니다.

플레이어가 직접 쌓은 벽 안에서, 플레이어가 직접 놓은 침대에,

밤이 되자 주민이 걸어 들어와 눕는 모습을 보면서

플레이어가 자연스럽게

> **"이 마을을 조금 더 키워보고 싶다."**

라고 생각하게 만드는 것이다.

그 감정이 만들어지기 전까지 게임의 규모를 확대하지 않는다.

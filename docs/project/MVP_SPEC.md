# 2. 수직 슬라이스의 최종 목표

최우선 목표는 **아름답게 만든 공간에서 정감 있는 주민이 실제로 살아가는 순간** 이다.
기존 블록·가구·조명으로 공간을 가꾸고, 기존 주민의 외형·대사·생활 동작으로 정감을
표현한다. 아름다움을 점수나 방 인식 조건으로 만들지 않는다.
주민 관계·호감도 시스템이나 새 콘텐츠를 추가하지 않고 현재 범위에서 검증한다.

플레이어가 약 90~120 분 플레이한 뒤 다음을 느끼는 것을 목표로 한다.

> 내가 아름답게 가꾼 공간에서, 정이 든 주민들이 편안하게 살아간다.

그리고 이어서

> 이 마을을 조금 더 키워보고 싶다.

## 2.1 검증 대상

세 개의 루프가 전부 돌아가는지 검증한다.

GAME_DESIGN의 시스템 축(건축·인식·사용·관찰)과 감성 축(공간·주민·생활·애착)을
동등한 성공 조건으로 본다. 아래는 시스템 루프이며 그래픽·감성 검증을 대체하지 않는다.

# 3. 가장 중요한 개발 원칙

## 3.0 MVP 규모와 확장 목표를 구분한다

MVP는 **주민 3명 시작 → 최대 5명**, **128 × 64 × 128 섬 1개**를 구현한다.
아키텍처는 **주민 100명과 대형 월드로 확장 가능해야 한다.**
주민 수와 섬 크기는 데이터 설정이며 엔티티·좌표·저장 구조의 고정 상한이 아니다.
ARCHITECTURE 2.3과 ADR 017의 경계를 MVP 구현부터 지킨다.

대형 월드의 구체 크기, 활성 청크 수, 동시 상세 시뮬레이션 범위와 성능 기준은
확장 구현 전에 정의하고 측정한다. 36장의 성능 목표는 현재 MVP 시험 장면에 적용한다.
100명 콘텐츠나 월드 스트리밍의 완성은 MVP 완료 조건에 추가하지 않는다.


## 3.1 기능보다 반응을 먼저 만든다

```text
잘못된 우선순위            올바른 우선순위

블록 100 종               침대 1 개
가구 50 종                    ↓
방 레시피 20 종            방이 인식된다
주민 30 명                     ↓
                          주민이 밤에 들어간다
                              ↓
                          침대에 눕는다
                              ↓
                          감사 포인트가 뜬다
```

콘텐츠 개수보다 연결성이 중요하다.

## 3.2 판정 실패는 반드시 설명한다

방이 인식되지 않았을 때 플레이어가 이유를 알 수 없으면 게임이 그 자리에서 끝난다.

**방 진단 UI 는 선택 기능이 아니다.** 방 인식과 같은 Phase에서 구현하며 TASK-022를 통과해야 한다.

# 7. 월드

## 7.1 크기

```text
x   128
y    64
z   128
```

```text
y = 0        bedrock. 파괴 불가
y = 1 ~ 23   돌
y = 24       해수면
y = 25 ~ 34  지표면 (섬의 기복)
y = 35 ~ 63  하늘
```

사방이 바다다. 절차적 생성을 쓰지 않는다.
섬 지형은 고정 데이터로 생성한다.

## 7.2 청크

```text
청크 크기     16 × 16 × 16
청크 개수     8 × 4 × 8 = 256
인덱스        index = x + z * 16 + y * 256
저장          Uint16Array(4096)
```

## 7.3 좌표계

```text
BlockPos       정수 복셀 좌표 { x, y, z }
Vec3           실수 월드 좌표 { x, y, z }
```

블록 한 변의 길이는 월드 좌표 1.0 이다.

```text
blockToWorldMin(p)     = { x: p.x,       y: p.y,       z: p.z       }
blockToWorldCenter(p)  = { x: p.x + 0.5, y: p.y + 0.5, z: p.z + 0.5 }
standCellToWorldFeet(p)= { x: p.x + 0.5, y: p.y,       z: p.z + 0.5 }
worldToBlock(v)        = { x: floor(v.x), y: floor(v.y), z: floor(v.z) }
```

**변환 함수 이름에 기준점을 명시한다.** `blockToWorld` 라는 이름을 쓰지 않는다.
어느 지점인지 모르면 캐릭터가 블록 모서리에 서는 버그가 반복된다.

## 7.4 섬 구성

```text
영역          중심 좌표 (x, z)    내용
마을 터        (64, 64)           폐허. 부서진 판자벽과 기초. 마을의 종 1 개
숲            (40, 48)           나무 24 그루 (그루당 log 4 + leaves 20)
채석장         (88, 52)           노출된 돌 지대
물가           (64, 96)           담수와 모래
어두운 외곽     (64, 24) / (24,64) 몬스터 스폰 지점 2 곳
바다           섬 바깥             y=24 까지 물
```

마을의 종은 `(64, 지표면, 64)` 에 고정 배치된다. 플레이어가 부술 수 없다.
여기서 지표면은 7.5와 같은 기준이다. 열의 최상단 지형 블록 y를 `surfaceY`라 할 때
종 블록은 광장 지면 위 `(64, surfaceY + 1, 64)` 칸에 선다. 시작 위치의 `지표면+1`도
같은 `surfaceY + 1`, 즉 발이 놓이는 칸이다 (TASK-008에서 해석을 확정했다).

나무 한 그루는 `log` 4 개와 `leaves` 20 개로 구성한다.
섬 전체의 초기 공급은 `log` 96, `leaves` 480 이며 35.2 / 35.5 의 검산이 이 값을 쓴다.
정확한 나무 형상은 `island.ts` 가 소유하고 TASK-008 에서 실제 개수를 기록한다.

## 7.5 스폰

```text
플레이어 시작   (64, 지표면+1, 70)
농부           (62, 지표면+1, 62)
요리사          (66, 지표면+1, 62)
목수           (64, 지표면+1, 60)
```

## 8.2 terrain 플래그의 의미

```text
terrain = true    몬스터가 파괴하지 않는다. 우회한다
terrain = false   몬스터가 파괴한다
```

플레이어가 `dirt` 를 캐서 다시 놓아도 `terrain` 이다.
"누가 놓았는가" 를 추적하지 않는다. 블록 종류만 본다.

이 규칙에서는 다시 놓은 흙벽도 파괴되지 않는다. 39 Test 8의 의도된 제한이다.
방으로 인정되는 벽은 8.4의 건축 블록뿐이지만 방어 장애물은 지형도 포함한다.
흙벽이 최적 방어가 될 위험은 TASK-045 / 053에서 검증한다.
노동량·미관만으로 균형이 맞는다고 가정하지 않는다.
`terrain=false`라도 `breakSeconds=null`인 종은 파괴 후보에서 제외한다.

## 8.3 door 는 통행에서만 비고체다

```text
Player / NPC    통과할 수 있다  (통행 판정에서 비고체)
Monster         통과할 수 없다  (통행 판정에서 고체, 파괴 대상)
방 인식          벽으로 인정된다
충돌             플레이어는 통과한다
```

문의 열림 / 닫힘 상태를 두지 않는다. 항상 이 규칙으로 동작한다.

## 8.4 벽으로 인정되는 블록

방 인식에서 경계로 인정되는 블록은 다음뿐이다.

```text
plank / stone_brick / window / door
```

`dirt`, `stone`, `log` 같은 지형 블록은 **벽으로 인정되지 않는다.**

이유는 산비탈을 파고 들어가 "동굴이 방이다" 라고 주장하는 것을 막기 위해서다.
방은 플레이어가 지은 것이어야 한다.

## 8.5 제작

제작대를 두지 않는다. 인벤토리에서 바로 제작한다.

```text
plank         × 4   ←  log × 1
stone_brick   × 4   ←  stone × 2
door          × 1   ←  plank × 4
window        × 2   ←  plank × 2 + sand × 1
torch         × 4   ←  log × 1
bed           × 1   ←  plank × 4 + leaves × 4
cooking_stove × 1   ←  stone × 6
water_pot     × 1   ←  stone × 3
table         × 1   ←  plank × 4
chair         × 1   ←  plank × 2
chest         × 1   ←  plank × 6
farmland      × 1   ←  dirt × 1
```

점토(clay)를 도입하지 않는다. 제작 재료는 8.1 표에 있는 블록으로만 구성한다.
재료 종류를 늘리는 것은 38 장의 금지 사항이다.

```text
충돌        카메라가 블록을 관통하면 거리를 줄인다
```

시선 원점은 발밑 중심 + 1.6(머리 칸 안), 여기서 카메라 기준 오른쪽으로 0.6 옮긴 어깨점이다.
어깨점이 고체 칸 안이면 시선 원점을 그대로 쓴다. 카메라는 어깨점에서 시선 반대 방향으로
거리만큼 뒤에 있고 시선 방향을 본다. 그래서 화면 중앙의 조준점과 10.1의 레이캐스트
(어깨점에서 시선 방향)가 같은 직선이며, 캐릭터가 조준점을 가리지 않는다.
카메라 충돌에서는 고체 블록과 door 가 카메라를 막는다(window 포함). 마우스 감도는
픽셀당 0.0025 라디안이다. 이 값들은 조작감 조정 대상이며 34장에 둔다.

천장 걷어 내기(TASK-033 G2 개선, ADR 026): 플레이어 머리 위 6 칸 안(발 칸 +2 ~ +7)에 카메라를 막는 블록이
있으면, 그중 가장 낮은 블록의 y 이상이고 플레이어에서 수평 7 칸 안인 블록을 그리지 않으며 카메라 충돌에서도 뺀다.
집 안에서 지붕이 시야와 카메라를 막지 않게 하기 위해서다. 블록 자체·충돌·방 판정은 바뀌지 않는다(보이지만 않는다).
잎(leaves)은 천장으로 치지 않는다. 나무 밑에 들어가면 주변 숲의 잎이 모두 걷혀 나무 밑인지 알 수 없었다(2026-09-25 오너 확인 HR-011).

1 인칭을 구현하지 않는다. 자기가 만든 마을을 보는 게임이다.

## 9.4 충돌

물리 엔진을 쓰지 않는다. 축 분리 AABB 스윕으로 직접 계산한다.

```text
1. x 축으로 이동시키고 겹치는 고체 블록을 찾아 밀어낸다
2. z 축으로 같은 과정
3. y 축으로 같은 과정. 지면에 닿으면 onGround = true
```

한 칸 자동 오르기(step-up)를 구현한다. 높이 1.0 이하의 턱은 자동으로 오른다.
자동 오르기는 지면에 서 있을 때만 하고, 올라선 자리에 머리 공간(높이 1.8)이 있어야 한다.

## 9.5 물·월드 경계·발판 상실 (READY-06)

수영·익사·낙하 피해를 추가하지 않는다. 물은 섬의 경계이며 캐릭터가 머무는 공간이 아니다.

```text
물 가장자리   지면에 서서 걸을 때, 이동한 뒤 몸 가운데 아래(4 칸 안)의 첫 블록이 water 면 그 이동을 막는다.
             x·z 한 축씩 다시 시도해 물가를 따라 미끄러지듯 걷는다 (HR-006, ADR 027)
물           충돌에서 비고체(8.1)지만 플레이어의 발 칸 또는 머리 칸이 water 가 되면
             즉시 마지막 안전 지면으로 복귀한다. 속도는 0 이 된다. 체력은 줄지 않는다
             (점프·추락·발밑 제거처럼 가장자리 멈춤을 넘어 들어간 경우에만 일어난다)
월드 경계     수평(x, z) 범위 밖은 플레이어 충돌에서 고체다. 보이지 않는 벽처럼 멈춘다
             y < 0 도 고체다. y ≥ 월드 높이는 air 다 (점프로 닿을 수 없다)
높은 곳 추락   중력과 최대 낙하 속도(9.1)대로 떨어진다. 낙하 피해가 없다
발밑 제거      발밑 블록이 사라지면(플레이어·몬스터·채석장 복구와 무관하게) 그대로 떨어진다
블록에 낀 경우  이동 시작 시 AABB 가 고체와 겹치면 같은 (x, z) 에서 위로 가장 가까운
             빈 자리(발 칸·머리 칸 비고체, 물 아님)로 올린다. 없으면 복귀한다
```

**안전 지면**은 플레이어가 지면에 서 있고, 발 아래 칸이 고체이며 물이 아니고, 발 칸과
머리 칸이 물이 아닌 마지막 위치의 칸이다. 시작 위치(7.5)가 첫 안전 지면이다.
복귀할 때 그 칸이 더 이상 안전 지면 조건을 만족하지 않으면(발밑이 부서졌거나 막혔으면)
시작 위치 칸에서 위로 가장 가까운 안전 지면을 쓴다.

해안 가까운 바다는 수심 1 칸이고 해변보다 2 칸 낮다. 물을 통과할 수 있게 두면 올라올 수
없는 곳에 갇히므로 물 진입을 복귀로 처리한다. 연못도 같은 규칙이다. 물 위에 블록을 놓아
다리를 만들 수 있다 (물 칸 자체에는 설치할 수 없다, 10.3). 이 절의 복귀는 플레이어 이동에만 적용한다.

NPC·몬스터(TASK-024): 통행 그래프는 발 칸 또는 머리 칸이 water 인 칸을 서 있을 수 있는 칸으로
보지 않는다. 경로가 물을 지나지 않으므로 복귀 규칙이 필요 없다. 방 판정의 가구 접근성(12.2)은
이 조건을 더하지 않는다. 물에 잠긴 접근 셀은 실제 경로 실패로 처리된다(12.2 의 마지막 문단).

# 10. 블록 파괴와 설치

## 10.1 대상 선택

9.3의 어깨점에서 시선 방향으로 레이캐스트한다.

```text
최대 거리        8.0   (2026-09-25 오너 확인: 5.0 은 3 인칭 카메라 거리 5 에서 가리킬 수 있는 곳이 너무 가까워 답답하다)
알고리즘         복셀 DDA (Amanatides & Woo)
결과            { blockPos, faceNormal } 또는 null
```

## 10.2 파괴

```text
좌클릭을 누르고 있는다
    ↓
진행도 += dt / blockDefinition.breakSeconds
    ↓
진행도 >= 1 이면 블록이 air 가 되고 drops 가 인벤토리에 들어간다
```

대상이 바뀌면 진행도는 0 으로 초기화된다.

`breakSeconds` 가 `-` 인 블록(bedrock / water / bell)은 파괴되지 않는다.

## 10.3 설치

```text
우클릭
    ↓
targetBlockPos + faceNormal 위치가 air 인가
    ↓
전체 점유 칸이 플레이어와 NPC AABB에 겹치지 않는가
    ↓
핫바의 현재 아이템이 1 개 이상인가
    ↓
설치 규칙(10.4)을 만족하는가
    ↓
설치와 아이템 1 소모를 함께 확정한다. 실패하면 둘 다 바뀌지 않는다
```

## 10.4 블록별 설치 규칙

```text
crop          아래가 farmland. 농부만 설치
farmland      아래가 고체
bed           수평 2칸. 두 칸 모두 air이고 아래가 고체
door          수직 2칸. 두 칸 모두 air이고 아래가 고체
나머지 가구     아래가 고체
torch         아래 또는 옆면이 고체
bell          플레이어 설치 불가
```

침대·문은 아이템 한 개를 소비하는 다중 칸 객체다. 카메라의 수평 방향을
가장 가까운 동서남북으로 양자화해 설치 방향을 정한다.
침대의 anchor와 방향으로 나머지 칸을, 문의 아래 anchor로 위 칸을 결정한다.
단일 칸 블록을 포함한 모든 설치에서 월드 범위·기존 객체·플레이어와 NPC AABB 충돌을 검사한다.
인벤토리 소비/드롭과 월드 편집은 함께 성공하거나 함께 실패한다.
알림 구독자가 블록만 바뀌고 아이템은 아직 바뀌지 않은 중간 상태를 읽게 하지 않는다.

VoxelWorld의 PlacementIndex가 객체 id / blockId / anchor / facing을 소유한다.
점유 칸에는 같은 blockId를 기록하고 각 칸에서 대표 객체를 조회할 수 있어야 한다.
설치·파괴·수리는 모든 점유 칸과 메타데이터를 원자적으로 변경한다.
어느 칸을 부숴도 객체 전체가 제거되고 플레이어에게 아이템은 한 개만 돌아온다.
몬스터 파괴는 드롭 없이 전체 원본 배치를 DamageLog에 한 건으로 기록한다.
수리·습격 피해 예산은 점유 복셀 수로 센다. 남은 예산보다 큰 객체는 부분 파괴·수리하지 않는다.
같은 blockId인 인접 객체도 서로 다른 id로 구별하며 저장·로드 후 유지한다.

## 10.4.1 지지면이 사라진 뒤 (READY-02)

10.4의 "아래가 고체"·"아래 또는 옆면이 고체"는 **설치할 때만** 검사한다.
설치 뒤 지지면이 부서져도(플레이어·몬스터·그 밖의 편집 모두) 위의 가구·침대·문·횃불·farmland 는
그 자리에 그대로 남는다. 떨어지거나 연쇄로 부서지지 않고 드롭도 생기지 않는다.
물리 엔진·복셀 중력을 도입하지 않는다.

```text
한 번의 파괴가 바꾸는 것   대상 블록 하나, 또는 대상이 속한 다중 칸 객체 전체 (10.4)
드롭                    그 대상의 drops 만. 지지하던 이웃은 바뀌지 않으므로 중복·유실이 없다
DamageLog              몬스터가 부순 그 대상의 원본 배치만 기록한다. 이웃은 기록하지 않는다
유일한 예외              farmland 가 사라지면 위의 crop 을 제거한다 (15.2, FarmSystem 이 TASK-030 에서 처리)
```

떠 있는 가구가 방 판정·통행에서 어떻게 보이는지는 11 / 12장의 기존 조건을 그대로 따른다
(예: 바닥 구멍은 방 실패 사유다). 판정 조건을 이 절에서 바꾸지 않는다.

## 10.5 변경 이후의 처리

블록이 바뀌면 다음이 순서대로 발생한다.

```text
1. VoxelWorld 가 블록을 쓴다
2. 해당 청크와 padded 뷰에 변경점이 포함된 인접 청크를 메싱 큐에 넣는다 (AO 포함)
3. 통행 판정이 읽은 좌표의 역참조로 캐시와 진행 중 경로를 즉시 무효화한다
4. 방 재판정 큐에 해당 좌표를 넣는다
5. 전체 변경이 커밋된 뒤 점유 칸별 BLOCK_CHANGED를 발행한다 (동일 batchId)
```

# 11. 방 인식

**이 장이 이 프로젝트의 핵심이다.**

## 11.1 파라미터

```text
roomMinFloorArea      4       2 × 2 미만은 방이 아니다
roomMaxFloorArea      100
roomMinWallHeight     2
roomDetectBudgetMs    3       프레임당 방 재판정 예산
```

## 11.2 빈 방 조건

다음을 모두 만족하면 방의 형태가 성립한다. 가구가 없으면 EmptyRoom이다.

1. 하나의 y 평면에서 연결된 내부 바닥 영역이 있다. 공기·비고체 장식·가구 점유 칸을 포함한다.
2. 내부 영역 바로 아래(y-1)가 전부 고체다.
3. 내부 영역의 수평 경계는 8.4의 벽 블록이다. 가구는 경계가 아니다.
4. 각 경계는 y와 y+1 모두 벽 블록이며, 문은 두 칸 객체여야 한다.
5. 경계에 문 객체가 하나 이상 있다.
6. 가구가 차지한 칸을 포함한 내부 바닥 면적은 4~100칸이다.

천장은 요구하지 않는다. 내부 영역과 보행 가능한 셀은 다르다.
가구 위·아래를 같은 방의 별도 면적으로 중복 계산하지 않는다.
지형 고체를 내부 장식이나 경계로 인정하지 않는 제한은 유지한다.

## 11.3 알고리즘

```text
입력: 읽기 전용 블록·배치 정보, 시작점, 방 제한값
1. 시작점의 y를 고정한다. 문에서는 아래 anchor의 수평 인접 셀을 시작점으로 쓴다
2. 4방향 flood fill. 분기 우선순위는 다음과 같다
   a. 벽 / 문 → 경계에 기록하고 멈춘다 (통행상 비고체인 문보다 이 검사가 우선)
   b. 월드 밖 → NOT_ENCLOSED
   c. 아래가 고체가 아님 → NO_FLOOR
   d. 공기 / 비고체 / 유효한 가구 점유 칸 → 내부 영역에 넣고 확장
   e. 그 외 고체 / 지형 → NOT_ENCLOSED
3. 내부 방문 수가 100을 넘으면 TOO_LARGE, 종료 후 4 미만이면 TOO_SMALL
4. 경계의 둘째 층이 벽인지 검사 → WALL_TOO_LOW
5. 경계에 완전한 두 칸 문 객체가 없으면 NO_DOOR
6. 성공 시 interior / boundary / doors / floorY를 반환
7. 별도로 머리 공간까지 고려한 보행 영역과 가구 접근 지점을 계산한다 (12.2)
```

같은 셀은 한 번 방문한다. 문마다 성공한 동일 interior 집합은 하나의 방으로 합친다.
두 방을 잇는 문은 각 면의 서로 다른 interior 집합에 각각 속할 수 있다.
열린 평지에서는 틈을 지나 100칸을 넘을 수 있다. TOO_LARGE를 곧바로
“벽 구멍 좌표를 찾았다”로 해석하지 않는다.

## 11.4 실패 사유와 확인 가능한 좌표

```ts
type RoomFailure =
  | { reason: 'NOT_ENCLOSED'; at: BlockPos }
  | { reason: 'NO_FLOOR';     at: BlockPos }
  | { reason: 'NO_DOOR' }
  | { reason: 'WALL_TOO_LOW'; at: BlockPos }
  | { reason: 'TOO_LARGE' }
  | { reason: 'TOO_SMALL' };
```

`at` 이 있는 실패는 진단 모드에서 그 좌표를 빨갛게 표시한다.
NO_FLOOR 의 `at` 은 비어 있는 바닥 칸(내부 칸의 y-1)이다. WALL_TOO_LOW 의 `at` 은 벽 블록이 아닌
둘째 층 칸이다. NOT_ENCLOSED 의 `at` 은 탐색이 닿은 월드 밖 칸 또는 벽이 아닌 블록이다.

## 11.5 진단 모드 (Tab)

인식된 방은 초록 경계와 이름을 표시한다.
실패한 공간은 플레이어 위치에서 문 없이도 같은 탐색을 실행한다.
NO_FLOOR / WALL_TOO_LOW / 지형 고체 경계는 확인한 원인 좌표를 표시한다.
NO_DOOR / TOO_SMALL은 문구와 조사 영역을 표시한다.
TOO_LARGE / 월드 밖 도달은 **“공간이 열려 있거나 너무 큽니다”**와
탐색한 영역·외부로 이어진 탐색 경로를 표시한다. 추측한 구멍을 정답처럼 표시하지 않는다.
지형으로 막힌 경우는 “이 블록은 방의 벽으로 인정되지 않습니다”로 구별한다.

방 형태는 맞지만 가구가 부족하거나 막혔으면 미충족 레시피와 가구 접근 실패 이유를 표시한다.
진단은 자동 재판정 대기열에 들어가지 않는다. 즉시 시작하고 같은 프레임 예산을 공유하며,
예산 소진 시 다음 프레임에 이어서 결과를 표시한다.
TASK-022에서 플레이어가 이 표시만으로 빠진 벽을 찾아 고칠 수 있는지 검증한다.

## 11.6 재판정 범위

RoomRegistry는 문 anchor의 공간 인덱스를 가진다. 블록 변경마다 다음을 큐에 넣는다.

1. 변경 좌표가 내부 바닥(y-1)·내부 두 층·경계 두 층에 포함되는 기존 방.
2. 문 anchor의 y가 변경 y-1, y, y+1 중 하나이고,
   xz Manhattan 거리가 roomMaxFloorArea+1 이하인 모든 문.
3. 새 문은 인덱스 추가 후 검사한다. 삭제된 문은 삭제 전 소속 방을 무효화한다.

유효한 방의 연결된 내부 셀은 최대 100개이므로 이 거리 안에 영향을 받는 문이 있다.
실패한 방을 영구 등록할 필요 없이, 문에서 먼 마지막 벽을 막거나 방을 복구해도 발견한다.
월드 블록 전역 스캔은 하지 않는다. 문 후보가 많아지는 비용은 큐로 분산한다.
작업 키는 문 anchor와 시작 면이고, 판정 성공 후 동일 interior는 방 단위로 합친다.

시간 예산은 프레임당 3ms다. 탐색 단계 사이에 예산을 확인하고 이어서 실행한다.
작업 도중 읽은 블록이 바뀌면 그 결과는 버리고 최신 상태로 재시작한다.
dirty 방의 시설은 판정 완료까지 신규 예약에 사용하지 않는다.
사용 중인 가구·접근 셀의 파괴는 큐 처리 전에 해당 Action을 취소한다.

## 11.7 방이 해제될 때

인식되어 있던 방이 조건을 잃으면:

```text
ROOM_UNREGISTERED 이벤트 발행
그 방에 배정된 침대 사용자는 배정을 잃는다
그 방을 목적지로 이동 중이던 NPC 는 현재 Action 을 취소한다
자고 있던 NPC 는 깨어난다
경고음과 함께 방 이름이 사라진다
```

**감사 포인트는 회수하지 않는다.** ADR 013 의 비가역 원칙이다.

# 12. 방 레시피

## 12.1 목록

```text
priority  type         조건
   40     DiningRoom   table >= 1
                       그 table 에 수평 인접한 접근 가능한 chair >= 2
   30     Kitchen      cooking_stove >= 1 AND water_pot >= 1
                       cooking_stove 에 12.2의 접근 셀 >= 1
   20     Bedroom      접근 가능한 bed >= 1
   10     Storeroom    chest >= 1
                       chest 에 12.2의 접근 셀 >= 1
    0     EmptyRoom    조건 없음
```

`priority` 내림차순으로 검사하여 최초로 만족하는 타입을 부여한다.
한 방은 하나의 타입만 가진다. 최종 타입이 제공하는 시설만 활성화한다.
침실에 주방 가구를 추가해 Kitchen이 되면 침대 배정은 해제된다.
가구 제거·접근성 변경·타입 변경 시 이전 시설과 비교하여 사라진 예약을 취소한다.
이 제한의 직관성은 TASK-022 / 033에서 검증한다.

## 12.2 가구 접근성

공통 순수 함수 isStandableCell은 아래 고체 + 발 셀 비고체 + 머리 셀 비고체를 검사한다.
room과 nav 모두 이 함수를 사용하며 문은 NPC에게만 비고체다.
방 내부에서 문 아래 셀과 연결되는 보행 셀을 구한다. 경계 벽이나 가구를 관통하지 않는다.

접근 가능한 가구는 전체 점유 영역이 방 내부에 있고,
적어도 한 수평 인접 셀이 위 보행 연결 집합에 속해야 한다.
침대는 두 점유 칸 중 하나에서 접근 가능하면 된다. 침대 수는 객체 수다.
화덕·상자·의자에도 같은 접근 조건을 적용한다.
식탁 옆 의자는 접근 가능한 의자만 세며 식탁 하나에 최소 두 개가 붙어 있어야 한다.

가구 결과는 objectId / anchor / approachCells / usePosition을 갖는다.
NPC는 approachCells 중 실제 경로가 있는 곳까지 걸은 뒤 사용 자세로 전환한다.
고체 침대·의자 자체를 A* 목적지로 사용하지 않는다.
사용 자세의 usePosition은 렌더 표현용이다. NPC의 충돌·저장 위치는 유효한 접근 셀에
유지해 사용 종료·취소·로드 후 고체 가구 안에 끼지 않게 한다.
배치 변화로 사용할 수 없으면 다른 시설을 찾거나 12.5의 대체 행동으로 간다.

이 판정은 방 안에서 문까지의 국소 접근성이다. 외부에 길이 없거나 NPC가 고립된
상황까지 보장하지 않는다. 실제 NPC 경로 실패는 별도 진단에 표시한다.
housingLevel은 국소 접근 가능한 Bedroom 침대 수이며 실제 취침 인원과 구별한다.

## 12.3 식당에 음식을 요구하지 않는다

DQB2 는 식탁 위의 음식을 요구한다.

이 프로젝트는 요구하지 않는다.

```text
음식을 요구한다   →  식당이 있어야 요리사가 배식한다
                    요리사가 배식해야 식당이 인식된다
                    → 순환 조건. 게임이 시작되지 않는다
```

음식은 요리사가 식사 시간에 식탁 위에 올리는 **연출** 이다. 판정 조건이 아니다.

## 12.4 방 타입이 주민에게 주는 것

```text
Bedroom      접근 가능한 침대 객체 + 접근 셀 + 사용 위치
Kitchen      접근 가능한 화덕 객체 + 접근 셀 + 사용 위치
DiningRoom   식탁에 인접한 의자 객체 + 접근 셀 + 사용 위치
Storeroom    접근 가능한 상자 객체 + 접근 셀
EmptyRoom    없음
```

matchRecipe 결과는 위 시설을 포함한다. NPC가 가구를 다시 스캔하지 않는다.
`Storeroom` 의 상자는 이번 범위에서 **플레이어의 기부 지점** 이다. 상자를 쓰는 NPC Action 은 없다.
따라서 창고는 방 수·최초 인식 보너스·보관 연출에만 기여한다. 운반 Action 을 추가하지 않는다.
침대는 SleepSystem이 고정 배정한다. 의자·화덕은 사용 Action 동안 NPCSystem이
objectId별로 한 명만 예약한다. 완료·취소·시설 무효화 시 예약을 해제한다.
방은 있어도 사용 가능한 시설이나 실제 경로가 없으면 12.5의 대체 동작을 적용한다.

## 12.5 방이 없을 때의 대체 동작

```text
Bedroom 없음     광장(종 주변)에서 RestAction. 잠들지 않는다
Kitchen 없음     요리를 하지 않는다. crop 이 쌓인다
DiningRoom 없음  광장에서 식사한다. 감사 포인트가 발생하지 않는다
Storeroom 없음   종의 위치가 기본 저장소다
```

**대체 동작이 존재하는 것이 중요하다.**
아무 방도 없는 상태에서 게임이 멈추면 안 된다.
그리고 대체 동작은 항상 감사 포인트를 주지 않는다. 그것이 방을 지을 동기가 된다.

# 13. 자원과 저장소

## 13.1 플레이어 인벤토리

```text
핫바      9 칸
가방      27 칸
스택      64
```

블록과 아이템을 구분하지 않는다. 모든 것이 블록이거나 재료다.

## 13.2 마을 저장소 (VillageStorage)

```text
seed    밭에 심을 씨앗
crop    수확한 작물
food    조리된 음식
```

NPC 는 **플레이어 인벤토리를 읽거나 쓰지 않는다.**

플레이어 → 마을 저장소 이동 경로는 하나다.

```text
chest 에 F 로 상호작용하여 seed / crop / food 를 기부한다
```

상자가 없으면 종의 통합 패널에서 [저장소] 탭을 연다. 종에는 [성장] / [저장소] 두 탭이 있고 F는 항상 이 패널 하나만 연다.

## 13.2.1 상호작용 대상과 기부 자격 (READY-07, ADR 033)

```text
대상 선택     조준선 하나로 고른다. 블록 편집과 같은 광선·사거리(reachDistance 8)를 쓴다
가림         광선은 처음 만나는 고체 블록에서 멈춘다. 벽 너머의 종·상자·주민은 고를 수 없다
주민         광선 위에서 블록보다 가까운 주민이 있으면 주민이 대상이다(대화, TASK-040)
우선순위      광선 위에서 가장 가까운 것 하나. 종·상자·주민이 가까이 모여 있어도 패널은 하나만 열린다
종           [성장] / [저장소] 두 탭을 가진 패널을 연다(성장 탭이 먼저)
상자          [저장소] 탭만 있는 같은 패널을 연다. 인식된 Storeroom 안이 아니어도 어느 상자나 기부 지점이다
그 밖         조준한 블록이 종·상자가 아니고 주민도 없으면 F 는 아무것도 하지 않는다
프롬프트      대상이 있으면 화면 중앙 하단에 "[F] 종" / "[F] 저장소" / "[F] 대화하기" 를 보인다
기부          seed / crop / food 를 종류별로 한 개 또는 전부 플레이어 인벤토리에서 마을 저장소로 옮긴다. 되돌리기는 없다
```

## 13.3 초기값

```text
VillageStorage.seed   3
VillageStorage.crop   0
VillageStorage.food   0
플레이어 인벤토리        비어 있다
```

# 14. 채집

```text
블록            drops              respawn
log             log × 1            나무는 재생하지 않는다 (24 그루 고정)
leaves          leaves × 1 + seed × 1 (25% 추가)  -
stone           stone × 1          채석장 노출면은 게임일마다 8 블록 복구
dirt / grass    dirt × 1           -
sand            sand × 1           -
```

`leaves` 에서 `seed` 가 25% 확률로 나오는 것이 씨앗의 유일한 신규 공급원이다.

나무 24그루 × 잎 약 20개 = 약 480회 파괴 → 최초 채집의 기대 seed 약 120개.
난수이므로 특정 나무 한 그루의 공급을 보장하지 않는다.
회수한 leaves를 다시 놓아 부숴도 동일 드롭 규칙이다. 씨앗 총량을 유한 자원으로 제한하지 않는다.
새 provenance 추적이나 자원을 추가하지 않는다.

표에 없는 제작 블록은 같은 아이템 한 개를 회수한다.
bed / door는 객체 한 개당 한 개이며 crop을 플레이어가 부수면 드롭 없이 제거한다.
플레이어 파괴는 인벤토리에 모든 드롭을 넣을 공간을 확보한 뒤 확정한다.
몬스터 파괴와 목수 수리는 아이템 드롭을 만들지 않는다.

## 14.1 결정적이지 않은 유일한 값

`leaves` 의 25% 만 난수를 쓴다.

다른 모든 판정은 결정적이다. 테스트 가능성을 위해서다.

## 14.2 채석장 재생 후보와 점유 보호 (READY-01)

`island.ts`가 생성 시 채석장 노출 돌 지대(중심 (88, 52), 반지름 10)에서 평지보다 높은
언덕 몸체의 원래 `stone` 칸을 후보 목록으로 만든다. 목록은 y → z → x 오름차순으로 고정된다.

```text
하루의 복구    후보 목록 앞에서부터 조건을 만족하는 칸을 최대 stoneRespawnPerDay(8) 개
조건          현재 air
              플레이어·NPC·몬스터 AABB와 겹치지 않는다
              면으로 맞닿은 칸에 terrain이 아닌 블록(건축·가구·문·횃불·작물·종)이 없다
부족할 때      조건을 만족하는 칸만 복구한다. 부족분을 다음 날로 넘기지 않는다
```

원래 돌이 아니던 칸, 플레이어가 놓은 블록·객체가 있는 칸은 복구하지 않는다.
채석장 안에 지은 구조물의 내부와 바로 옆도 메우지 않는다. 같은 월드 상태에서는 항상
같은 칸을 고른다. 선택은 순수 함수 `selectQuarryRespawnCells`가 담당한다.

## 14.3 채석장 재생 시각과 당일 처리 키 (READY-04)

```text
재생 시각      매 게임일 05:00 (dawn 시작). 직전 프레임 < 05:00 ≤ 현재를 넘었을 때 한 번
첫 재생        Day 2 05:00. 시작 시각 Day 1 07:00 은 이미 그날의 05:00 뒤다
소유           QuarryRespawnSystem. update 4 번(blockEdit) 슬롯의 BlockEditSystem 뒤
처리 키        respawnedThroughDay = 마지막으로 처리한 05:00 경계의 day
               현재 시각의 가장 최근 05:00 경계 day 가 이 값보다 클 때만 처리하고 그 값으로 바꾼다
               시작 값은 시작 시각의 최근 경계 day(= 1)다
여러 경계      한 프레임에 경계를 둘 이상 넘어도(디버그 시각 강제 설정) 한 번만 처리한다
               지나간 날의 몫을 보충하지 않는다 (14.2 의 이월 없음과 같다)
배속           배속은 gameMinutes 증가량만 바꾼다. 경계 검사가 같으므로 중복 처리가 없다
점유           그 순간 캐릭터 AABB 와 겹치는 후보는 건너뛰고 뒤의 후보로 채운다
               건너뛴 칸을 그날 나중에 다시 시도하지 않는다
BLOCK_CHANGED  by = 'world'. 드롭·DamageLog·수리 대상이 아니다. 방·통행은 다른 변경과 같이 무효화한다
저장           respawnedThroughDay 를 저장한다. 로드 중에는 처리하지 않는다
               로드 뒤 첫 update 에서 남은 경계가 있으면 그때 한 번 처리한다
```

05:00을 쓰는 이유: 밤 동안 바뀐 채석장을 아침에 발견하게 하고, 매일 07:00 자동 저장(32.5)
전에 그날의 복구를 끝내 저장에 포함한다. 주민 기상과 같은 시각이지만 서로 의존하지 않는다.
구현·검증은 TASK-023이다. 실제 저장 왕복은 TASK-051에서 확인한다.

# 15. 농사

## 15.1 밭

```text
farmland 블록 위에 crop 블록이 있으면 재배 중이다
```

플레이어는 `farmland` 를 깐다. `crop` 은 농부가 심는다.

## 15.2 성장

```text
경과 시간    [0,4)시간    [4,8)시간    [8,12)시간    12시간 이상
표시 단계       0            1            2              2
수확 가능       F            F            F              T
```

세 단계 각각 4시간을 유지한다. stage=2 자체가 성숙을 뜻하지 않는다.
성숙은 gameMinutes - plantedAtGameMinutes >= 720으로 계산한다.
성장은 농부와 무관하다. farmland 파괴 시 위 crop을 제거한다.
이 시간은 balance.farm.growthStages × hoursPerStage에서 계산한다.

## 15.3 농부의 반복 행동

```text
VillageStorage.seed >= 1 이고 빈 farmland 가 있다
    ↓  PlantAction
그 farmland 로 이동 → crop 을 심는다 → seed -1
    ↓
경과 12시간 이상인 crop 이 있다
    ↓  HarvestAction
그 위치로 이동 → 수확 → crop 블록 제거
    ↓
VillageStorage.crop +1, VillageStorage.seed +1
```

성숙 작물 수확을 빈 밭 파종보다 우선한다. 수확 뒤 같은 칸을 재파종한다.
각 작업은 접근 가능한 인접 셀에서 수행하며 심기·수확 자체는 도착 시 즉시 완료된다.
수확에서 seed가 한 개 돌아온다. 작물이 파괴되면 그 씨앗은 돌아오지 않으므로
추가 채집으로 보충한다. 안정된 밭의 씨앗만 순환한다고 설명한다.

## 15.4 구현 세부 (TASK-030, ADR 030)

```text
작업 칸        crop 칸(farmland 바로 위)의 수평 이웃 중 NPC 가 설 수 있는 칸. 다른 farmland 위가 아닌 칸을 우선한다
후보          FarmSystem 이 farmland 칸 목록을 블록 변경으로 유지한다. 농부에게 가까운 성숙 작물 → (seed ≥ 1 이면) 빈 밭 순
예약          한 칸은 한 농부만 잡는다. 완료·취소·실패 때 푼다
작업 자세      심기·수확의 효과는 도착 즉시 적용하고, 그 뒤 workPoseSeconds(0.8 실초) 동안 작업 자세를 보인다(렌더 표현)
작물 표시      crop 은 렌더 모형으로 그린다. 표시 단계 0 / 1 / 2 와 성숙(이삭)을 구별해 보인다
밭 정리        farmland 가 사라지면 위의 crop 을 제거한다. BLOCK_CHANGED by = 'world', 씨앗은 돌아오지 않는다
플레이어 파괴   crop 을 부수면 드롭 없이 사라지고 기록도 지운다(14 장)
```

# 16. 요리

```text
장소        Kitchen 의 cooking_stove 인접 셀
입력        VillageStorage.crop 2
출력        VillageStorage.food 3
소요        게임 시간 1 시간
조건        역할 작업 시간이고, 사용 가능한 Kitchen과 crop >= 2가 있다
```

**작물보다 음식이 많아지는 것** 이 주방을 짓는 이유다. DQB2 와 같은 구조다.

요리 완료 시 crop 2를 원자적으로 소비하고 food 3과 감사 포인트 +3을 준다.
시작 시 재료를 예약하되 소비하지 않으며 중단·로드 시 예약만 해제한다.
재료가 부족한 완료 요청은 실패한다. 식사를 못 했다고 다음 업무를 금지하지 않는다.

## 16.1 구현 세부 (TASK-031, ADR 031)

```text
작업 칸        cooking_stove 의 접근 셀(12.2). 요리사가 걸어가 그 칸에 선 뒤 조리한다
후보          CookingSystem 이 Kitchen 의 cookingSpots 를 방 이벤트로 유지한다. 요리사에게 가까운 빈 화덕 하나
재료 준비      다른 요리사의 예약을 뺀 crop >= 2. 음식 양·식사 여부는 보지 않는다
예약          화덕 하나는 요리사 한 명(가는 중부터). 재료는 조리 시작 때 예약하고 완료 때 소비한다
시간          조리 시작 뒤 게임 시간 1 시간(게임분 기준, 배속과 무관)이 지나면 완료한다
중단          역할 작업 시간이 끝나거나(12:00 / 18:00) 다른 행동으로 바뀌면 예약만 풀린다. 다음 역할 시간에 처음부터 다시 조리한다

재료 재검증    crop 이 예약 합계보다 적어지면 나중에 잡은 예약부터 푼다. crop 이 음수가 되지 않는다
조리 자세      화덕을 보고 서서 젓는 자세와 화덕 위의 김(렌더 표현). 밭일·걷기·대기와 구별된다
```

# 17. 식사

```text
식사 시각    12:00 ~ 13:00 (점심)
            18:00 ~ 19:00 (저녁)
1 회 소비    VillageStorage.food 1
```

허기 수치는 없다. mealId=(day, lunch|dinner)와 hasEatenThisMeal을 둔다.
각 구간 진입 시 새 mealId로 갱신하고 플래그를 초기화한다. 로드·같은 구간 재진입으로 초기화하지 않는다.
food가 0이면 그 끼니 시도를 끝내지만 다음 업무를 막지 않는다.

```text
DiningRoom 이 있다   chair 로 이동 → 앉는다 → 먹는다 → 감사 포인트 +2
DiningRoom 이 없다   광장으로 이동 → 먹는다 → 감사 포인트 없음
food 가 0 이다       먹지 않고 넘어간다. happinessLevel 이 내려간다
```

식사 시간에 요리사는 식탁 위에 `food` 오브젝트를 시각적으로 올린다.
블록을 설치하지 않는다. 연출 전용 오브젝트다.

## 17.1 구현 세부 (TASK-032, ADR 032)

```text
mealId        "day:lunch" / "day:dinner". 주민마다 저장한다. 구간 안에서 주민의 mealId 가 현재와 다르면 갱신하고 플래그를 초기화한다
식사 판단      식사 구간이고, 아직 먹지 않았고, food >= 1 일 때만 먹으러 간다. food 가 0 이면 그 끼니는 넘어간다
의자          MealSystem 이 DiningRoom 의 diningSeats(식탁에 맞닿은 의자)를 방 이벤트로 유지한다. 주민에게 가까운 빈 의자 하나
예약          의자 하나는 한 명(가는 중부터). NPCSystem 이 소유하고 Action 이 바뀔 때 푼다(경로 실패·취소·구간 종료 포함)
의자 부족      의자를 얻지 못한 주민은 광장 칸에서 먹는다(12.5 의 대체 동작, 감사 포인트 없음)
소비          의자 접근 셀(또는 광장 칸)에 도착해 앉을 때 food 1 을 소비하고 hasEatenThisMeal = true (한 트랜잭션)
먹는 시간      앉은 뒤 eatGameMinutes(20 게임분) 동안 먹는 모습을 보인다. 구간이 끝나거나 의자가 사라지면 일어선다
식탁 위 음식   먹는 주민 앞 식탁 윗면에 그릇과 음식을 렌더 모형으로 놓는다. 블록이 아니며 먹는 동안만 보인다
자세          의자 위에 앉아 식탁을 보고 숟가락질한다(렌더 표현). 광장에서는 바닥에 앉아 먹는다. 취침·대기와 구별된다
```

요리사가 식탁까지 걸어가 음식을 놓는 별도 동작은 두지 않는다. 음식은 주민이 앉을 때 그 앞에 나타난다(ADR 032).

# 19. NPC

## 19.1 역할

```text
Farmer      PlantAction / HarvestAction
Cook        CookAction (배식은 식사 시간 연출)
Carpenter   RepairAction (수리 대상이 없으면 IdleAction)
Villager    (레벨업으로 도착하는 주민) 역할 없음. 생활만 한다
```

## 19.2 공통 제원

```text
높이         1.8
폭           0.6 (플레이어와 같다. 1 칸 문을 지난다)
이동 속도     3.2 / 초
도피 속도     5.0 / 초
체력         10
```

NPC 는 죽지 않는다. 체력이 0 이 되면 기절 상태로 30 게임분 동안 행동하지 않는다.

## 19.3 상태는 현재 Action 이다

별도의 `state` 필드를 두지 않는다. ADR 008 을 그대로 유지한다.

```text
IdleAction / MoveAction / PlantAction / HarvestAction / CookAction
EatAction / SleepAction / RestAction / RepairAction
FleeAction / TalkAction
```

표시용 라벨은 Action 이 제공한다.

## 19.4 판단 우선순위

위에서 아래로 한 번만 평가한다.

```text
1  위협      반경 12 안에 몬스터가 있다        → FleeAction
2  대화      플레이어가 대화를 걸었다           → TalkAction
3  생리      식사 시간 / 취침 시간             → EatAction / SleepAction / RestAction
4  역할      역할별 작업 조건을 만족한다         → 역할 Action
5  기본      아무것도 아니면                   → IdleAction
```

## 19.4.1 도피 (TASK-047)

```text
위협         반경 12 안의 몬스터. 도피를 시작한 주민은 15 보다 멀어질 때까지 위협으로 본다(경계에서 흔들림 방지)
도피 칸       이미 방 안이면 제자리. 아니면 24 칸 안의 가장 가까운 인식된 방 안 칸(문을 지나 들어간다). 없으면 몬스터 반대쪽 10 칸 부근
속도         5.0. 도착하면 "숨는 중" 으로 서 있는다. 위협이 풀리면 이전 행동을 이어가지 않고 새로 판단한다
```

## 19.5 생활 시간표

```text
05:00 ~ 07:00   기상. 방에서 나온다
07:00 ~ 12:00   역할 작업
12:00 ~ 13:00   점심
13:00 ~ 18:00   역할 작업
18:00 ~ 19:00   저녁
19:00 ~ 20:00   자유 행동 (광장 / 모닥불 주변)
20:00 ~ 05:00   취침
```

역할이 없는 주민(Villager)은 역할 작업 시간에 광장 칸으로 가서 머문다(ADR 034). 식사·취침·기상은 다른 주민과 같다.

## 19.6 새 주민 도착 (TASK-038, ADR 034)

```text
예약         종을 쳐 레벨 L 이 되면 고유 키 L 로 도착 한 명을 예약한다. 시각은 종을 친 시각보다 엄격히 뒤인 다음 07:00
도착         그 시각을 넘긴 첫 프레임에 섬 가장자리의 도착 칸에 Villager 한 명을 세우고 예약을 완료한다(한 트랜잭션)
같은 날 두 레벨  예약마다 한 명씩 두 명이 같은 아침에 온다. 두 번째는 도착 칸 옆 칸에 선다
걸어 들어옴    07:00 은 역할 작업 시간이므로 새 주민은 도착 칸에서 광장으로 걸어 들어온다
침대          도착과 함께 침대 배정 대상이 된다. 실제 경로가 있는 빈 침대가 있으면 곧 배정된다(18.1)
연출          화면 상단에 "새 주민이 마을에 왔어요" 알림. NPC_ARRIVED 를 발행한다
```

## 19.7 주민의 한마디 (TASK-BARK-001, ADR 042)

주민이 지금 상황에 맞는 짧은 말을 머리 위 말풍선으로 한다. 2026-09-25 사용자 결정으로 추가했다.
**모달이 아니고 조작·시간을 멈추지 않는다.** 진행 대사(27.4)와 별개이며 해금·보상·목표·Action·판단을 바꾸지 않는다.
저장하지 않는다(32.2). 말하는 계기는 이미 있는 Action 전환·이벤트·플레이어의 거리뿐이다. 새 메커닉·자원·역할을 만들지 않는다.

```text
상황          계기                                                           상황별 간격(주민마다, 실초)
인사          플레이어가 반경 greetRadius(4) 안에 들어온다(greetCheckSeconds 0.5 마다 확인). 시간대별 문장   120
말 걸기        진행 대사가 없는 주민에게 F. 아래 우선순위로 문장을 고른다                           1   (공통 간격 무시)
기상          SleepAction 이 끝나고 05:00~09:00 에 다른 Action 으로 바뀐다                      —
기상(바닥)      RestAction(침대 없이 쉬기) 이 끝나고 같은 조건                                   —
취침          SleepAction 시작                                                             —
잘 곳 없음      RestAction 시작                                                              —
식사(식당)      식당 의자에서 EatAction 시작                                                   —
식사(광장)      의자 없이 EatAction 시작                                                       —
수확 / 심기     harvest / plant 시작                                                        90
조리          cook 시작                                                                   90
수리          repair 시작                                                                 90
도피          flee 시작                                                                   30  (공통 간격 무시)
맞음 / 기절     COMBAT_HIT(npc). 맞은 뒤 기절했으면 기절 문장                                   5   (공통 간격 무시)
습격 끝        RAID_ENDED. 플레이어 반경 reactRadius(16) 안의 주민                               —
새 방          ROOM_REGISTERED / ROOM_TYPE_CHANGED(새 타입). 방 중심 반경 16 안에서 가장 가까운 주민 한 명. 방 타입별 문장  —
마을 레벨       VILLAGE_LEVEL_UP. 플레이어 반경 16 안의 주민                                     —
도착          NPC_ARRIVED 의 그 주민                                                        —
```

- 공통 간격: 한 주민의 두 말 사이는 npcCooldownSeconds(10 실초) 이상이다. 위 표의 "공통 간격 무시" 만 예외다.
- 말하지 않을 때: 자는 중(sleep)·대화 중(talk)·기절 중. 기절 중에는 맞음 / 기절 문장만 한다.
- 말 걸기 문장의 우선순위: 도피 중 → 기절 중 → 배고픔(식사 구간·이번 끼니 안 먹음·저장소 food 0) →
  잘 곳 없음(19:00~05:00·배정된 침대 없음) → 지금 하는 일(Action 종류. 서 있거나 걷는 중이면 역할별 잡담).
  인사 문장은 시간대(새벽·아침 / 낮 / 저녁 / 밤)마다 따로 둔다.
  배고픔·잘 곳 없음은 플레이어가 할 일을 주민의 말로 알려 주는 힌트다. 조건식은 판단(19.4)의 것을 읽기만 한다.
- 문장 고르기는 결정적이다. 14.1 의 유일한 무작위를 늘리지 않는다. 주민·상황별로 말한 횟수 n 과 주민 id 의 해시 h 로
  `lines[(h + n) % lines.length]` 를 고른다. 횟수는 저장하지 않는다(로드 뒤 처음부터 센다).
- 문장은 `src/game/data/barks.ts` 에 둔다. 창립 주민(농부·요리사·목수)은 역할별 문장이 있으면 그것을, 없으면 공통 문장을 쓴다.
  말투는 진행 대사와 같은 반말이다. 한 문장은 24 자 안팎으로 짧게 쓴다.
- 표시(렌더): 말풍선은 머리 위에 3.5 실초 보이고 흐려진다. 같은 주민이 새 말을 하면 이전 말풍선을 바꾼다.
  카메라에서 22 칸보다 먼 주민의 말풍선은 숨기고, 동시에 보이는 말풍선은 가까운 순으로 4 개까지다.
  글자 선명도를 위해 방 이름 라벨·+N 과 같은 DOM 방식이다. 벽 뒤에서도 보인다(거리 제한으로 줄인다).
- 소리(TASK-BARK-002): 말풍선과 함께 짧은 웅얼거림을 낸다. 글자(공백·문장부호 제외) 두 자마다 짧은 음 하나, 1~6 개.
  음높이는 역할별(목수 낮게 · 농부 중간 · 요리사 높게 · 주민은 id 마다 조금씩 다르게)이고 글자마다 조금 오르내린다.
  도피·맞음은 빠르고 높게, 기절은 느리게 내려가고, "?" 로 끝나면 끝음이 올라간다. 같은 문장은 같은 소리다.
  듣는 위치(카메라)에서 멀수록 작아지고 22 칸 밖은 소리를 내지 않는다. 동시에 두 주민까지만 낸다. 음소거(30 장)를 따른다.
- 규모: 인사 확인은 주민 수에 비례하는 거리 비교뿐이며 복셀을 탐색하지 않는다. 표시 개수 상한은 렌더가 가진다.
  주민 100 명이어도 말의 빈도는 주민별 간격으로 묶인다.

# 20. Game Clock

```text
secondsPerGameHour   25 실초
1 게임일              600 실초 = 10 분
시작 시각             07:00, Day 1
```

90~120분 플레이 = 약 9~12게임일.
gameMinutes=0은 Day 1 07:00이다. absoluteMinutes=7×60+gameMinutes에서
day=1+floor(absoluteMinutes/1440), 시각은 absoluteMinutes%1440으로 계산한다.
nightId와 예약 시각도 이 기준을 공유한다.

## 20.1 DayPhase

```text
05:00 ~ 07:00   dawn
07:00 ~ 12:00   morning
12:00 ~ 13:00   noon
13:00 ~ 18:00   afternoon
18:00 ~ 20:00   evening
20:00 ~ 05:00   night
```

## 20.2 시간 배속

디버그 모드에서만 1× / 4× / 16× 를 지원한다. 배속은 게임 시계만 빠르게 한다. 캐릭터 이동 속도는 그대로이므로
16× 에서는 주민이 게임 시간으로 늦게 도착한다(시험용 동작, ADR 025).

## 20.3 시간은 앞으로만 간다

gameMinutes는 줄어들지 않는다. 디버그의 "시각 강제 설정"은 지정한 시각의 **다음 도래**로
앞당기기만 한다(이미 지났으면 다음 날의 그 시각). 채석장·취침·식사·예약의 처리 키가
단조 증가하는 시간을 전제하기 때문이다. 시각 경계는 등호가 아니라 "직전 값 < 경계 ≤ 현재 값"의
통과로 검사한다. 한 번의 강제 설정으로 여러 DayPhase를 지나도 `DAY_PHASE_CHANGED`는
최종 DayPhase로 한 번만 발행한다.

# 21. World State

ADR 004 를 유지한다. **아무것도 저장하지 않는 순수 계산기다.**

## 21.1 계산식

```text
population     = registry.npcs.size

foodLevel      = clamp(round(100 * storage.food
                             / (population * mealsPerDay * targetDays)), 0, 100)
                 mealsPerDay = 2, targetDays = 2
                 population == 0 이면 100

housingLevel   = clamp(round(100 * 접근 가능한 침대 수 / population), 0, 100)
                 population == 0 이면 100

safetyLevel    = 습격이 한 번도 없었으면 100
                 아니면 round(100 * (직전 습격에서 마을 중심에 도달하지 못한 몬스터 수)
                                  / (직전 습격의 총 몬스터 수))

happinessLevel = round(foodLevel * 0.4 + housingLevel * 0.3 + safetyLevel * 0.3)
```

## 21.2 반올림 규칙

모든 지표는 `Math.round` 를 마지막에 한 번만 적용한다.
중간 계산에서 반올림하지 않는다.

## 21.3 변경 API 를 제공하지 않는다

```text
increaseFood()    없다
setPopulation()   없다
```

지표를 바꾸려면 원인이 되는 실제 상태를 바꾼다.

## 21.4 safetyLevel 이 Version 0.2 와 다른 이유

Version 0.2 는 `막힌 입구 타일 수 / 5` 였다.

자유 건축에는 정해진 입구가 없다. 벽을 사전에 채점하면
플레이어가 미학이 아니라 점수를 위해 벽을 쌓는다.

**결과로만 판정한다.** 근거는 ADR 015 다.

## 21.5 계산 시점

GameWorld.update의 14번째 슬롯에서 계산해 이후 UI·이벤트에 공유한다.
종 비용 확정처럼 원자적 변경이 필요한 명령은 같은 순수 함수로 현재 입력을 재검증한다.
저장하지 않는다.

## 21.6 각 지표를 읽는 곳

```text
foodLevel        레벨 3 게이트. 종 패널 / 디버그 패널 표시
housingLevel     레벨 2 / 3 게이트. 종 패널 / 디버그 패널 표시
safetyLevel      happinessLevel 의 입력. 디버그 패널 표시
happinessLevel   표시 전용. 이번 범위에서 게이트·NPC 판단에 쓰지 않는다
```

이번 범위에서 네 지표는 상시 HUD 에 두지 않는다. 종 패널의 게이트 목록과
F3 디버그 패널에서 본다. 17 장의 "happinessLevel 이 내려간다" 는 결과의 설명이며
그 값을 조건으로 쓰는 시스템이 있다는 뜻이 아니다.

# 22. 감사 포인트

## 22.1 획득

```text
주민이 침대에서 잠들었다          +5   밤당 주민 1 명 1 회
주민이 조리를 완료했다             +3   조리 1 회당
주민이 식당에서 식사했다           +2   식사 1 회당
새 방 타입이 처음 인식되었다        +20  타입당 최초 1 회
진행 이벤트를 완료했다             +15  이벤트당 1 회
```

**반복 보상은 주민의 사용에서 발생한다.** 최초 방 타입과 진행 이벤트는 일회성 예외다.
`EmptyRoom`은 최초 인식 보너스를 주지 않는다.
ROOM_REGISTERED와 ROOM_TYPE_CHANGED를 같은 타입별 중복 방지 경로로 처리한다.
취침 중복 키는 npcId + nightId다. nightId는 그 취침 구간이 시작된 20:00의 day다.
자정 뒤 00~05시에도 이전 day의 nightId를 사용한다. 로드 후에도 키를 유지한다.

## 22.2 표시

포인트가 발생하면 해당 주민(또는 방) 위에 `+N` 이 떠올라 사라진다.

**이 연출은 필수다.** 포인트가 어디서 나왔는지 모르면 인과가 끊어진다.

## 22.3 회수하지 않는다

방이 해제되어도, 몬스터가 벽을 부숴도 이미 얻은 포인트는 줄지 않는다.

# 23. 마을 레벨과 종

## 23.1 레벨표

```text
레벨  해당 단계 비용   게이트 조건                                     주민 정원
 1     -         시작 상태                                        3
 2     80        인식된 방 >= 2
                 housingLevel >= 50                               4
 3     200       인식된 방 >= 4
                 foodLevel >= 50
                 housingLevel >= 100                              5
```

레벨 4 이상은 수직 슬라이스 범위 밖이다. 레벨 3까지 총 소비량은 80+200=280이다.

## 23.2 해금표

```text
레벨 1   plank / door / torch / farmland / bed / table / chair / cooking_stove / water_pot
레벨 2   window / chest
레벨 3   stone_brick
```

해금되지 않은 블록은 제작 UI 에 회색으로 보이고, 필요 레벨이 표시된다.

**보이지 않게 숨기지 않는다.** 다음에 무엇이 오는지 알아야 계속할 이유가 생긴다.

## 23.3 종을 치는 절차

```text
종에 F 로 상호작용
    ↓
종 UI 가 열린다. 감사 포인트와 게이트 조건이 전부 표시된다
    ↓
모든 조건을 만족하면 [종을 친다] 버튼이 활성화된다
    ↓
gratitude -= cost
villageLevel += 1
해금 적용
ResidentArrivalSystem이 레벨별 고유 예약을 만들어 다음 07:00에 한 명씩 도착시킨다.
레벨 2와 3을 같은 날 달성하면 다음 아침에 두 예약을 각각 처리한다.
스폰과 예약 완료를 원자적으로 처리하며 진행 이벤트는 주민을 생성하지 않는다
```

## 23.4 미충족 조건을 반드시 표시한다

```text
감사 포인트    120 / 80     OK
인식된 방       1 / 2        부족
housingLevel  33 / 50      부족
```

"칠 수 없음" 만 표시하면 안 된다.

## 23.5 레벨은 내려가지 않는다

게이트 조건이 다시 거짓이 되어도 이미 올린 레벨과 해금은 유지된다.

근거는 ADR 013 이다.

# 24. 몬스터

## 24.1 습격

```text
1 차 습격    villageLevel >= 2 를 달성한 뒤 첫 21:00     몬스터 3
2 차 습격    villageLevel >= 3 이고 1차 습격이 종료된 뒤 첫 21:00     몬스터 5
```

그 외의 밤에는 몬스터가 나오지 않는다.

**상시 스폰을 하지 않는다.** 습격은 사건이어야 하며, 배경 소음이 되면 안 된다.

## 24.2 제원

```text
체력          3
이동 속도      2.6 / 초
공격력         2 (NPC / 플레이어에게)
공격 간격      1.5 초
파괴 속도      blockDefinition.breakSeconds × 2.0
강제 소멸      05:00
공격 사거리    수평 1.2 (26.1)
```

## 24.3 AI

목표는 종 블록 자체가 아니라 종 중심 반경 6 안의 통행 가능한 발 위치 집합이다.
종까지의 3차원 거리는 NPC와 같은 발밑 중심 좌표로 계산한다.

1. 목표 집합으로 경로를 찾는다. 있으면 이동한다.
2. NODE_LIMIT이면 현재 위치에서 탐색 세션을 다음 프레임에 이어간다.
   매번 처음부터 다시 시작하지 않는다. 입력 월드가 바뀌면 세션을 무효화한다.
   탐색을 취소하고 이동할 경우에도 검증된 partialPath만 허용한다.
3. NO_PATH이면 탐색으로 확인한 도달 가능 영역의 경계에서 파괴 대상을 고른다.
   후보는 terrain=false, breakSeconds!=null이고, 도달 가능한 셀에서 수평 인접 또는
   그 위 칸으로 공격 가능한 장애물이다. 목표까지 거리 → 접근 경로 길이 → 좌표 순으로 고른다.
4. 접근 경로를 따라 벽 앞으로 이동한 뒤 파괴한다. 벽에서 떨어져 스폰돼도 접근해야 한다.
5. 후보가 없거나 습격 피해 상한을 소진하면 도달 가능한 플레이어/NPC를 추적·공격한다.
   그 경로도 없으면 배회한다. 05:00에는 모두 소멸한다.
   추적 대상은 반경 chaseRadius(12) 안에서 가장 가까운 대상이다. 경로는 1 초마다 대상의 현재 칸으로 다시 찾되,
   탐색 한 번의 누적 확장은 chaseMaxNodes(800)까지다. 상한에 걸리거나 NO_PATH 이면 그 대상을
   chaseRetrySeconds(3 실초) 동안 쫓지 않고 다음으로 가까운 대상을 본다. 쫓을 대상이 없으면
   추적 전 모드(종 도달 뒤 대기 / 배회)로 돌아간다 (TASK-PERF-003, ADR 040).

습격당 파괴 상한은 점유 복셀 16칸이다. 문·침대는 2칸을 한 번에 차감한다.
상한보다 큰 객체는 파괴하지 않는다. 파괴 예산과 이미 사용한 수는 저장한다.
피해 상한 소진은 종 도달 판정을 막지 않는다. 이미 열린 경로가 있으면 계속 이동한다.

## 24.4 마을 중심 도달 판정

```text
몬스터가 종으로부터 반경 6 안에 들어오면 "도달" 로 기록한다
```

이 기록이 `safetyLevel` 계산의 분자를 만든다.

## 24.5 습격 종료

```text
모든 몬스터가 처치되었거나 소멸했다
    ↓
RAID_ENDED 이벤트 발행
safetyLevel 계산에 쓰일 (도달 수 / 총 수) 를 기록한다
```

# 25. 파괴와 수리

## 25.1 DamageLog

DamageEntry는 고유 damageId, 원본 blockId, 전체 점유 cells, gameMinutes와
다중 칸 객체의 anchor / facing / objectId를 보관한다.
단일 블록은 cells 한 개이고 다중 칸 객체는 한 건으로 기록한다.
같은 객체의 BLOCK_CHANGED 알림을 여러 번 받아도 batchId로 한 번만 기록한다.

피해 이력과 미수리 목록을 구별한다. 아침 보고는 실제 파괴 당시 기록으로 계산하고,
그 사이 수리한 좌표는 미수리 표시에서만 지운다.

## 25.2 목수의 수리

```text
낮 시간(07:00 ~ 18:00)에만 수행한다
하루 최대 repairPerDay = 8 점유 복셀 (두 칸 객체는 2)
수리 시간은 점유 복셀당 게임 시간 15분
재료를 소비하지 않는다
```

재료를 소비하지 않는 이유는 창고 관리가 새 밸런스 축이 되기 때문이다.
대신 **하루 8 점유 복셀**이라는 상한이 플레이어의 개입 여지를 남긴다.

## 25.3 플레이어의 수리

플레이어가 해당 좌표에 다시 놓으면 수리한 것으로 처리한다.
다중 칸 피해는 원래의 모든 cells가 다시 점유되면 해결한다.
목수는 전체 cells가 비어 있고 캐릭터와 겹치지 않을 때만 원래 객체를 복원한다.
부분적으로 플레이어가 채운 피해는 자동 덮어쓰기하지 않고 수리 대상에서 건너뛴다.
당일 수리량과 기준 day는 저장하며 자정에 한 번 초기화한다.

## 25.4 아침 피해 보고

```text
07:00 에 지난밤 파괴 이력이 있으면 (보고 여부는 저장)
    피해 요약 패널을 띄운다
    "지난밤 블록 12 개가 파괴되었습니다"
    파괴 좌표를 월드에 반투명 붉은 표시로 나타낸다 (수리될 때까지)
```

# 26. 플레이어 전투

```text
공격          좌클릭 (블록이 아닌 몬스터를 조준했을 때)
공격력         1
공격 간격      0.5 초
사거리         2.5
넉백          약하게
```

무기 / 장비 / 스킬을 구현하지 않는다.

플레이어 체력이 0 이 되면 종 옆에서 부활하고, 인벤토리를 잃지 않는다.
게임 오버를 두지 않는다.

## 26.1 공격·기절·부활의 세부 (READY-05, ADR 036)

```text
플레이어 공격    조준 광선이 사거리 2.5 안에서 블록보다 먼저 몬스터 몸체에 닿으면 좌클릭이 공격이다. 그때는 블록을 부수지 않는다
넉백            맞은 몬스터를 플레이어 반대쪽으로 0.3 칸 밀어낸다(충돌 이동)
몬스터 공격      수평 거리 1.2 이하, 높이 차 1.5 미만, 두 몸체 가슴 높이를 잇는 선분에 고체 칸이 없을 때
몬스터 대상      사거리 안의 공격 가능한 대상 중 가장 가까운 것(플레이어·기절하지 않은 주민). 없으면 원래 판단(종으로 이동·파괴)
추적            종 반경에 도달했거나 파괴 후보·예산이 없으면 반경 12 안 가장 가까운 대상을 추적한다. 없으면 배회한다
주민 기절        체력 0 → 30 게임분 행동하지 않고 주저앉는다. 기절 중에는 공격받지 않는다. 깨어나면 체력 10 으로 회복한다
플레이어 부활     체력 0 → 종 둘레 광장 칸 중 몬스터와 3 칸 이상 떨어진 칸(없으면 가장 먼 광장 칸)에서 체력 20 으로 부활한다
부활 보호        부활 뒤 3 실초 동안 공격받지 않는다. 열린 모달은 닫는다
```

# 27. 진행 이벤트

## 27.1 목록

```text
id                      조건                                      보상 / 결과
EVENT_ARRIVAL           게임 시작                                  목표: "섬을 둘러보세요"
EVENT_FARM_REQUEST      Farmer 와의 첫 대화를 마쳤다                 목표: 밭을 만든다
EVENT_KITCHEN_REQUEST   VillageStorage.crop >= 3                   목표: 주방을 만든다
EVENT_BEDROOM_REQUEST   VillageStorage.food >= 3                   목표: 침실을 만든다
EVENT_BELL_REQUEST      인식된 방 >= 2                             목표: 종을 친다
EVENT_WALL_REQUEST      1 차 습격이 끝났다                          목표: 마을을 벽으로 막는다
EVENT_NEW_RESIDENT      villageLevel >= 3 AND population >= 5       도착 확인 대화·연출
EVENT_SLICE_END         2차 습격 종료 뒤 첫 07:00 이후 AND population >= 5  엔딩 연출
```

8개다. 표의 순서대로 이전 이벤트 완료를 AND 조건으로 붙인다.
종 요청은 EmptyRoom을 포함한 인식된 방 수를 센다. 레벨 게이트와 같은 기준이다.
주민 도착 이벤트는 도착 사실을 확인할 뿐 스폰하지 않는다.
엔딩은 07:00 한 프레임과의 동등 비교가 아니라 누적 시각의 도달 여부로 판정한다.
같은 프레임의 주민 예약 처리를 먼저 마치고 이벤트를 표 순서대로 평가한다.

## 27.2 모든 조건은 결정적이다

게임 상태만으로 참 / 거짓을 판정할 수 있다.
"첫 번째 밤 또는 두 번째 밤" 같은 모호한 조건을 쓰지 않는다.

## 27.3 완료된 이벤트는 롤백되지 않는다

조건이 다시 거짓이 되어도 완료 상태를 유지한다.

몬스터가 벽을 부술 수 있게 되었으므로(ADR 015) 이 규칙이 필수다.

## 27.4 이벤트와 대사를 분리한다

ADR 010 을 유지한다.

```text
이벤트 발생          →  일회성 보상과 NPC 대화 표시가 적용된다 (제작 해금은 레벨 소유)
플레이어가 대화한다    →  목표 문구가 바뀐다
```

해금을 대사에 걸지 않는다. 제작 해금은 대사에 묶지 않는다. 단, 첫 Farmer 대화 완료는 FARM_REQUEST의 명시적인 조건이다.
ARRIVAL은 초기 목표와 주민 세 명의 첫 대화 표시를 등록한다.
후속 대사를 나중에 읽어도 이미 달성한 조건·보상은 되돌리지 않는다.
진행 대사는 dialogueId로 식별하며 NPC별 미완료 목록에 순서대로 보관한다.
같은 NPC의 새 대사가 기존 미완료 대사를 덮어쓰지 않는다.
목표는 27.1의 원천 이벤트 순서로 전진한다. 늦게 읽은 이전 단계 대사는 현재 목표를
과거 단계로 되돌리지 않는다. 첫 Farmer 대사는 종료 시 밭 목표를 적용하고 완료 id를
기록한다. FARM_REQUEST는 그 사실을 확인해 보상하며 같은 요청을 다시 듣게 하지 않는다.
구체 타입·소유권과 저장 형식은 ARCHITECTURE 20~23장을 따른다.

# 28. 플레이 시나리오

시간 구간은 테스트할 가설이며 이벤트의 조건이 아니다. 첫 취침은 20~30분 내 목표다.
90~120분을 채우려고 대기·채집량을 인위적으로 늘리지 않는다. 실제 소요를 기록한다.

## Phase 0 — 도착 (0 ~ 5 분)

```text
EVENT_ARRIVAL
목표          "섬을 둘러보세요"
```

플레이어가 폐허 마을에 도착한다. 주민 3 명의 머리 위에 대화 표시가 있다.

대사가 먼저 시작되지 않는다. 플레이어가 다가가는 것이 첫 행동이다.

이 구간에서 플레이어가 배워야 하는 것:

```text
움직인다 / 나무를 벤다 / 흙을 판다 / 블록을 놓는다
```

**방도 주민 행동도 아직 없다. 블록을 만지는 것 자체가 기분 좋아야 한다.**

## Phase 1 — 밭 (5 ~ 10 분)

```text
EVENT_FARM_REQUEST   Farmer 와 첫 대화를 마쳤다
```

농부:

> 밭이 망가져서 먹을 것을 만들 수 없어.

```text
목표          "밭흙을 4 칸 만들어 주세요"
```

플레이어가 `dirt` 를 캐서 `farmland` 로 제작하고 깐다.

초기 씨앗 3개에 잎에서 얻은 1개를 종 [저장소] 탭으로 기부한다.
농부가 밭으로 걸어가 씨앗을 심는다. 12게임시간 후 역할 시간에 수확한다.

## Phase 2 — 주방 (10 ~ 20 분)

```text
EVENT_KITCHEN_REQUEST   VillageStorage.crop >= 3
```

요리사:

> 작물은 생겼는데, 요리할 곳이 없어.

```text
목표          "주방을 만들어 주세요"
```

**여기가 플레이어가 처음으로 방을 만드는 지점이다.**

대사에서 조건을 명시한다.

> 벽으로 둘러싸고, 문을 하나 달고, 화덕과 물통을 놓아 줘.
> 벽은 두 칸 높이는 되어야 해.

플레이어가 만든다. 십중팔구 처음에는 인식되지 않는다.

`Tab` 으로 진단 모드를 열면 원인이 보인다.

```text
   공간이 열려 있거나 너무 큽니다  (탐색 영역과 경로 표시)
```

막는다. 방 이름이 뜬다.

```text
   주방
```

감사 포인트 +20.

요리사가 주방으로 걸어간다. 조리한다. 감사 포인트 +3.

## Phase 3 — 침실 (20 ~ 30 분)

```text
EVENT_BEDROOM_REQUEST   VillageStorage.food >= 3
```

목수:

> 밥은 먹었지만, 잘 곳이 없어.

```text
목표          "침실을 만들어 주세요"
```

침대는 최초 사용을 볼 1개부터 만들고, 첫 종의 housing 조건을 위해 2개 이상 준비한다.
주민 3명 모두를 재우려면 3개가 필요하다. 밤이 오면 배정된 주민이 걸어 들어가 눕는다.

감사 포인트 +5 × 실제 침대에서 잠든 주민 수.

**이 장면이 이 게임의 핵심 검증 지점이다.**

## Phase 4 — 첫 번째 종 (30 ~ 45 분)

```text
EVENT_BELL_REQUEST   인식된 방 >= 2
```

목수:

> 마을에 종이 있어. 마을이 커졌을 때 치는 거야.

```text
목표          "마을의 종을 쳐 주세요"
```

플레이어가 종을 친다.

```text
마을 레벨 2
해금          window / chest
주민 정원      4
```

종 대사는 “주민이 늘어요. 밭을 8칸으로 넓히고 씨앗과 침대도 준비해 주세요”라고 안내한다.
같은 대사에서 다음 종의 조건도 알려 준다. **인식된 방 4개, housingLevel 100,
foodLevel 50 이상**이다. 침대와 음식의 필요량은 현재 주민 수와 같은 게이트 평가에서
계산해 표시한다. 주민 3명이면 침대 3개·food 6, 4명이면 침대 4개·food 8이 예시다.
도착 예정 주민의 침대도 미리 준비하도록 안내하되 현재 게이트의 추가 조건으로 세지 않는다.
새로 해금된 `chest`로 창고를, 이미 있는 `table` / `chair`로
식당을 만들 수 있다는 것까지 말해 준다.
레벨 3 게이트는 종 패널(23.4)에도 계속 표시되지만, 요청 루프가 끊기지 않도록
무엇을 지으면 되는지를 대사로 먼저 준다.
다음 아침, 새 주민이 도착한다.

## Phase 5 — 첫 번째 습격 (45 ~ 60 분)

`villageLevel >= 2` 를 달성한 뒤 첫 21:00.

몬스터 3 마리가 나타난다. 마을에 벽이 없으므로 그대로 들어온다.

주민들이 도망친다. 플레이어가 싸운다.

```text
EVENT_WALL_REQUEST   1 차 습격이 끝났다
```

목수:

> 이대로는 안 돼. 마을을 막아야 해.

```text
목표          "마을을 벽으로 둘러싸 주세요"
```

이 목표에는 진행 수치를 붙이지 않는다.
어디를 어떻게 막을지는 플레이어가 정한다.

## Phase 6 — 확장·두 번째 습격과 엔딩 (60 ~ 120 분)

플레이어가 방 4 개를 채우고 종을 다시 친다.
Phase 4 의 안내와 종 패널의 미충족 항목을 따라 식당과 창고를 더한다.
어떤 방을 고를지는 플레이어가 정한다. 방 수와 지표만 게이트다.

```text
마을 레벨 3
해금          stone_brick
주민 정원      5
EVENT_NEW_RESIDENT
```

1차 습격 종료 조건을 만족하는 다음 21:00에 몬스터 5마리.

몬스터가 벽 앞에서 멈추고 부수기 시작한다.
플레이어가 막아선다. 판자벽 몇 칸이 부서지지만 마을은 지켜진다.

```text
EVENT_SLICE_END   2 차 습격이 끝난 뒤 첫 07:00
```

아침. 목수가 부서진 곳을 고치기 시작한다.

주민 5 명이 각자의 일로 흩어진다.

```text
   이 마을을 조금 더 키워보고 싶다.
```

## 29.0 모달 중 시간·입력·포인터 락 (READY-03)

화면 상태는 셋 중 하나다.

```text
조작 중      포인터 락. 게임 입력이 들어간다
모달        인벤토리·제작(E) / 종 / 저장소 / 대사 / 피해 보고. 포인터 락을 풀어 커서로 조작한다
메뉴        Esc 메뉴. 일시정지
```

```text
                 게임 시간·NPC·몬스터·습격     플레이어 이동·시선·파괴·설치
조작 중           진행                         입력대로
모달             진행 (멈추지 않는다)            막는다. 캐릭터는 제자리에 선다
메뉴             멈춘다 (world.update 없음)      막는다
```

- 모달은 한 번에 하나만 열린다. 모달이 열린 동안 다른 모달 키는 무시한다.
- 조작 중 포인터 락이 풀리면(Esc, 창 전환, 탭 이동) 메뉴가 열린다. 게임 시작 화면도 메뉴다.
- 메뉴는 캔버스 클릭 또는 [계속] 으로 닫고 포인터 락을 다시 건다. 그 클릭은 게임 조작이 아니다.
- 인벤토리는 E 로 열고 E 로 닫는다. E 로 닫으면 포인터 락을 다시 요청한다.
  Esc 로 닫으면 브라우저가 Esc 로 포인터 락을 다시 걸 수 없으므로 메뉴로 간다.
  락 요청이 거부되면 메뉴로 간다.
- 모달을 열 때 눌려 있던 키·마우스 버튼은 모두 뗀 것으로 한다. 모달을 닫은 뒤에도
  모달 동안 눌렀거나 계속 누르고 있던 키는 새로 누르기 전까지 게임에 들어가지 않는다
  (눌린 키 잔류 없음). 모달 안의 클릭은 게임의 파괴·설치로 전달되지 않는다 (클릭 관통 없음).
- 모달 중에도 몬스터는 플레이어를 공격할 수 있다. 플레이어가 기절하면 열린 모달을 닫는다
  (기절·전투 연결은 TASK-046). 종·대사·저장소·피해 보고의 실제 연결은 036 / 040 / 049 / 051 에서 한다.
- 방 진단(Tab)과 디버그 패널(F3)은 모달이 아니다. 조작을 막지 않는다.

## 29.1 UI 는 게임 상태를 소유하지 않는다

ADR 003 을 유지한다. UI 는 `*_CHANGED` 이벤트를 구독해서 표시만 한다.

DOM 오버레이로 구현한다. three 를 import 하지 않는다.

## 32.4 시간값은 전부 게임 시간 기준이다

실시간 `Date.now()` 를 저장하지 않는다.

## 32.5 Auto Save

```text
매일 07:00 에 자동 저장
종을 친 직후 자동 저장
```

저장소는 `localStorage` 가 아니라 `IndexedDB` 를 쓴다.
TypedArray를 문자열로 팽창시키지 않고 원자적으로 저장하기 위해 IndexedDB를 쓴다.
전체 원시 블록 배열은 약 2MiB이며 이것만으로 localStorage 한도를 넘는다고 단정하지 않는다.
저장은 프레임 끝의 커밋된 상태를 복사한다. 저장만으로 진행 중 Action·경로·예약을
취소하거나 다시 시작하지 않는다. 로드할 때만 저장하지 않은 임시 예약과 Action을
비우고 지속 상태에서 재판단한다.
활성 습격의 몬스터 체력·위치·도달 이력·피해 예산은 유지한다.
자동 저장은 현재 슬롯 한 개를 원자적으로 교체하며 로드 중 이벤트 보상은 발행하지 않는다.
전체 SaveData와 재구축 계약은 ARCHITECTURE 23장을 따른다.

# 35. 검산

## 35.1 식량 수급

```text
주민 3명: food 6/일. 주민 5명: food 10/일
요리: crop 2 → food 3
성장: 3단계 각각 4시간 = 12시간
농부: 07~12, 13~18시 근무. 한 칸은 하루 한 번 수확·재파종을 기준으로 잡는다
밭 4칸 → crop 4/일 → food 6/일: 시작 주민 3명의 이론상 유지량
밭 8칸 → crop 8/일 → food 12/일: 주민 5명 소비 10 + 여유 2
```

4칸은 입문 목표다. 첫 종 대사에서 8칸으로 늘리고 씨앗을 보충하도록 안내한다.
시작 3명 때도 이동·식사·위협과 첫 성장 대기 때문에 비축 없이 항상 충족된다는 보장은 없다.
요리 4회는 하루 4게임시간으로 역할 시간 10시간 안에 들어간다.
대표 배치(종 주변 평지, 각 시설 접근 거리 16칸 이내)의 실제 일간 생산은 TASK-053에서 측정한다.
음식 0에서도 농부·요리사는 다음 업무를 수행하므로 부족이 영구 정지를 만들지 않는다.

## 35.2 씨앗 수급

파종 seed -1, 정상 수확 seed +1이다. 작물이 파괴되지 않을 때만 순환한다.
4칸 입문에 초기 3개 + 채집 1개, 8칸 확장에는 총 8개를 확보한다.
잎은 25% 확률로 씨앗을 추가 드롭한다. 한 그루에서 반드시 나온다고 보장하지 않는다.
회수 leaves와 seed는 별도 드롭이며 leaves는 침대 제작에 쓴다.

## 35.3 감사 포인트 — 레벨 2의 단계 비용 80

```text
ARRIVAL / FARM / KITCHEN / BEDROOM 완료       4 × 15 = 60
Kitchen / Bedroom 최초 인식                  2 × 20 = 40
최소 예시 합계                                         100
```

주방 가구는 레벨 1에 해금되어 이 경로가 가능하다.
Kitchen + Bedroom 두 방, 침대 2개면 주민 3명의 housingLevel=67로 게이트를 통과한다.
이후 BELL_REQUEST의 +15와 주민 사용 보상은 위 최소 예시에 포함하지 않았다.
따라서 종을 칠 때 실제 잔액은 더 높을 수 있다.
이 계산은 진행 가능성을 검산하는 것이며 주민 사용의 재미를 입증하지 않는다.

## 35.4 감사 포인트 — 레벨 3의 단계 비용 200

레벨 2 이전 총 100을 얻었다고 보수적으로 계산하면 소비 후 잔액은 20이다.
추가로 180을 얻으면 레벨 3에서 200을 소비한다. 총 단계 비용은 280이다.

```text
DiningRoom / Storeroom 최초 인식             40
BELL_REQUEST / WALL_REQUEST                  30
취침 4명×5 + 요리 3회×3 + 식당 식사 4명×2끼×2 = 45/일
40 + 30 + 45×3일 = 205
```

밭을 8칸으로 늘리고 주민 4명용 침대·식사를 갖춘 경우 약 3게임일은 검증 가설이다.
4개의 방, food 8 이상(주민 4명 기준 foodLevel 50), 접근 가능한 침대 4개가 필요하다.
실제 플레이에서는 첫 밤 시각·조리·식사·습격·이동에 따라 달라진다.
레벨 3에서 도착할 다섯째 주민의 침대도 미리 준비하도록 종 대사에서 안내한다.

## 1. 현재 판단과 문서 역할

현재 구현 계획은 일반 Task 53개와 구조 검증 Task 2개이며, 그중 32개를 완료했다(PERF-001 포함).
TASK-022 재미 검증(G1)은 사람의 플레이로 두 축 모두 통과했다([기록](../state/2026-09-23_1400-task-022-gate-g1-passed.md)).
Phase D(023~026·028·029·034)와 READY-04 를 완료했다([기록](../state/2026-09-23_2241-phase-d-time-movement-and-sleep-gate.md)).
TASK-033 재미 검증 G2 도 사람의 플레이로 통과했다([기록](../state/2026-09-23_2309-task-033-gate-g2-passed.md)). 표현 개선 대상은 그 기록에 있다. 일반 화면 확인은 HUMAN_REVIEW 3장에 대기 중이다.

이 문서는 전체 이정표, 단계별 결과와 확장 시점을 안내한다. 세부 실행 순서·선행 의존·
Acceptance Criteria의 정본은 계속 [TASKS](TASKS.md)다. 같은 완료 조건을 별도로
관리하지 않으며 충돌하면 TASKS를 먼저 따른다. 수치·조건은 [MVP_SPEC](MVP_SPEC.md),
구조는 [ARCHITECTURE](ARCHITECTURE.md), 의도는 [GAME_DESIGN](GAME_DESIGN.md)을 따른다.

| 준비 영역 | 검토 결과 | 실행 기준 |

이유로 관계없는 기초 작업을 멈추거나, 반대로 명세 없이 해당 기능을 구현하지 않는다.

## 2. MVP 전체 로드맵

목표는 **아름답게 만든 공간에서 정감 있는 주민이 생활하는 순간**이다.
공간 표현과 주민 동작을 기능과 같은 단계에서 확인한다. MVP는 최대 5명·고정 섬이며,
100명 구조 시험은 별도 fixture다. 아래 행의 완료는 해당 Task의 AC와 검증 기록으로 판단한다.

| 단계 | 시작 조건 | 실행 묶음 | 단계 끝에 확인할 결과 |
| --- | --- | --- | --- |
| A. 복셀 기반 | TASK-001 준비 확인 | 001~008 + 027 | 고정 섬·폐허·종이 보이고 청크 편집과 Worker 결과가 일치한다. 팔레트와 계측 기준을 확보한다 |
| B. 플레이어 | A 완료, 관련 준비 항목 확정 | 009~016 | 걸으며 채집·제작·설치·파괴할 수 있다. 인벤토리와 월드 편집이 함께 확정된다 |
| C. 방 인식 ★ | B 완료 | 017~022 | 방 5종의 인식·실패 진단이 동작하고, 공간을 더 가꾸고 싶은지 실제 플레이로 판단한다 |
| D. 시간과 이동 | **022 통과** | 023~026, 028~029, 034 | 주민 3명의 이동·판단 골격과 낮밤이 연결된다. 아직 생활 기능 완료는 아니다 |
| E. 주민 생활 ★ | D 완료 | **033 → PERF-001 → 030~032 → SHAPE-001** | 귀가·취침·기상의 만족감을 먼저 검증한 뒤 농사·요리·식사를 연결한다 |
| F. 성장 | E 완료 | **039 → 035~038** | 주민 사용이 감사로 이어지고, 종·해금·기부·새 주민 도착이 동작한다 |
| G. 진행 | F 완료 | 040~043 | 요청·대사·목표로 첫 종까지 디버그 없이 진행한다. 후반 습격 조건은 이 단계에서 fixture 검증이다 |
| H. 방어 | G 완료, 전투 정책 확정 | 044~049 → PERF-002 | 습격·전투·도피·파괴·수리·피해 보고가 이어지고 실제 후반 진행과 연결된다 |
| I. 수직 슬라이스 검증 | H 완료 | 050~053 | 오디오·저장·엔딩을 완성하고 통합 테스트·실플레이·MVP 성능을 검증한다 |

범위 표기는 기능 묶음이다. 실제 순서는 [TASKS 2.3](TASKS.md#23-실행-순서와-기존-번호)을
따른다. 특히 027·039의 선행 이동과 034→033, 두 PERF의 위치를 유지한다.
일부 최소 효과음은 C와 F에서 이미 필요하며 I까지 미루지 않는다.

### 반드시 멈추는 지점

- **TASK-022**: 직접 방을 짓고 진단으로 고치는 과정, 공간을 가꾸고 싶은 마음을 확인한다.
  실패하면 판정·진단과 표현 문제를 나누어 개선하고 다시 검증한다. D로 넘어가지 않는다.
- **TASK-033**: 한 주민의 귀가→취침→기상을 보고, 이후 세 주민의 배정까지 확인한다.
  장면이 만족스럽지 않으면 이동·조명·실루엣·사용 자세를 개선한다. PERF-001과 농사로
  넘어가지 않으며 포인트를 붙여 실패를 가리지 않는다.
- **TASK-053**: 10개 통합 테스트, 분량 가설과 실제 소요, 시스템·감성 결과, 성능을
  함께 검토한다. 미통과 항목이 있으면 관련 Task를 다시 열고 MVP 완료로 표시하지 않는다.

022/033에서 플레이 관찰과 사람의 감상 기록 없이 자동 테스트만으로 재미 통과를
선언하지 않는다. 결과 형식은 TASKS 4.1을 사용한다.
PERF-001/002는 구조 위반을 수정하는 점검이다. synthetic 100명 시험의 FPS 미달을
MVP 진행 중단 조건으로 바꾸지 않는다. MVP 자체의 성능 완료 기준은 053에서 검증한다.

## 3. 세부 로드맵의 운영

1. TASKS 2.3에서 다음 Task를 고른다. 숫자순이나 본문에 놓인 Phase로 고르지 않는다.
2. 선행 Task의 완료 기록과 TASKS 2.5의 준비 항목을 확인한다. 미결정 항목은 정본을
   먼저 보완하고 검증 사례를 해당 Task의 AC에 넣는다.
3. Task의 작업·AC를 세션 단위로 구현한다. 한 세션에 크면 같은 Task 안에서
   데이터/순수 로직 → 연결 → 브라우저 검증으로 나누고 남은 AC를 기록한다.
   부분 작업을 완료된 Task로 세거나 범위를 넓히는 새 Task로 바꾸지 않는다.
4. 단위·통합·브라우저 검증의 범위를 구분하여 기록하고 체크박스를 갱신한다.
   코드 검증만으로 화면·재미·성능을 확인했다고 쓰지 않는다.
5. docs/state에 결과·다음 Task를 남기고 해당 변경만 commit/push한 뒤 원격을 확인한다.

Phase A는 2026-09-23에 완료했다([기록](../state/2026-09-23_1036-phase-a-voxel-foundation.md)).
Phase B는 같은 날 완료했다([기록](../state/2026-09-23_1130-phase-b-player.md)). READY-06 / 02 / 03을 확정했고
Test 1(블록)을 디버그 없이 통과했다. Phase C는 구현을 마쳤다([기록](../state/2026-09-23_1208-phase-c-room-recognition.md),
ADR 023). Test 2(1~11, 감사 포인트 제외)·Test 3을 headless 브라우저에서 통과했다. TASK-022 게이트 G1은
2026-09-23 사람의 플레이로 통과했다. READY-04 와 Phase D 를 2026-09-23 에 마쳤다. G2 를 통과했고 PERF-001 도 마쳤다([기록](../state/2026-09-24_0200-perf-001-structure-check.md)). 현재 다음 작업은 **TASK-030** 이다. 첫 실행 묶음의 문서 참조와 결과물은
[TASKS 2.7](TASKS.md#27-첫-실행-묶음phase-a의-세부-계획)에 있다.

고정 납기나 총 개발 일수는 아직 산정하지 않는다. 구현 속도와 두 재미 검증의 재작업량을
측정하지 않았기 때문이다. A 완료 시 Task별 실제 소요와 장애 원인을 기록하고 B~C의
예상 세션 수를 갱신한다. 022·033 통과 시 다음 묶음을 다시 추정하고, 053 뒤 확장 계획을
재검토한다. 완료일 가정 때문에 검증을 생략하지 않는다.

## 4. MVP 이후의 조건부 로드맵

아래는 장기 목표까지의 **계획 단계**다. 확장 구현 Task나 추가 콘텐츠가 승인·확정된
목록이 아니다. GAME_DESIGN 19 / MVP_SPEC 43의 후보를 그대로 두고, MVP 이후의 측정과
범위 결정에 연결한다. 현재 55개 Task에 다음 기능을 끼워 넣지 않는다.

| 단계 | 진입 조건 | 먼저 만들 계획·검증 | 다음 단계로 갈 근거 |
| --- | --- | --- | --- |
| 확장 계획 확정 | 053 완료와 작은 마을의 시스템·감성 결과 검토 | 방·가구·행동 확장 후보 중 다음 범위를 선택하고 MVP_SPEC의 후속 명세·AC·ADR을 마련 | 플레이 관찰에 근거한 범위, 담당 작업, 시험 장면·성능 예산이 명시됨 |
| 주민 10명 규모 | 확장 범위·완료 조건 확정 | GAME_DESIGN 19의 방·가구와 직업 후보를 필요한 만큼 구체화. 작업 후보·예약·시설 부족·생활 표현 검증 | 새 방이 실제 주민 행동으로 이어지고 기존 주민의 개성과 생활을 계속 알아볼 수 있음 |
| 주민 50명 규모의 중간 검증 | 10명 장면과 다음 규모 명세 통과 | 대형 월드 크기·활성/상주/가시 범위와 예산 정의. 측정 병목에 따라 Job·다중 주기·계층 경로·LOD·스트리밍의 도입 순서 결정 | 실생활·근경/원경·편집·저장/로드를 같은 조건에서 측정하고 정합성·감성·성능 기준 통과 |
| 주민 100명·대형 마을 검증 | 중간 규모 결과와 최종 시험 명세 확보 | 전체/상세/가시 주민 수를 구분해 장기 저녁 장면 검증. 미로드 경계·원거리 작업·시설 파괴·저장 복구 검증 | 큰 마을을 계속 바라보고 싶은지와 합의한 성능·정합성 기준을 실제 구현에서 확인 |
| 배포 형태 확정 | 지원 환경·에셋 규모·배포 요구가 구체화됨 | Browser와 Desktop/Steam 후보 비교. 필요한 에셋 팩·저장 어댑터·설치/업데이트 검증 계획 | 대상 플랫폼에서 실행·에셋·저장 호환성을 확인. wrapper와 출시 일정은 그때 결정 |

50명은 장기 목표 50~100명 사이의 측정 단계이며 새 주민 정원이나 게임 규칙이 아니다.
배포 계획은 규모 확대와 별도로 검토할 수 있고 100명 완성을 선행 조건으로 삼지 않는다.
자동 건설·지역/섬·전투 심화·관계 시스템은 기존 후보로 남긴다. 위 규모 단계가
그 후보 전부의 구현을 요구하는 것은 아니다.

장기 구조의 구체 책임은 ARCHITECTURE 2.3 / 3.2~3.3 / 9.5~9.6 / 11.6 / 14.4를 따른다.
PERF fixture 결과를 실제 100명 콘텐츠의 재미·성능 통과로 대신하지 않는다.

## 5. 갱신 기준

- Task의 상태·AC는 TASKS, 관찰 증거와 실제 소요는 docs/state에 기록한다.
- 단계 범위나 순서가 바뀌면 TASKS를 먼저 고치고 이 로드맵의 해당 행을 맞춘다.
- 게임 규칙·구조 변경은 각 정본을 먼저 고치고 주요 결정은 ADR에 남긴다.
- 미결정 정책의 최신 목록은 TASKS 2.5다. 과거 state 문서의 열린 항목은 역사적 기록이다.
- 현재 구현 상태와 다음 Task는 README / docs/README에도 함께 반영한다.

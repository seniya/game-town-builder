# 설계 문서 검토 — 핵심 방향은 유지하되 구현 전 정합성 보완 필요

검토일: 2026-09-22
검토 기준 커밋: 1655c3b
상태: 검토 완료, 아래 문제들은 미수정

## 범위와 방법

GAME_DESIGN → MVP_SPEC → ARCHITECTURE → TASKS 순서로 읽고,
README, 작업 규약, 관련 ADR, 조사 문서와 이전 정합성 기록을 대조했다.
폐기된 ADR와 개정 전 작업 기록은 현재 구현 기준으로 사용하지 않았다.

저장소에는 구현 코드, package.json, lockfile이 없다. 따라서 이번 결과는
문서 정적 검토와 명세의 작은 반례 검산이며, 실제 게임 테스트 결과가 아니다.
방 탐색 규칙을 임시 Python 코드로 옮겨 빈 방 / 가구 / 벽 구멍을 비교했다.
Vite·Vitest 공식 근거 확인은 [조사 기록](../research/2026-09-22-review-source-check.md)에 남겼다.

검토 결과만 추가했다. 방 규칙, 해금, 수치, 기술 스택 변경은 확정하지 않았다.
새로운 기술 결정을 채택하지 않았으므로 ADR은 추가하지 않았다.

## 전체 판단

핵심 목표인 **자유 건축 → 방 인식 → 주민의 사용 → 플레이어의 관찰**은 일관된다.
방 실패 진단을 필수로 둔 점, TASK-022 / 033에서 재미를 검증하는 점,
게임 규칙과 렌더의 분리, 현재 상태와 누적 성취의 분리는 유지할 가치가 있다.

그러나 현재 문서를 그대로 구현하면 정상 플레이가 막히거나 핵심 완료 조건을
만족할 수 없다. README의 “문서 설계 완료”를 구현 준비 완료로 해석하면 안 된다.

## 먼저 해결할 명세 문제

### R01. 침대 재료인 leaves를 획득할 경로가 없다 — P1

근거: MVP_SPEC 8.5, 13.3, 14 (338, 699, 711행).

침대는 plank 4 + leaves 4를 요구하지만, leaves 파괴 드롭은 seed 1개(25%)뿐이다.
시작 인벤토리는 비어 있고 leaves 제작·지급 경로도 없다.
드롭 표를 그대로 구현하면 침대를 만들 수 없어 취침과 housing 게이트가 막힌다.

수정 방향: 잎 블록 회수와 씨앗 추가 드롭의 관계를 명시하거나 기존 재료만으로
침대 레시피를 조정한다. 다른 제작 블록의 회수 드롭도 함께 명시해야 한다.
확인 조건: 새 게임에서 디버그 없이 침대 제작까지 도달한다.

### R02. 주방 요청이 주방 가구 해금보다 먼저 온다 — P1

근거: MVP_SPEC 23.2, 27.1, 28 Phase 2~4, 35.3; TASK-037 / 043.

의도한 순서는 밭 → 주방 → 음식 → 침실 → 첫 종이다.
그러나 cooking_stove와 water_pot은 첫 종을 친 뒤 레벨 2에서 열린다.
레벨 2 수급 검산도 아직 만들 수 없는 Kitchen 최초 인식 보너스를 포함한다.

침실·식당을 먼저 짓는 우회 가능성과 별개로, “요청만 따라가도 레벨 2 도달”은
현재 규칙으로 보장되지 않는다. R01도 별도로 해결해야 한다.

수정 방향: 주방을 먼저 요구한다면 필수 가구를 레벨 1에 두거나,
첫 종까지의 요청 순서와 포인트 검산을 함께 재설계한다.
확인 조건: 초기 자원·해금 상태로 여덟 이벤트를 끝까지 추적하는 진행 표를 만든다.

### R03. 고체 가구를 놓으면 방 인식이 실패한다 — P1

근거: MVP_SPEC 8.1, 11.2~11.3 (280~285, 498, 518행); TASK-019.

침대·화덕·식탁·상자는 고체다. flood fill은 비고체만 내부로 인정하고,
벽 이외의 고체를 만나면 NOT_ENCLOSED로 실패한다.
따라서 빈 방 안에 침대를 놓는 순간 Bedroom 판정에 도달하기 전에 실패한다.

검산: 7×7 외곽, 5×5 내부의 방은 내부 25칸으로 성공했다.
동일 방 중앙에 고체 가구를 넣으면 가구 좌표에서 NOT_ENCLOSED가 나왔다.

수정 방향: 방의 바닥 영역, 가구 점유 영역, 실제 보행 영역을 구분하고,
면적 계산과 가구 수집 기준을 같이 정의한다. 문은 통행에서 비고체여도
방 탐색에서는 경계 검사를 먼저 적용한다는 우선순위도 명시한다.
확인 조건: 빈 방 → 침대 설치 → 침실 → 침대 철거 → 빈 방이 성립한다.

### R04. 문에서 먼 벽을 완성·복구하면 재인식되지 않을 수 있다 — P1

근거: MVP_SPEC 11.6 (565~568행); ARCHITECTURE 10.5 (605~607행).

재판정 대상은 기존 방과 변경점에 인접한 문뿐이다.
문을 먼저 설치하고 먼 벽을 마지막에 막으면 아직 기존 방이 없어 큐에 들어가지 않는다.
이미 해제된 방의 먼 벽을 복구할 때도 같은 문제가 생긴다.
현재 RoomShape는 바닥 위 첫 층의 interior / boundary만 저장하므로,
바닥 아래 또는 벽 둘째 층 변경을 어떤 방에 연결할지도 정해져 있지 않다.

수정 방향: 실패한 후보 영역을 유지하거나 변경점에서 영향을 받는 문·후보를 찾는
제한된 탐색을 정의한다. 바닥·머리 공간·벽 높이까지 무효화 범위에 포함한다.
확인 조건: 건축 순서와 무관한 인식, 해제 후 복구, 둘째 층 벽 제거를 검증한다.

### R05. 현재 flood fill로는 “정확한 벽 구멍 좌표”를 보장하지 못한다 — P1

근거: MVP_SPEC 11.3 / 39 Test 3; TASK-018 / 022.

평지에 벽 한 칸이 빠져 있으면 그 틈은 정상적인 공기 셀이다.
탐색은 바깥 평지로 확장되다가 100칸 상한에서 TOO_LARGE로 끝날 수 있다.
이 실패 타입에는 좌표도 없다. 월드 경계까지 갔더라도 그 좌표는 벽의 구멍이 아니다.
임시 반례에서도 벽 한 칸 누락은 TOO_LARGE로 종료했다.

수정 방향: 방 인식과 별도로 누수 후보를 찾는 진단을 설계하거나,
모든 열린 형태에서 정확한 한 칸을 보장한다는 완료 조건을 현실적으로 정리한다.
플레이어가 의도한 방 모양이 유일하지 않은 열린 지형도 고려해야 한다.

### R06. 방 접근성과 실제 NPC 통행 조건이 다르다 — P1

근거: ARCHITECTURE 7.2, 8.2, 10.2, 28.3;
MVP_SPEC 12.2 / 12.4; ADR 015 통행 조건.

matchRecipe는 발 위치의 비고체와 바닥만으로 통행 가능하다고 설명하지만,
NavigationGraph는 머리 공간까지 두 칸이 비어 있어야 한다.
침대 옆에 한 칸 높이 공간만 있어도 housing에 포함될 수 있다.
실내의 국소 인접성만으로 외부 주민부터의 도달 가능성도 보장되지 않는다.

또한 침대·의자 좌표 자체를 이동 목적지로 쓰는데 이 블록들은 고체다.
접근 셀까지 걷기와 가구 사용 자세로 전환하기를 분리해야 한다.
발밑 중심을 저장하는 AabbBody에 blockToWorldCenter를 적용하면 y가 0.5 높아지는
좌표 기준 차이도 있다.

수정 방향: 공통 순수 통행 판정, 접근 셀, 사용 위치, 실제 경로 실패 시 대체 행동을
명시한다. room이 nav 구현체를 가져오지 않는다는 원칙만으로 중복 판정을 정당화하지 않는다.

### R07. 두 칸 침대와 두 칸 문을 표현하는 계약이 빠졌다 — P1

근거: MVP_SPEC 10.4 / 11.2; ARCHITECTURE 6.2~6.3, 10.2, 23.

침대는 두 칸을 점유하지만 저장 배열에는 blockId만 있고,
방향·대표 좌표·부속 칸의 연결 정보가 정의되지 않았다.
서로 붙은 두 침대를 구분하거나 한쪽 파괴 시 나머지 처리와 드롭을 결정할 수 없다.
DamageEntry도 좌표와 blockId만 보관하여 원래 배치를 복원할 정보가 부족하다.

문 역시 한 번 설치하면 세로 두 칸인지, 문 블록 둘을 따로 놓는지 불명확하다.
한 칸 문 위에 판자를 두면 벽 높이는 충족하지만 1.8 높이 주민이 통과하지 못한다.

수정 방향: 다중 칸 가구의 점유·설치·파괴·수리·저장 계약과 문 높이를 먼저 결정한다.
확인 조건: 회전 배치, 두 침대 인접 배치, 부속 칸 파괴, 저장·로드를 다룬다.

### R08. 몬스터가 열린 마을에서도 종까지의 경로에 실패할 수 있다 — P1

근거: MVP_SPEC 8.1 / 24.3; ARCHITECTURE 18.1~18.2 (1007~1029행).

목표가 종 블록 좌표인데 bell은 고체이므로 그 좌표는 통행 가능한 발 위치가 아니다.
목표 판정의 별도 예외가 없으면 열린 마을에서도 NO_PATH가 나온다.
경로가 없을 때 파괴 후보는 현재 위치에 인접한 블록으로 한정되어,
벽과 떨어져 스폰된 몬스터가 벽까지 접근하는 경로도 보장되지 않는다.
terrain=false만 검사하면 파괴 불가인 bell도 파괴 후보가 된다.

수정 방향: 종 반경 안의 도달 가능한 셀을 목표 집합으로 정하고,
현재 도달 가능한 영역의 경계에서 파괴 대상을 고르는 규칙을 정의한다.
파괴 후보에 실제 파괴 가능 여부도 포함한다.
NODE_LIMIT의 “목표 방향으로 move”도 유효한 부분 경로 없이 벽을 관통하지 않게 정의한다.

### R09. 농사 검산에서 성장 단계와 NPC 근무 시간을 빠뜨렸다 — P1

근거: MVP_SPEC 15.2 (743행), 19.5, 35.1 (1775~1781행); TASK-030 / 053.

0(심은 직후) → 1 → 2(수확 가능), 전이당 4시간이면 성숙은 8시간이다.
반면 작업 완료 조건과 검산은 12시간을 요구한다. 단계별 지속시간을 명시해야 한다.

12시간을 채택해도 24 / 12 = 하루 두 번 수확은 성립하지 않는다.
농부의 역할 작업은 07~12시와 13~18시다. 같은 칸을 수확·재파종한 뒤
12시간 후에는 그날 역할 시간이 끝났으므로 같은 칸을 하루 두 번 수확할 수 없다.
따라서 밭 네 칸은 많아야 crop 4/일, food 6/일이다. 주민 다섯 명은 food 10/일을 쓴다.
이동·식사·위협을 고려하면 실제 생산은 더 줄 수 있다.

수정 방향: 성장 시간을 먼저 일치시키고 시간표를 포함한 일 단위 생산을 검산한다.
“밭 네 칸으로 다섯 명 유지”를 고정할지, 기존 수치나 목표를 고칠지 결정한다.
또한 요리 조건의 “배고프지 않음”은 허기 수치가 없는 현재 구조에서 의미를 정의해야 한다.

### R10. 진행 중 습격을 저장·로드로 이어갈 정보가 없다 — P1

근거: ARCHITECTURE 23 SaveData (1234~1262행); MVP_SPEC 32.

저장 형식에는 lastRaid와 raidsFired만 있고 진행 중 몬스터·도달 기록·습격 상태가 없다.
예를 들어 레벨 2 습격 중 레벨 3 종을 치면 명세상 자동 저장이 발생할 수 있다.
재로드 시 이미 발동한 습격은 다시 시작하지 않지만 남은 몬스터와 종료 결과도 복원할 수 없다.
그 결과 다음 이벤트의 “습격이 끝났다” 조건을 보장하지 못한다.

추가로 NPC 체력·기절 종료 시각, 목수의 당일 수리량, 예약된 주민 도착,
현재 목표와 대화 가능 상태를 저장하거나 재구성하는 계약이 빠져 있다.
현재 Action을 버리는 정책과 별개로 지속되어야 하는 상태다.
시간도 SaveData는 day/hour/minute, 23.4는 gameMinutes 하나로 서로 다르다.

수정 방향: 저장할 최소 지속 상태와 안전한 저장 시점을 명시하고,
종 직후·습격 도중·수리 여덟 번 뒤·자정 전후 로드의 결과를 완료 조건에 포함한다.

| R16. 밤당 보상과 날짜당 보상 불일치 — P2 | MVP_SPEC 18.2 / 22.1; ARCHITECTURE 16.1 | 20시에 잠든 NPC가 자정 뒤 위협·침대 파괴로 깼다가 다시 자면 같은 밤에 날짜가 바뀌어 두 번 받을 수 있다. 달력 날짜가 아니라 취침 구간 식별 기준을 정의한다. |
| R17. 시스템 호출 규칙 자체 충돌 — P2 | ARCHITECTURE 15.1 / 16 / 28.3 / 28.5 | 다른 시스템 변경 호출을 금지하면서 gain과 spend를 직접 호출하도록 한다. 허용된 서비스 API인지 커맨드 전달인지 통일한다. SleepAction에 필요한 감사 포인트 접근도 ActionContext에 없다. |
| R18. Worker 결과 최신성 계약 누락 — P2 | ARCHITECTURE 9.1~9.2 | 요청·결과에 청크 버전이 없고 처리 중 재편집 시 규칙도 없다. 여러 Worker의 오래된 결과가 최신 메시를 덮어쓰지 않도록 버전 검사 또는 청크당 직렬 처리를 명시한다. |

추가 편집 사항:

- TASK-002의 “ARCHITECTURE 33장”은 존재하지 않는다. 폴더 구조는 MVP_SPEC 33장이다.
- ARCHITECTURE 11.1은 통행 조건을 MVP_SPEC 15장으로 연결하지만 그 장은 농사다.
- ARCHITECTURE 25.1의 방 예시는 y=0에서 시작하면서 아래 고체 바닥을 제공하지 않는다. 기본 바닥 생성 규칙도 없어 그대로면 NO_FLOOR다.
- TASK-004는 “22종, id 0~22”라고 쓴다. 공기 포함 23개와 공기 제외 22종을 구분한다.
- NPCContext는 “전부 readonly”라는 설명과 달리 가변 NPC·RoomRegistry를 받는다. 읽기 전용 계약의 실제 타입 범위를 정한다.
- 종의 F 상호작용은 종 UI와 상자 없는 저장소 UI가 동시에 요구된다. 한 화면의 탭 또는 버튼 등 진입 규칙이 필요하다.
- GAME_DESIGN·ADR 012에는 식당의 음식 조건이 남아 있지만 MVP_SPEC 12.3은 명시적으로 제외한다. 수치 예시가 아닌 규칙 차이이므로 적용 범위를 보정한다.
- Accepted 상태의 구 ADR 003 / 007 / 010에는 Phaser UI·unlockBuilding 등 폐기된 구체 예시가 남아 있다. ADR 006처럼 살아남은 원칙과 폐기된 예시를 상단에서 구분한다.

## 방향성에서 검증할 것

### 핵심 장면에 도달하는 시점이 늦다

MVP_SPEC 28장은 첫 주방을 25~45분, 첫 침실을 45~60분에 배치한다.
개발에서도 핵심 취침 검증이 TASK-033에 있다. 목표 경험을 확인하기 전에
메싱·채집·제작·농사·요리·식사까지 오래 구현하고 플레이하게 된다.

권고: TASK-022와 033의 중단 원칙은 유지하되, 기존 디버그 기능과 시험 월드를 이용해
방 하나·침대·주민 한 명의 이동과 취침을 먼저 연결하는 검증 경로를 정한다.
90~120분은 최종 분량 가설로 유지하고 첫 재미를 보기 위한 대기 시간으로 삼지 않는다.
새 콘텐츠를 추가하자는 제안이 아니라 기존 핵심 기능의 검증 순서에 관한 제안이다.

### “자유 건축”과 판정 제약 사이에 의도적인 선택이 필요하다

지형 벽 불인정, 동일 높이 바닥, 방당 타입 하나는 구현 범위를 줄이는 선택이다.
다만 플레이어에게는 흙집·동굴집·침대가 있는 주방이 직관적으로 쓸 수 있는 집일 수 있다.
현재 높은 priority의 가구를 추가하면 Bedroom 타입이 사라져 취침 기능을 잃을 수도 있다.
조건 완화 여부를 지금 임의로 결정하지 말고 TASK-022에서 이 사례를 직접 관찰한다.
방 이름 변경과 기존 시설 사용 가능 여부의 관계도 명시해야 한다.

### 흙벽은 의도와 다른 최적 방어가 될 수 있다

MVP_SPEC 8.2는 종류 기반 terrain 판정으로 흙벽 무적 요새를 막는다고 설명하지만,
39 Test 8은 흙벽으로 완전히 막으면 safetyLevel 100을 주는 것이 의도라고 한다.
후자가 현재 테스트 기준이다. 노동량과 미관으로 균형이 잡힌다는 근거는 아직 없다.

또한 GAME_DESIGN 10.3과 ADR 015의 피해 규모 상한은 MVP 수치·Task에 없다.
21~05시는 200실초이고 판자 하나 파괴는 1.6초이므로, 이동·전투를 제외한 단순 상한은
몬스터 한 마리당 125칸이다. 실제 피해량 예측치는 아니지만 “몇 칸만 부서짐”이
현재 수치에서 보장되지 않는다는 뜻이다. 하루 수리 8칸과 함께 검증해야 한다.

### 첫 레벨업 보상은 핵심 의도를 직접 검증하지 않는다

35.3은 이벤트 60 + 최초 방 인식 40으로 주민의 시설 사용 없이도 80을 채운다.
최초 인식 보너스 자체는 의도된 예외지만, “사용이 성장의 원인”이라는 강조와 다르다.
따라서 레벨 2 도달을 취침·사용 루프 성공의 증거로 삼으면 안 된다.
TASK-033의 독립적인 관찰 검증을 유지한다.

### 수치 목표를 측정 가능한 가설로 둔다

60 FPS·3ms·5초에는 기준 하드웨어, 브라우저, DPR, 시험 장면이 필요하다.
기존 연구의 번들 크기·다운로드 수는 조사 시점과 빌드 조건이 다른 비교다.
이는 Three.js 선택의 보조 근거이지 우리 성능을 보장하는 측정이 아니다.
6.25%는 채워진 16³ 블록에서 내부 면을 컬링한 비율이며,
AO 때문에 그리디 병합률이 낮아지는 것과는 별개다. 기존 연구는 두 효과를 혼동한다.

Vite 8 / Vitest 3 조합은 [공식 근거 확인 기록](../research/2026-09-22-review-source-check.md)에 따라 재검토한다.
DQB2의 레벨 하락 주장은 이번에는 확인하지 못했다. 오류로 단정하지 않았다.
